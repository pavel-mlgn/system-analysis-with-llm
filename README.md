# Системная аналитика без посредников: работа с кодом через LLM

Четыре LLM получили один и тот же код демо-проекта и пять типовых задач системного аналитика: от паспорта системы до постановки на доработку. Каждое утверждение моделей затем сверялось с исходным кодом.

## Структура репозитория

```
.
├── transfer-limit-system/      код демо-проекта - ровно та версия, которую получили модели
├── experiment/                 входные данные, промпты и ответы моделей по кейсам
│   ├── code.txt                код проекта одним файлом - в таком виде его получали модели
│   ├── 01-recon/               кейс 1. Паспорт системы
│   ├── 02-business-logic/      кейс 2. Бизнес-логика и реестр аномалий
│   ├── 03-specs/               кейс 3. Спецификации: HTTP API, схема БД, контракты сообщений
│   ├── 04-diagrams/            кейс 4. Диаграммы в Mermaid
│   └── 05-change-request/      кейс 5. Постановка на доработку
├── reference/                  эталон и инструменты проверки
│   ├── etalon.md               факты о системе, чек-листы, шкала оценки
│   ├── etalon-verification.md  проверка эталона по коду и на запущенной системе
│   ├── verifier-prompt.md      промпт верификатора
│   ├── score.py                подсчет баллов по вердиктам одного кейса
│   ├── total.py                сводная таблица по всем кейсам
│   └── compare.py              сравнение вердиктов двух верификаторов
├── review/                     результаты проверки
│   ├── _mapping.json           какая буква (A–E) какой модели соответствует в каждом кейсе
│   ├── total.md                итоговая таблица по всем кейсам
│   ├── decisions.md            журнал ручных решений: где верификаторы разошлись и что решено
│   └── <кейс>/
│       ├── anon/               обезличенные ответы, которые видели верификаторы
│       ├── claude/, gemini/    вердикты каждого верификатора
│       ├── compare.md          где вердикты верификаторов разошлись
│       └── final/              итоговые вердикты после ручной сверки
└── LICENSE
```

В папке каждого кейса в `experiment/`:

- `prompt.md` - промпт, одинаковый для всех моделей;
- `answer-<модель>-<режим рассуждения>.md` - ответ модели без правок.

В `review/04-diagrams/` дополнительно лежат `mermaid-report.md` и `mermaid.json`: какие диаграммы в ответах открываются, а какие нет.

## Демо-проект

`transfer-limit-system` - система обработки денежных переводов: три микросервиса и общая библиотека на Java 21, Spring Boot 3.4, Kafka (включая Kafka Streams) и PostgreSQL. Сервисы общаются только через Kafka, у каждого своя база данных.

Проект сделан специально для эксперимента: популярные открытые репозитории модели могли видеть при обучении и "вспомнить", а не прочитать. Архитектура повторяет учебный проект [piomin/sample-spring-kafka-microservices](https://github.com/piomin/sample-spring-kafka-microservices): три сервиса, общий топик Kafka и объединение результатов через Kafka Streams. Предметная область, бизнес-логика, модель данных и код написаны заново.

Запуск: `docker compose up -d --build` в папке `transfer-limit-system/`.

## Как проводился эксперимент

- **Входные данные.** Модели получали файл `experiment/code.txt`: 57 файлов проекта (исходники, конфигурация, миграции БД, Dockerfile, docker-compose), около 25 тыс. токенов. README, LICENSE и служебные файлы сборки исключены, чтобы модели работали только с кодом и конфигурацией.
- **Промпты** универсальные: в них нет знаний о конкретной системе, их можно запускать на любом проекте.
- **Изолированные сессии.** Каждый кейс выполнялся в новом временном или инкогнито-чате, без истории, памяти и пользовательских инструкций.
- **Одна попытка.** Без повторной генерации и уточняющих вопросов.
- **Без внешних источников.** Веб-поиск выключен там, где есть переключатель; кроме того, в каждом промпте есть прямой запрет на поиск.
- **Выбор модели.** Самая сильная модель и максимальный режим рассуждения, доступные в веб-чате.

## Как проверялись ответы

1. **Эталон.** Для проверки составлен эталон (`reference/etalon.md`): факты о системе и чек-лист для каждого кейса. Он составлялся по коду и дорабатывался по ходу эксперимента, все ответы проверены по одной итоговой версии. В чек-листе два уровня: обязательные пункты (без них ответ неполон) и пункты сильного ответа (то, что заметил бы опытный аналитик). Эталон проверен по коду и на запущенной системе, отчет о проверке и внесенные по ее итогам правки - в `reference/etalon-verification.md`.
2. **Обезличивание.** Ответы переименованы в `answer-A.md` … `answer-E.md` и перемешаны, верификаторы не знали, какой модели принадлежит ответ. Соответствие букв моделям - в `review/_mapping.json`. Из ответов ChatGPT при обезличивании убраны служебные метки чата `:chatgpt-content-reference`, их число по каждому ответу записано в поле `markers_removed`. Поэтому файлы в `review/<кейс>/anon/` могут отличаться от исходных ответов в `experiment/`.
3. **Два верификатора.** Каждый ответ независимо проверили Claude Opus 5.5 и Gemini 3.1 Pro по промпту `reference/verifier-prompt.md`. Верификатор получал код, эталон, промпт кейса и ответ и возвращал JSON-вердикт: какие пункты чек-листа закрыты (с цитатой из ответа) и какие ошибки найдены (со ссылкой на код). Вердикты лежат в `review/<кейс>/claude/` и `review/<кейс>/gemini/`.
4. **Ручная сверка.** Все расхождения между верификаторами (`review/<кейс>/compare.md`) разобраны вручную по коду. Ошибка засчитывается, если ее нашел хотя бы один верификатор и она подтвердилась при ручной сверке. Итоговые вердикты - в `review/<кейс>/final/`, все решения по расхождениям - в `review/decisions.md`.
5. **Подсчет баллов.** Баллы считает скрипт `reference/score.py`, а не модель. Шкала (раздел 0 эталона):
   - все группы обязательных пунктов закрыты - 7 баллов; группа закрыта частично - −0,5; не закрыта - −1;
   - каждый пункт сильного ответа - +1;
   - ошибки: неточность −0,5; мелкая ошибка −1; выдуманная проблема −1; галлюцинация −2; искажение бизнес-правила −2; отступление от промпта −0,5; неоткрывающаяся диаграмма Mermaid −1.

   Итог кейса - набранные баллы в процентах от максимума кейса. Максимумы по кейсам: 13, 16, 16, 14 и 17, всего 76.

   Колонка "Обязательное" в статье считает закрытые атомы обязательных групп. Группа K5-M7 (открытые вопросы) закрыта при 3 атомах из 5 и дает не больше 3 пунктов, поэтому обязательных пунктов в статье 102, а атомов в вердиктах 104.

## Как пересчитать итог

```bash
cd reference
python3 total.py ../review --out ../review/total.md
```

`total.py` берет итоговые вердикты из `review/<кейс>/final/` и `review/04-diagrams/mermaid.json` и строит сводную таблицу. Результат совпадает с `review/total.md`.

Где в репозитории найти цифры из статьи:

| В статье | В репозитории |
|---|---|
| Итоговая таблица: баллы по кейсам и общий процент (процент по кейсу = балл / максимум кейса) | `review/total.md` |
| Совпадение верификаторов (94–98% пунктов чек-листа) | `review/<кейс>/compare.md` |
| Ручные решения по расхождениям | `review/decisions.md` |
| Неоткрывающиеся диаграммы | `review/04-diagrams/mermaid-report.md` |
| Факты о системе и чек-листы | `reference/etalon.md` |

## Как воспроизвести

1. Откройте новый чат без истории и памяти (временный или инкогнито-режим).
2. Приложите файл `experiment/code.txt`.
3. Вставьте текст `prompt.md` нужного кейса без изменений.

Модели регулярно обновляются, поэтому ваши результаты могут отличаться от опубликованных.

## Как добавить модель

Результаты в статье относятся к прогонам 05.10.2026 (тег `v1.0`). Новую модель или новую версию уже проверенной модели можно добавить в общую таблицу, если соблюдать те же условия.

1. **Прогон.** Те же `experiment/code.txt` и `prompt.md` без изменений, новый чат без истории и памяти, одна попытка, веб-поиск выключен. Ответы положить в `experiment/<кейс>/answer-<модель>-<режим рассуждения>.md`. Если модель уже есть в таблице и это повторный прогон, добавить в имя дату (`answer-<модель>-<режим>-<ГГГГ-ММ>.md`), чтобы не затереть прежний ответ. Прогон записать в таблицу "Прогоны".
2. **Эталон не менять.** Проценты сравнимы, только пока эталон один и тот же. Верные утверждения, которых нет в эталоне, дают 0 баллов (раздел 0.1 эталона). Если эталон все же нужно дополнить, перепроверить придется все ответы, включая старые.
3. **Обезличивание и проверка.** Ответ получает следующую свободную букву (F, G, …) в `review/<кейс>/anon/`, соответствие записывается в `review/_mapping.json`. Поле `model` для нового прогона должно быть новым (например, с датой), иначе `total.py` смешает новый и старый прогоны в одной строке таблицы. Ответ проверяют два верификатора по `reference/verifier-prompt.md`, их вердикты сравнивает `reference/compare.py`. Расхождения разбираются вручную по тому же правилу, решения дописываются в `review/decisions.md`, итоговый вердикт кладется в `review/<кейс>/final/`. Для кейса 4 нужно проверить, открываются ли диаграммы, и записать результат в `review/04-diagrams/mermaid.json`.
4. **Контроль проверки.** Если верификаторы обновились с момента исходной проверки, вместе с новым ответом стоит перепроверить один-два старых. Если их баллы совпали с прежними, новой проверке можно доверять. Дату проверки и версии верификаторов записать рядом с прогоном.
5. **Пересчет.** Добавить читаемое название модели в словарь `NAMES` в `reference/total.py` и запустить `python3 total.py ../review --out ../review/total.md` из папки `reference/`. Новая строка появится в общей таблице, максимум по кейсам останется 76.

После публикации код, эталон и ответы открыты и могут попасть в обучающие данные новых моделей. Высокий результат модели, вышедшей позже публикации, стоит проверить на признаки того, что она вспоминает, а не читает код, например на дословные формулировки из эталона.
