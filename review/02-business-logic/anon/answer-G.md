# Анализ бизнес-логики

В коде найдены **7 точек входа**: три HTTP-эндпоинта, три обработчика входящих сообщений и один потоковый обработчик итоговых решений. Задачи по расписанию и самостоятельные точки входа в `transfer-common` не найдены.

## 1. Точки входа

### ТОЧКА ВХОДА: TransferController.create()

*(transfer-service/src/main/java/com/example/transfer/controller/TransferController.java — create(), duplicate(), publishNew(); transfer-service/src/main/java/com/example/transfer/controller/TransferRequest.java)*

**Триггер:** HTTP-запрос `POST /transfers`.

**Алгоритм:**

1. Проверяются обязательные реквизиты запроса, положительность и точность суммы, формат валюты.
2. Если валюта не указана, используется `RUB`.
3. По переданному идентификатору ищется существующий перевод.
4. Если перевод уже существует, его реквизиты сравниваются с реквизитами запроса:
   - при расхождении возвращается конфликт;
   - при совпадении и статусе `NEW` перевод повторно передаётся на обработку;
   - при совпадении и любом другом статусе повторная передача не выполняется.
5. Если перевод отсутствует, он сохраняется со статусом `NEW`; одновременно создаётся первая запись истории.
6. После сохранения перевод передаётся на дальнейшую обработку. Ожидание подтверждения передачи составляет до 10 секунд.
7. При одновременном создании перевода с тем же идентификатором и возникновении конфликта уникальности запись повторно ищется и обрабатывается как уже существующая.

**Бизнес-правила:**

- **БП-1:** Если не заполнены идентификатор перевода, отправитель, получатель или сумма, сумма неположительна либо имеет более 13 целых и более 2 дробных разрядов, или указанная валюта не состоит из трёх заглавных латинских букв, то запрос отклоняется с HTTP 400 без создания перевода.
- **БП-2:** Если валюта не указана, то используется `RUB`.
- **БП-3:** Если идентификатор новый, то перевод и начальная запись истории сохраняются со статусом `NEW` до передачи перевода на обработку.
- **БП-4:** Если новый перевод сохранён и успешно передан на обработку, то возвращается HTTP 201.
- **БП-5:** Если идентификатор уже существует, но отправитель, получатель, сумма или валюта отличаются, то возвращается HTTP 409, а повторная обработка не запускается.
- **БП-6:** Если повторный запрос полностью совпадает с существующим переводом и его статус `NEW`, то перевод повторно передаётся на обработку.
- **БП-7:** Если повторный запрос полностью совпадает с существующим переводом и его статус отличен от `NEW`, то повторная передача на обработку не выполняется.
- **БП-8:** Если повторный запрос совпадает с существующим переводом и необходимая для статуса `NEW` повторная передача успешна, то возвращается HTTP 200 с существующим переводом.
- **БП-9:** Если событие о новом или повторно обрабатываемом переводе не удалось передать, то возвращается HTTP 503; сохранённый перевод остаётся в статусе `NEW`, а ответ предлагает повторить запрос с тем же идентификатором.
- **БП-10:** Если при одновременном создании возник конфликт уникальности идентификатора, то выполняется повторный поиск перевода и применяются правила обработки существующей записи; если запись по-прежнему не найдена, возвращается внутренняя ошибка.

**Данные:**

- Читается `transfers` по `id`.
- Для нового перевода заполняются `transfers.id`, `sender_id`, `recipient_id`, `amount`, `currency`, `status`, `created_at`, `updated_at`.
- Добавляется запись `transfer_history` со `stage = NEW`, `status = NEW` и тем же временем, что у создания перевода.
- При повторных запросах поля существующего перевода не изменяются.

**Исходы:**

- HTTP 201 — новый перевод сохранён и передан на обработку.
- HTTP 200 — запрос является допустимым повтором существующего перевода.
- HTTP 400 — запрос не прошёл проверку.
- HTTP 409 — идентификатор занят переводом с другими параметрами.
- HTTP 503 — перевод сохранён или найден, но передать его на обработку не удалось.
- HTTP 500 — непредусмотренная ошибка сохранения или другая необработанная ошибка.

### ТОЧКА ВХОДА: TransferController.all()

*(transfer-service/src/main/java/com/example/transfer/controller/TransferController.java — all(); transfer-service/src/main/java/com/example/transfer/repository/TransferRepository.java)*

**Триггер:** HTTP-запрос `GET /transfers`.

**Алгоритм:**

1. Загружаются все сохранённые переводы.
2. Список сортируется по времени создания: сначала самые новые.
3. Возвращается список без истории по каждому переводу.

**Бизнес-правила:**

- **БП-11:** Если запрошен список переводов, то возвращаются все переводы в порядке убывания времени создания; при отсутствии записей возвращается пустой список.

**Данные:** читаются все записи `transfers`; изменений нет.

**Исходы:**

- HTTP 200 — список переводов, возможно пустой.
- HTTP 500 — ошибка чтения или другая необработанная ошибка.

### ТОЧКА ВХОДА: TransferController.getById()

*(transfer-service/src/main/java/com/example/transfer/controller/TransferController.java — getById())*

**Триггер:** HTTP-запрос `GET /transfers/{id}`.

**Алгоритм:**

1. По идентификатору ищется перевод.
2. Если перевод не найден, возвращается «не найдено».
3. Если перевод найден, загружается его история.
4. История упорядочивается по стадиям `NEW → LIMIT → SCREENING → FINAL`, а внутри стадии — по времени изменения.
5. Возвращаются текущее состояние перевода и его история.

**Бизнес-правила:**

- **БП-12:** Если перевод с запрошенным идентификатором отсутствует, то возвращается HTTP 404.
- **БП-13:** Если перевод найден, то возвращается HTTP 200 с переводом и историей, упорядоченной по стадиям `NEW`, `LIMIT`, `SCREENING`, `FINAL`, затем по времени внутри стадии.

**Данные:** читаются `transfers` и `transfer_history`; изменений нет.

**Исходы:**

- HTTP 200 — перевод и история; история может быть пустой только при отсутствии записей в данных.
- HTTP 404 — перевод не найден.
- HTTP 500 — ошибка чтения или другая необработанная ошибка.

### ТОЧКА ВХОДА: TransferEventListener.onEvent()

*(transfer-service/src/main/java/com/example/transfer/listener/TransferEventListener.java — onEvent(); transfer-service/src/main/java/com/example/transfer/service/TransferTrackingService.java — recordServiceResult(), applyFinalStatus())*

**Триггер:** входящее сообщение из `transfers`, `limit-results` или `screening-results`.

**Алгоритм:**

1. Для результата лимитной проверки определяется стадия `LIMIT`, для результата проверки отправителя — `SCREENING`.
2. Если перевод результата не найден, результат пропускается.
3. Если запись соответствующей стадии уже есть, результат считается повтором и пропускается.
4. Первый результат каждой проверки добавляется в историю; у перевода изменяется только время обновления, текущий статус остаётся прежним.
5. Сообщение `NEW` из `transfers` не приводит к дополнительным изменениям.
6. Для любого сообщения из `transfers` со статусом, отличным от `NEW`:
   - неизвестный перевод пропускается;
   - при уже существующей стадии `FINAL` сообщение пропускается;
   - иначе полученные статус, источник решения и пояснение становятся текущими, а в историю добавляется `FINAL`.

**Бизнес-правила:**

- **БП-14:** Если для известного перевода впервые получен результат лимитной проверки или проверки отправителя, то результат добавляется в историю соответствующей стадии, а у перевода обновляется только `updated_at`.
- **БП-15:** Если результат проверки относится к неизвестному переводу, то он пропускается без записи истории.
- **БП-16:** Если результат для той же стадии уже был записан, то последующий результат этой стадии пропускается, а первый сохраняется.
- **БП-17:** Если из `transfers` получено сообщение со статусом `NEW`, то дополнительные изменения состояния и истории не выполняются.
- **БП-18:** Если для известного перевода впервые получено сообщение из `transfers` со статусом, отличным от `NEW`, то этот статус применяется как окончательный и добавляется запись истории `FINAL`.
- **БП-19:** Если окончательный статус относится к неизвестному переводу, то он пропускается.
- **БП-20:** Если запись `FINAL` уже существует, то последующий окончательный статус пропускается, а первый сохраняется.

**Данные:**

- Читаются `transfers` и `transfer_history`.
- При первом результате проверки добавляется `transfer_history` со стадией `LIMIT` или `SCREENING`; обновляется `transfers.updated_at`.
- При первом окончательном событии обновляются `transfers.status`, `decided_by`, `message_info`, `updated_at`; добавляется `transfer_history` со стадией `FINAL`.
- Для `NEW`, неизвестных переводов и повторов изменений нет.

**Исходы:**

- Результат проверки записан в историю.
- Окончательный статус применён.
- Сообщение пропущено как повторное, относящееся к неизвестному переводу или как `NEW`.
- Для неожиданного имени источника предусмотрено только предупреждение; в рамках объявленной подписки эта ветка не достигается.
- При ошибке обработки настроены до трёх повторов с паузой 1 секунда; после исчерпания попыток сообщение направляется в `transfers.DLT`, `limit-results.DLT` или `screening-results.DLT` соответственно.

### ТОЧКА ВХОДА: DecisionTopologyConfig.decisionStream()

*(transfer-service/src/main/java/com/example/transfer/config/DecisionTopologyConfig.java — decisionStream(); transfer-service/src/main/java/com/example/transfer/service/TransferDecisionService.java — decide())*

**Триггер:** поступление пары результатов лимитной проверки и проверки отправителя с одинаковым ключом сообщения, если их метки времени попадают в 10-секундное окно. Дополнительного времени ожидания опоздавших записей не предусмотрено.

**Алгоритм:**

1. Для объединённой пары сравниваются результаты двух проверок.
2. Если обе проверки успешны, перевод считается завершённым.
3. Если обе проверки отклонили перевод, формируется отказ с объединёнными причинами.
4. Если отклонила только одна проверка, перевод отменяется с указанием этой проверки и её причины.
5. Для любых других сочетаний результатов формируется отмена с пояснением `UNEXPECTED_RESULT`.
6. Итоговое решение передаётся в `transfers`.
7. Если пара не образовалась, отдельное решение по истечении окна не формируется.

**Бизнес-правила:**

- **БП-21:** Если результаты двух проверок объединены по одинаковому ключу в пределах 10-секундного окна, то для этой пары формируется итоговое решение.
- **БП-22:** Если оба результата `APPROVED`, то итоговый статус `COMPLETED`, источник решения и пояснение очищаются.
- **БП-23:** Если оба результата `DECLINED`, то итоговый статус `DENIED`, источник решения не указывается, а причины объединяются через `; `.
- **БП-24:** Если лимитная проверка дала `DECLINED`, а проверка отправителя — `APPROVED`, то итоговый статус `CANCELLED`, источник `limit`, используется причина лимитной проверки.
- **БП-25:** Если лимитная проверка дала `APPROVED`, а проверка отправителя — `DECLINED`, то итоговый статус `CANCELLED`, источник `screening`, используется причина проверки отправителя.
- **БП-26:** Если сочетание результатов отличается от четырёх предусмотренных, то итоговый статус `CANCELLED`, источник не указывается, а пояснение содержит `UNEXPECTED_RESULT` и оба полученных результата.
- **БП-27:** Если подходящая пара результатов не образовалась, то итоговое решение не формируется; отдельного результата по тайм-ауту в коде нет.

**Данные:** таблицы БД не читаются и не изменяются. Итоговое событие создаётся на основе данных результата лимитной проверки; статус, источник решения и пояснение заменяются согласно правилам.

**Исходы:**

- `COMPLETED`.
- `DENIED`.
- `CANCELLED` по решению `limit`.
- `CANCELLED` по решению `screening`.
- `CANCELLED` с `UNEXPECTED_RESULT`.
- Отсутствие итогового события, если пара не объединена.
- Запись, которую потоковый обработчик не смог прочитать, пропускается согласно настройке `LogAndContinueExceptionHandler`; отдельная обработка такой записи в коде не найдена.

### ТОЧКА ВХОДА: limit-service TransferEventsListener.onEvent()

*(limit-service/src/main/java/com/example/limit/listener/TransferEventsListener.java — onEvent(); limit-service/src/main/java/com/example/limit/service/LimitLedger.java — decide(), settle(); limit-service/src/main/java/com/example/limit/service/LimitService.java — onNewTransfer(), sendAndWait())*

**Триггер:** входящее сообщение из `transfers`. Статус `NEW` запускает лимитную проверку; любой другой статус рассматривается как событие завершения.

**Алгоритм для `NEW`:**

1. По идентификатору перевода ищется ранее сохранённое решение.
2. Если решение уже есть, повторная проверка и изменение использованных лимитов не выполняются; отправляется сохранённое решение.
3. Если сумма отсутствует или неположительна, сохраняется отказ `INVALID_AMOUNT`; в записи решения сумма заменяется нулём, состояние — `NONE`.
4. Для допустимой суммы загружается использование лимитов отправителя. Если записи нет, создаётся новая с нулевыми счётчиками.
5. Дневной и месячный счётчики актуализируются по текущей дате сервера.
6. Сначала проверяется дневной лимит `50 000,00`, затем месячный — `200 000,00`.
7. При превышении сохраняется отказ без резервирования суммы.
8. Если оба лимита позволяют операцию, сумма прибавляется к обоим счётчикам, а решение сохраняется как `APPROVED` с состоянием `RESERVED`.
9. Сохранённое решение передаётся в `limit-results`; ожидание подтверждения — до 10 секунд.

**Алгоритм для статуса, отличного от `NEW`:**

1. Ищется сохранённое решение по идентификатору перевода.
2. Если решения нет или его состояние не `RESERVED`, завершение игнорируется.
3. Для активного резерва:
   - `COMPLETED` переводит резерв в `COMMITTED`, использованные лимиты не уменьшаются;
   - `CANCELLED` или `DENIED` переводит резерв в `RELEASED` и освобождает сумму с учётом даты резервирования;
   - другой непустой статус оставляет резерв без изменений.
4. При освобождении сначала актуализируются текущие дневной и месячный периоды, затем сумма вычитается только из счётчиков соответствующего периода, не ниже нуля.

**Бизнес-правила:**

- **БП-28:** Если для повторного `NEW` уже существует запись решения, то возвращается сохранённые решение и причина, а счётчики и состояние резерва не изменяются.
- **БП-29:** Если сумма отсутствует или неположительна, то сохраняется `DECLINED` с причиной `INVALID_AMOUNT`, состоянием `NONE` и нулевой суммой; использование лимитов не изменяется.
- **БП-30:** Если для отправителя с допустимой суммой ещё нет учёта использования, то создаётся запись с нулевыми дневным и месячным счётчиками и текущими датами периодов.
- **БП-31:** Если текущая дата отличается от даты последнего дневного сброса, то дневной счётчик обнуляется, а дата сброса заменяется текущей.
- **БП-32:** Если текущий месяц отличается от месяца последнего месячного сброса, то месячный счётчик обнуляется, а дата сброса заменяется текущей.
- **БП-33:** Если текущее дневное использование плюс сумма перевода больше `50 000,00`, то сохраняется `DECLINED` с причиной `DAILY_LIMIT_EXCEEDED`; сумма не резервируется, месячный лимит в этой ветке не проверяется.
- **БП-34:** Если дневной лимит не превышен, но текущее месячное использование плюс сумма больше `200 000,00`, то сохраняется `DECLINED` с причиной `MONTHLY_LIMIT_EXCEEDED`; сумма не резервируется.
- **БП-35:** Если обе расчётные суммы не превышают соответствующие лимиты, включая равенство лимиту, то сохраняется `APPROVED` с состоянием `RESERVED`, а сумма прибавляется к дневному и месячному использованию.
- **БП-36:** Если при завершении перевода запись решения не найдена, то событие завершения пропускается.
- **БП-37:** Если состояние решения отличается от `RESERVED`, то событие завершения пропускается; повторное завершение не изменяет состояние.
- **БП-38:** Если активный резерв получает `COMPLETED`, то его состояние становится `COMMITTED`, а занятые дневной и месячный лимиты сохраняются.
- **БП-39:** Если активный резерв получает `CANCELLED` или `DENIED`, то его состояние становится `RELEASED`, а исходная сумма резерва освобождается по правилам соответствующего периода.
- **БП-40:** Если дата резервирования совпадает с текущей датой, то после актуализации периодов сумма вычитается из дневного и месячного счётчиков, но не ниже нуля.
- **БП-41:** Если дата резервирования отличается от текущей, но месяц совпадает, то старая сумма не вычитается из текущего дневного счётчика, а из месячного вычитается с ограничением не ниже нуля.
- **БП-42:** Если месяц резервирования отличается от текущего, то старая сумма не вычитается из счётчиков текущих периодов после их актуализации.
- **БП-43:** Если активный резерв получает непустой статус, отличный от `COMPLETED`, `CANCELLED` и `DENIED`, то завершение не выполняется и состояние остаётся `RESERVED`.

**Данные:**

- Читаются `reservations` по `transfer_id` и `sender_usage` по `sender_id`.
- При новом решении добавляется `reservations`: `amount`, `decision`, `reason`, `state`, `reserved_on`, `created_at`, `updated_at`.
- При допустимой сумме сохраняется `sender_usage`, включая выполненные сбросы, даже если решение — отказ.
- При одобрении изменяются `sender_usage.daily_used`, `monthly_used`.
- При завершении изменяются `reservations.state`, `updated_at`; при освобождении также изменяются счётчики `sender_usage`.

**Исходы:**

- Сохранённое решение повторно отправлено без нового резервирования.
- `DECLINED`: `INVALID_AMOUNT`, `DAILY_LIMIT_EXCEEDED` или `MONTHLY_LIMIT_EXCEEDED`.
- `APPROVED` с активным резервом.
- Резерв переведён в `COMMITTED` или `RELEASED`.
- Завершение пропущено из-за отсутствия решения, уже завершённого/отсутствующего резерва или неподдерживаемого статуса.
- При пустом статусе активного резерва возникает ошибка переключения по статусу; при отсутствии записи использования при освобождении также возникает ошибка.
- При ошибке обработки выполняются повторы, затем исходное сообщение направляется в `transfers.DLT`. Если решение уже сохранено, а сбой произошёл при его отправке, сохранённое решение остаётся в БД.

### ТОЧКА ВХОДА: screening-service TransferEventsListener.onEvent()

*(screening-service/src/main/java/com/example/screening/listener/TransferEventsListener.java — onEvent(); screening-service/src/main/java/com/example/screening/service/ScreeningJournal.java — check(); screening-service/src/main/java/com/example/screening/service/ScreeningService.java — onNewTransfer(), sendAndWait())*

**Триггер:** входящее сообщение из `transfers`. Проверка выполняется только для `NEW`; остальные статусы игнорируются.

**Алгоритм:**

1. По идентификатору перевода ищется ранее сохранённая проверка.
2. Если проверка уже существует, её результат используется повторно без нового обращения к списку блокировок.
3. Если проверки нет, по идентификатору отправителя ищется запись блокировки.
4. При наличии блокировки сохраняется `DECLINED` с причиной `SENDER_BLOCKED`.
5. При отсутствии блокировки сохраняется `APPROVED` без причины.
6. Сохранённый результат передаётся в `screening-results`; ожидание подтверждения — до 10 секунд.
7. Для статуса, отличного от `NEW`, никаких действий не выполняется.

**Бизнес-правила:**

- **БП-44:** Если для повторного `NEW` уже существует сохранённая проверка, то используется её результат, а новая проверка блокировки не выполняется.
- **БП-45:** Если отправитель присутствует в `blocked_senders`, то сохраняется `DECLINED` с причиной `SENDER_BLOCKED`.
- **БП-46:** Если отправитель отсутствует в `blocked_senders`, то сохраняется `APPROVED` без причины.
- **БП-47:** Если получен статус, отличный от `NEW`, то проверка отправителя и изменение данных не выполняются.

**Данные:**

- Читаются `screening_checks` по `transfer_id` и `blocked_senders` по `sender_id`.
- Для новой проверки добавляется `screening_checks` с `result`, `reason`, `checked_at`.
- Повторная проверка не изменяет данные.
- Миграцией добавляются заблокированные отправители `5`, `13`, `21`, `34`, `42`. Сохранённая в `blocked_senders.reason` причина блокировки при проверке не используется.

**Исходы:**

- `APPROVED`.
- `DECLINED` с `SENDER_BLOCKED`.
- Повторно отправлен ранее сохранённый результат.
- Сообщение не `NEW` проигнорировано.
- При ошибке обработки выполняются повторы, затем исходное сообщение направляется в `transfers.DLT`. Если проверка уже сохранена, а сбой произошёл при отправке результата, запись проверки остаётся в БД.

Отдельные точки входа для блокировки или разблокировки отправителей в коде не найдены.

# 2. Сводный реестр

## 2.1. Полный список бизнес-правил

### Transfer-service

- **БП-1:** Если обязательные реквизиты запроса отсутствуют или нарушены ограничения суммы и формата валюты, то запрос отклоняется с HTTP 400 без создания перевода.
- **БП-2:** Если валюта не указана, то используется `RUB`.
- **БП-3:** Если идентификатор новый, то перевод и начальная история сохраняются со статусом `NEW` до передачи на обработку.
- **БП-4:** Если новый перевод сохранён и успешно передан на обработку, то возвращается HTTP 201.
- **БП-5:** Если идентификатор уже существует, но параметры перевода отличаются, то возвращается HTTP 409 без повторной обработки.
- **БП-6:** Если повтор совпадает с переводом в статусе `NEW`, то перевод повторно передаётся на обработку.
- **БП-7:** Если повтор совпадает с переводом в статусе, отличном от `NEW`, то повторная передача не выполняется.
- **БП-8:** Если допустимый повтор обработан, включая необходимую повторную передачу `NEW`, то возвращается HTTP 200 с существующим переводом.
- **БП-9:** Если событие передать не удалось, то возвращается HTTP 503, а сохранённый перевод остаётся `NEW` для повтора с тем же идентификатором.
- **БП-10:** Если одновременное создание вызвало конфликт уникальности, то выполняется повторный поиск и обработка как существующего перевода; если запись не найдена, возвращается ошибка.
- **БП-11:** Если запрошен список переводов, то возвращаются все записи по убыванию времени создания или пустой список.
- **БП-12:** Если перевод по идентификатору отсутствует, то возвращается HTTP 404.
- **БП-13:** Если перевод найден, то возвращаются перевод и история в порядке стадий `NEW`, `LIMIT`, `SCREENING`, `FINAL`, затем по времени внутри стадии.
- **БП-14:** Если впервые получен результат проверки известного перевода, то он записывается в историю соответствующей стадии, а у перевода обновляется только `updated_at`.
- **БП-15:** Если результат проверки относится к неизвестному переводу, то он пропускается.
- **БП-16:** Если стадия проверки уже записана, то последующий результат этой стадии пропускается.
- **БП-17:** Если из `transfers` получен `NEW`, то дополнительные изменения состояния и истории не выполняются.
- **БП-18:** Если для известного перевода впервые получен статус из `transfers`, отличный от `NEW`, то он применяется как окончательный и записывается в `FINAL`.
- **БП-19:** Если окончательный статус относится к неизвестному переводу, то он пропускается.
- **БП-20:** Если `FINAL` уже существует, то последующий окончательный статус пропускается.
- **БП-21:** Если результаты проверок объединены по ключу в 10-секундном окне, то для пары формируется итоговое решение.
- **БП-22:** Если оба результата `APPROVED`, то формируется `COMPLETED` без источника и пояснения.
- **БП-23:** Если оба результата `DECLINED`, то формируется `DENIED` без источника и с объединёнными причинами.
- **БП-24:** Если лимит отклонён, а отправитель одобрен, то формируется `CANCELLED` с источником `limit` и причиной лимитной проверки.
- **БП-25:** Если лимит одобрен, а отправитель отклонён, то формируется `CANCELLED` с источником `screening` и причиной проверки отправителя.
- **БП-26:** Если сочетание результатов нестандартно, то формируется `CANCELLED` с `UNEXPECTED_RESULT`.
- **БП-27:** Если подходящая пара не образовалась, то итоговое решение не формируется.

### Limit-service

- **БП-28:** Если решение для `NEW` уже существует, то используется сохранённое решение без изменения счётчиков и состояния.
- **БП-29:** Если сумма отсутствует или неположительна, то сохраняется `DECLINED / INVALID_AMOUNT / NONE` с нулевой суммой без изменения использования.
- **БП-30:** Если учёта использования отправителя нет, то для допустимой суммы создаётся запись с нулевыми счётчиками.
- **БП-31:** Если изменилась календарная дата, то дневной счётчик обнуляется.
- **БП-32:** Если изменился календарный месяц, то месячный счётчик обнуляется.
- **БП-33:** Если дневное использование с новой суммой превышает `50 000,00`, то сохраняется отказ `DAILY_LIMIT_EXCEEDED` без резервирования.
- **БП-34:** Если дневной лимит пройден, но месячное использование с новой суммой превышает `200 000,00`, то сохраняется отказ `MONTHLY_LIMIT_EXCEEDED` без резервирования.
- **БП-35:** Если оба лимита пройдены, включая равенство границе, то сохраняется `APPROVED / RESERVED`, а сумма добавляется к обоим счётчикам.
- **БП-36:** Если при завершении нет записи решения, то событие пропускается.
- **БП-37:** Если решение не находится в `RESERVED`, то событие завершения пропускается.
- **БП-38:** Если активный резерв завершается статусом `COMPLETED`, то он становится `COMMITTED`, а использование лимитов сохраняется.
- **БП-39:** Если активный резерв завершается статусом `CANCELLED` или `DENIED`, то он становится `RELEASED`, а сумма освобождается.
- **БП-40:** Если резерв создан в текущую дату, то при освобождении сумма вычитается из обоих счётчиков не ниже нуля.
- **БП-41:** Если дата другая, но месяц текущий, то при освобождении сумма вычитается только из месячного счётчика.
- **БП-42:** Если месяц резервирования не текущий, то старая сумма из счётчиков текущих периодов не вычитается.
- **БП-43:** Если получен другой непустой статус завершения, то активный резерв остаётся `RESERVED`.

### Screening-service

- **БП-44:** Если проверка для `NEW` уже существует, то используется её сохранённый результат без новой проверки блокировки.
- **БП-45:** Если отправитель заблокирован, то сохраняется `DECLINED / SENDER_BLOCKED`.
- **БП-46:** Если отправитель не заблокирован, то сохраняется `APPROVED` без причины.
- **БП-47:** Если получен статус, отличный от `NEW`, то проверка не выполняется.

## 2.3. Реестр аномалий

### АН-01. Отсутствие завершения при непарном или опоздавшем результате

- **Описание:** итоговое решение создаётся только для пары результатов в 10-секундном окне. Обработки истечения окна и завершения по одному результату нет.
- **Сценарий:** одна проверка не вернула результат, результат был пропущен из-за ошибки чтения или второй результат поступил слишком поздно.
- **Последствие:** перевод остаётся `NEW`. Если лимит был одобрен, резерв остаётся `RESERVED`, а сумма продолжает уменьшать доступный дневной и месячный лимит и может препятствовать последующим переводам.
- **Серьёзность:** критичная.
- **Затронутые сервисы:** transfer-service, limit-service, screening-service.
- **Код:** `transfer-service/.../DecisionTopologyConfig.java — decisionStream()`; `transfer-service/.../application.yml — LogAndContinueExceptionHandler`; `limit-service/.../LimitLedger.java — settle()`.

### АН-02. Сохранённое решение может остаться неопубликованным

- **Описание:** лимитное решение и проверка отправителя сохраняются до отправки результата. После исчерпания повторов автоматическая повторная публикация сохранённого решения не предусмотрена. Для начального HTTP-перевода восстановление зависит от повторного запроса клиента.
- **Сценарий:** БД успешно зафиксировала решение, но отправка результата завершилась ошибкой; все повторы исчерпаны. Для HTTP — клиент получил 503 и не повторил запрос.
- **Последствие:** пара итогового решения не образуется, перевод остаётся `NEW`; одобренный лимит может остаться занятым. Сохранённое решение само по себе обработку не возобновляет.
- **Серьёзность:** критичная.
- **Затронутые сервисы:** все три сервиса.
- **Код:** `limit-service/.../LimitService.java — onNewTransfer(), sendAndWait()`; `screening-service/.../ScreeningService.java — onNewTransfer(), sendAndWait()`; `transfer-service/.../TransferController.java — create(), publishNew()`. Обработчики DLT и задачи повторной публикации в коде не найдены.

### АН-03. Окончательный статус принимается без проверки допустимости и предшествующих решений

- **Описание:** любое событие из `transfers` со статусом, отличным от `NEW`, может стать `FINAL`. Не проверяются ни перечень допустимых статусов, ни наличие истории `LIMIT` и `SCREENING`.
- **Сценарий:** для существующего перевода поступает `COMPLETED` или нестандартный статус до объединения проверок. Первое событие создаёт `FINAL`, последующее штатное решение пропускается как повтор.
- **Последствие:** перевод может завершиться без подтверждения обеих проверок либо получить статус вне перечня OpenAPI. При нестандартном статусе лимитный резерв остаётся `RESERVED`; при преждевременном `COMPLETED` последующая отмена может не изменить текущий статус.
- **Серьёзность:** критичная.
- **Затронутые сервисы:** transfer-service, limit-service.
- **Код:** `transfer-service/.../TransferEventListener.java — onEvent()`; `transfer-service/.../TransferTrackingService.java — applyFinalStatus()`; `limit-service/.../LimitLedger.java — settle()`; `transfer-service/.../openapi/transfer-api.yaml`.

### АН-04. Пара решений объединяется только по ключу сообщения

- **Описание:** не проверяется совпадение идентификаторов и реквизитов переводов внутри двух результатов.
- **Сценарий:** два сообщения имеют одинаковый ключ, но разные идентификаторы, отправителей или суммы. Итог создаётся на основе данных лимитного результата с использованием решения второй проверки.
- **Последствие:** к переводу может быть применено решение, относящееся к другим исходным данным; возможны ошибочный статус и ошибочное завершение резерва.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** все три сервиса.
- **Код:** `transfer-service/.../DecisionTopologyConfig.java — decisionStream()`; `transfer-service/.../TransferDecisionService.java — decide()`.

### АН-05. Повторный `NEW` сверяется с прежним решением только по идентификатору

- **Описание:** limit-service и screening-service не проверяют, совпадают ли отправитель, сумма и другие реквизиты повторного события с первоначальными.
- **Сценарий:** в `transfers` поступает повтор с тем же идентификатором, но другой суммой или отправителем. Возвращается прежнее одобрение или отказ.
- **Последствие:** решение может не соответствовать содержимому обрабатываемого события: лимит был зарезервирован для одной суммы, а проверка отправителя выполнялась для другого лица.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** limit-service, screening-service, transfer-service.
- **Код:** `limit-service/.../LimitLedger.java — decide()`; `limit-service/.../LimitService.java — onNewTransfer()`; `screening-service/.../ScreeningJournal.java — check()`; `screening-service/.../ScreeningService.java — onNewTransfer()`.

### АН-06. Лимиты объединяют разные валюты без пересчёта

- **Описание:** учёт использования ведётся только по отправителю, без валюты. Проверяется числовое значение суммы; валютная конверсия отсутствует. HTTP проверяет только формат валюты, но не перечень поддерживаемых валют.
- **Сценарий:** один отправитель выполняет переводы, например, в `RUB` и `USD`; обе суммы складываются в одни счётчики. Также допускается любое значение из трёх заглавных букв.
- **Последствие:** смешиваются разные денежные единицы, поэтому экономическая корректность одобрения или отказа не обеспечивается. Требуемая базовая валюта лимитов в коде не определена.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** transfer-service, limit-service.
- **Код:** `transfer-service/.../TransferRequest.java`; `limit-service/.../LimitLedger.java — decide()`; `limit-service/.../SenderUsage.java`; `limit-service/.../db/changelog/001-create-tables.sql`.

### АН-07. Не проверяются допустимость участников и самоперевод

- **Описание:** идентификаторы перевода, отправителя и получателя проверяются только на наличие. Положительность идентификаторов и различие отправителя и получателя не проверяются.
- **Сценарий:** передаются нулевые или отрицательные идентификаторы либо одинаковые отправитель и получатель. При прохождении лимита и отсутствии блокировки перевод может получить `COMPLETED`.
- **Последствие:** в данных появляются операции с потенциально недопустимыми участниками; самоперевод расходует лимит отправителя.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** все три сервиса.
- **Код:** `transfer-service/.../TransferRequest.java`; `transfer-service/.../TransferTrackingService.java — createTransfer()`.

### АН-08. Сообщения для ещё отсутствующих данных пропускаются без отложенной обработки

- **Описание:** неизвестный перевод в истории, неизвестный перевод в окончательном событии и отсутствующая запись резерва при завершении приводят к обычному пропуску, а не к ошибке или повтору.
- **Сценарий:** результат или окончательное событие поступило раньше соответствующей записи. Метод завершается штатно; при появлении записи старое сообщение повторно этим кодом не запрашивается.
- **Последствие:** могут отсутствовать история или окончательный статус, а завершение резерва может не выполниться. Восстановление зависит от последующих событий, которые не гарантированы.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** transfer-service, limit-service.
- **Код:** `transfer-service/.../TransferTrackingService.java — recordServiceResult(), applyFinalStatus()`; `limit-service/.../LimitLedger.java — settle()`.

### АН-09. Тестовые блокировки включены в основной набор миграций

- **Описание:** файл с тестовыми данными подключён к основному `changelog-master.yaml` без отдельного условия или профиля.
- **Сценарий:** миграции выполняются на пустой БД в любой среде. Отправители `5`, `13`, `21`, `34`, `42` автоматически становятся заблокированными.
- **Последствие:** все новые переводы этих отправителей получают `DECLINED / SENDER_BLOCKED` до изменения данных; отдельного интерфейса разблокировки в коде нет.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** screening-service, transfer-service.
- **Код:** `screening-service/src/main/resources/db/changelog/002-insert-test-data.sql`; `screening-service/src/main/resources/db/changelog/changelog-master.yaml`; `screening-service/.../ScreeningJournal.java — check()`.

### АН-10. Ошибка отправки в DLT не считается неуспехом восстановления

- **Описание:** для обработчика ошибок установлено `setFailIfSendResultIsError(false)`.
- **Сценарий:** основная обработка многократно завершилась ошибкой, после чего отправка исходного сообщения в DLT также не удалась.
- **Последствие:** не гарантируется наличие сообщения в DLT для последующего разбора; при отсутствии другого восстановления перевод или резерв может остаться в промежуточном состоянии.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** все три сервиса.
- **Код:** `KafkaErrorHandlingConfig.java — kafkaErrorHandler()` в `transfer-service`, `limit-service` и `screening-service`.

### АН-11. Период лимита зависит от даты и часового пояса сервера обработки

- **Описание:** используется текущая дата обработки, а не дата создания перевода; явный бизнесовый часовой пояс не задан.
- **Сценарий:** перевод создан до полуночи или границы месяца, а обработан после неё, либо компоненты работают в разных часовых поясах.
- **Последствие:** перевод может быть отнесён не к ожидаемому пользователю дню или месяцу; спорные ситуации на границе периода кодом не разрешаются.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** limit-service.
- **Код:** `limit-service/.../LimitLedger.java — decide(), settle()`; `limit-service/.../SenderUsage.java — lazyReset(), release()`.

### АН-12. Порядок истории в HTTP-ответе не является строго хронологическим

- **Описание:** после загрузки истории по времени выполняется повторная сортировка по стадии.
- **Сценарий:** окончательное событие записано раньше одного из результатов проверки. В ответе `FINAL` всё равно будет расположен после `LIMIT` и `SCREENING`, хотя его `changed_at` может быть раньше.
- **Последствие:** порядок строк отражает жизненный цикл стадий, а не фактическую последовательность обработки; для аудита необходимо дополнительно учитывать `changed_at`.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** transfer-service.
- **Код:** `transfer-service/.../TransferController.java — getById()`.

### АН-13. Конкретная причина блокировки отправителя теряется в результате проверки

- **Описание:** запись блокировки содержит причину, но результат всегда получает только `SENDER_BLOCKED`.
- **Сценарий:** для отправителя сохранено, например, `Fraud detected` или `Sanctions list`; в результат проверки это пояснение не передаётся.
- **Последствие:** по истории и итоговому решению нельзя определить конкретное основание блокировки без отдельного чтения БД.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** screening-service, transfer-service.
- **Код:** `screening-service/.../ScreeningJournal.java — check()`; `screening-service/.../BlockedSender.java`.

### АН-14. Объединение причин двух отказов не обрабатывает отсутствующие пояснения

- **Описание:** при двух `DECLINED` причины объединяются строковой операцией без проверки на отсутствие значения.
- **Сценарий:** в нештатном входном результате хотя бы одна причина отсутствует. В собственных реализациях проверок отказы всегда имеют причину, поэтому сценарий относится к нестандартным сообщениям.
- **Последствие:** итоговое пояснение может содержать текст `null` и быть непонятным пользователю.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** transfer-service.
- **Код:** `transfer-service/.../TransferDecisionService.java — decide()`.

### АН-15. Исходная некорректная сумма не сохраняется в лимитном решении

- **Описание:** при нулевой или отрицательной сумме в `reservations.amount` записывается `0`, а не полученное значение.
- **Сценарий:** непосредственно в `transfers` поступает `NEW` с отрицательной суммой; HTTP такое событие не пропустил бы.
- **Последствие:** по записи решения нельзя восстановить фактически отклонённую сумму; нулевое значение может быть ошибочно воспринято как исходное.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** limit-service.
- **Код:** `limit-service/.../LimitLedger.java — decide()`; `limit-service/.../Reservation.java`.
