## ТОЧКА ВХОДА: `TransferController.create()`

**Триггер:** HTTP `POST /transfers`, тело — `TransferRequest`.

**Алгоритм:**
1. Проверить, есть ли уже перевод с таким `id`.
2. Если есть — сравнить отправителя, получателя, сумму и валюту с запросом.
3. Если параметры совпадают:
   - если существующий перевод в статусе `NEW` — повторно опубликовать событие `NEW`;
   - вернуть существующий перевод.
4. Если параметры не совпадают — вернуть конфликт.
5. Если перевода нет — создать запись перевода в статусе `NEW`, зафиксировать историю этапа `NEW`, опубликовать событие `NEW`.
6. Если при создании возникла конкурентная вставка — найти существующий перевод и обработать его как повторный запрос.
7. Если публикация события `NEW` не удалась — вернуть сообщение о том, что перевод сохранён, и предложить повторить запрос с тем же `id`.

**Бизнес-правила:**
- БП-1: Если перевод с указанным `id` уже существует и параметры совпадают, новый перевод не создаётся; возвращается существующий.
- БП-2: Если перевод с указанным `id` уже существует, но параметры отличаются, возвращается конфликт `409`.
- БП-3: Если существующий перевод в статусе `NEW` и параметры совпадают, событие `NEW` публикуется повторно.
- БП-4: Если перевода с `id` нет, создаётся новый перевод в статусе `NEW`; валюта по умолчанию — `RUB`, если не указана.
- БП-5: При создании перевода фиксируется запись истории этапа `NEW`.
- БП-6: После создания перевода публикуется событие `NEW`; при неудаче публикации возвращается `503` с сообщением, что перевод сохранён и нужно повторить запрос с тем же `id`.
- БП-7: Если при создании возникает нарушение целостности из-за конкурентного duplicate, выполняется поиск существующего перевода и обработка как duplicate.
- БП-8: Валидация входного запроса: `id`, `senderId`, `recipientId` обязательны; `amount` положительный, до 13 целых и 2 дробных; `currency` ровно 3 заглавные латинские буквы, если указана.

**Данные:**
- Читается: `transfers.id`, `transfers.sender_id`, `transfers.recipient_id`, `transfers.amount`, `transfers.currency`, `transfers.status`, `transfers.created_at`.
- Изменяется: `transfers` (новая запись), `transfer_history` (новая запись этапа `NEW`).

**Исходы:**
- `201 Created` — перевод создан и событие `NEW` опубликовано.
- `200 OK` — перевод уже существует, параметры совпадают.
- `409 Conflict` — перевод с таким `id` уже есть, но параметры другие.
- `400 Bad Request` — ошибка валидации запроса.
- `503 Service Unavailable` — Kafka недоступна, перевод сохранён.
- `500 Internal Server Error` — прочие необработанные ошибки.

**Данные:**
- Читается: `transfers`, `transfer_history`.

**Исходы:**
- `200 OK` — перевод и история.

- `500 Internal Server Error` — необработанная ошибка.

## ТОЧКА ВХОДА: `TransferEventListener.onEvent()`

**Триггер:** входящее сообщение из топиков `transfers`, `limit-results`, `screening-results`; группа `transfer-tracker`.

**Алгоритм:**
1. Определить топик, из которого пришло сообщение.
2. Если топик `limit-results` — записать результат этапа `LIMIT`.
3. Если топик `screening-results` — записать результат этапа `SCREENING`.
4. Если топик `transfers`:
   - если статус `NEW` — ничего не делать;
   - если статус не `NEW` — применить финальный статус.
5. Если топик неизвестен — залогировать предупреждение.

**Бизнес-правила:**
- БП-12: При получении события из топика `limit-results` записывается результат этапа `LIMIT`.
- БП-13: При получении события из топика `screening-results` записывается результат этапа `SCREENING`.
- БП-14: При получении события из топика `transfers` со статусом не `NEW` применяется финальный статус перевода.
- БП-15: При получении события из топика `transfers` со статусом `NEW` ничего не делается.
- БП-16: При получении события из неизвестного топика пишется предупреждение, обработка не выполняется.
- БП-17: Результат этапа `LIMIT`/`SCREENING` записывается только если перевод существует и запись по этому этапу ещё не существует.
- БП-18: Финальный статус применяется только если перевод существует и запись этапа `FINAL` ещё не существует.

**Данные:**
- Читается: `transfers.id`, `transfer_history.transfer_id`, `transfer_history.stage`.
- Изменяется: `transfer_history` (записи `LIMIT`, `SCREENING`, `FINAL`), `transfers` (`status`, `decided_by`, `message_info`, `updated_at`).

**Исходы:**
- Запись этапа `LIMIT`/`SCREENING` создана.
- Запись этапа пропущена как дубликат.
- Финальный статус применён.
- Финальный статус пропущен как дубликат.
- Перевод не найден — запись пропущена.
- Неизвестный топик — предупреждение.
- Ошибка БД — исключение, возможен retry/DLT.

## ТОЧКА ВХОДА: `DecisionTopologyConfig.decisionStream()`

**Триггер:** потоковая обработка: соединение событий из `limit-results` и `screening-results` по ключу перевода.

**Алгоритм:**
1. Читать события `limit-results`.
2. Соединить их с событиями `screening-results` по ключу перевода.
3. Окно соединения — 10 секунд без grace period.
4. Для каждой пары событий вызвать принятие финального решения.
5. Опубликовать финальное решение в топик `transfers`.

**Бизнес-правила:**
- БП-19: События `limit-results` и `screening-results` сопоставляются по ключу перевода в окне 10 секунд без grace period; только при наличии обоих событий в окне формируется финальное решение.
- БП-20: Если limit `APPROVED` и screening `APPROVED`, финальный статус `COMPLETED`, `decidedBy=null`, `messageInfo=null`.
- БП-21: Если limit `DECLINED` и screening `DECLINED`, финальный статус `DENIED`, `decidedBy=null`, `messageInfo=склейка причин limit и screening через "; "`.
- БП-22: Если limit `DECLINED` и screening `APPROVED`, финальный статус `CANCELLED`, `decidedBy="limit"`, `messageInfo=причина limit`.
- БП-23: Если limit `APPROVED` и screening `DECLINED`, финальный статус `CANCELLED`, `decidedBy="screening"`, `messageInfo=причина screening`.
- БП-24: Во всех остальных комбинациях статусов финальный статус `CANCELLED`, `decidedBy=null`, `messageInfo="UNEXPECTED_RESULT: limit=..., screening=..."`.
- БП-25: Сформированное финальное решение публикуется в топик `transfers`.

**Данные:**
- Читается: `limit-results`, `screening-results`.
- Изменяется: `transfers` (публикация финального решения).

**Исходы:**
- Финальное решение опубликовано.
- Соединение не произошло из-за окна 10 секунд — финальное решение не сформировано.
- Ошибка десериализации — сообщение пропущено (в настройках streams).

## ТОЧКА ВХОДА: `TransferEventsListener.onEvent()` в limit-service

**Триггер:** входящее сообщение из топика `transfers`; группа `limit`.

**Алгоритм:**
1. Если статус `NEW` — принять решение по лимитам.
2. Если статус не `NEW` — урегулировать ранее зарезервированную сумму.

**Бизнес-правила:**
- БП-26: При получении события `NEW` запускается принятие решения по лимитам.
- БП-27: При получении события не `NEW` запускается урегулирование ранее зарезервированной суммы.
- БП-28: При принятии решения по лимитам, если по `transferId` уже есть запись, возвращается ранее сохранённое решение.
- БП-29: Если сумма перевода `null` или `<= 0`, перевод отклоняется с причиной `INVALID_AMOUNT`.
- БП-30: Перед проверкой лимитов выполняется ленивый сброс дневного и месячного использования, если сменился день/месяц.
- БП-31: Если дневное использование + сумма > дневного максимума, перевод отклоняется с причиной `DAILY_LIMIT_EXCEEDED`.
- БП-32: Иначе, если месячное использование + сумма > месячного максимума, перевод отклоняется с причиной `MONTHLY_LIMIT_EXCEEDED`.
- БП-33: Иначе перевод одобряется, сумма резервируется в дневном и месячном использовании.
- БП-34: Решение по лимиту публикуется в топик `limit-results` со статусом `APPROVED`/`DECLINED`, `decidedBy="limit"`, `messageInfo=причина`.
- БП-35: При урегулировании, если запись не найдена, обработка пропускается.
- БП-36: При урегулировании, если резерв не в состоянии `RESERVED`, обработка пропускается.
- БП-37: При финальном статусе `COMPLETED` резерв помечается `COMMITTED`.
- БП-38: При финальном статусе `CANCELLED` или `DENIED` зарезервированная сумма освобождается: дневное и месячное использование уменьшаются с учётом даты резерва, но не ниже нуля; резерв помечается `RELEASED`.
- БП-39: При прочих финальных статусах урегулирование не выполняется, пишется предупреждение.

**Данные:**
- Читается: `transfers` (сообщение), `reservations`, `sender_usage`.
- Изменяется: `reservations`, `sender_usage`; публикуется `limit-results`.

**Исходы:**
- Решение `APPROVED`/`DECLINED` сохранено и опубликовано.
- Дубликат `NEW` — возвращено сохранённое решение и опубликовано повторно.
- Резерв переведён в `COMMITTED` или `RELEASED`.
- Урегулирование пропущено: нет записи, не `RESERVED`, неожиданный статус.
- Ошибка БД/Kafka — исключение, возможен retry/DLT.

## 2. ТАБЛИЦЫ РЕШЕНИЙ

### 2.1. Финальное решение по лимиту и скринингу (`TransferDecisionService.decide`)

| limit status | screening status | Итог | decidedBy | messageInfo |
|---|---|---|---|---|
| APPROVED | APPROVED | COMPLETED | null | null |
| DECLINED | DECLINED | DENIED | null | `limit.messageInfo + "; " + screening.messageInfo` |
| DECLINED | APPROVED | CANCELLED | limit | limit.messageInfo |
| APPROVED | DECLINED | CANCELLED | screening | screening.messageInfo |
| любая иная комбинация | любая иная комбинация | CANCELLED | null | `UNEXPECTED_RESULT: limit=..., screening=...` |

Решение принимается в `TransferDecisionService.decide`.

### 2.2. Решение по лимитам (`LimitLedger.decide`)

| Условие | Решение | reason | state | Изменение usage |
|---|---|---|---|---|
| Запись по `transferId` уже есть | возврат существующей | — | — | не меняется |
| amount == null или amount <= 0 | DECLINED | INVALID_AMOUNT | NONE | не меняется |
| dailyUsed + amount > dailyMax | DECLINED | DAILY_LIMIT_EXCEEDED | NONE | не меняется |
| dailyUsed + amount <= dailyMax, но monthlyUsed + amount > monthlyMax | DECLINED | MONTHLY_LIMIT_EXCEEDED | NONE | не меняется |
| dailyUsed + amount <= dailyMax и monthlyUsed + amount <= monthlyMax | APPROVED | null | RESERVED | dailyUsed и monthlyUsed увеличиваются на amount |

Решение принимается в `LimitLedger.decide`.

### 2.3. Проверка отправителя (`ScreeningJournal.check`)

| Условие | Результат | reason |
|---|---|---|
| Запись по `transferId` уже есть | возврат существующей | — |
| Отправитель найден в `blocked_senders` | DECLINED | SENDER_BLOCKED |
| Отправитель не найден в `blocked_senders` | APPROVED | null |

Решение принимается в `ScreeningJournal.check`.

### 2.4. Обработка повторного POST /transfers (`TransferController.duplicate`)

| Перевод существует | Параметры совпадают | Статус существующего | Результат |
|---|---|---|---|
| да | да | NEW | опубликовать NEW повторно, вернуть 200 |
| да | да | не NEW | вернуть 200 без публикации |
| да | нет | любой | вернуть 409 |
| нет | — | — | создать новый перевод |

Решение принимается в `TransferController.create` / `TransferController.duplicate`.

### 2.5. Урегулирование резерва (`LimitLedger.settle`)

| Запись найдена | state | Финальный статус | Действие |
|---|---|---|---|
| нет | — | любой | пропустить |
| да | не RESERVED | любой | пропустить |
| да | RESERVED | COMPLETED | markCommitted |
| да | RESERVED | CANCELLED | release usage, markReleased |
| да | RESERVED | DENIED | release usage, markReleased |
| да | RESERVED | иной | предупреждение, ничего не делать |

Решение принимается в `LimitLedger.settle`.

### 2.6. Освобождение использования (`SenderUsage.release`)

| reservedOn | today | dailyUsed | monthlyUsed |
|---|---|---|---|
| совпадает с today | — | уменьшается на amount, не ниже 0 | — |
| не совпадает | — | не уменьшается | — |
| — | тот же месяц, что reservedOn | — | уменьшается на amount, не ниже 0 |
| — | другой месяц | — | не уменьшается |

Перед этим выполняется `lazyReset(today)`. Решение принимается в `SenderUsage.release`.

### 2.7. Запись истории (`TransferTrackingService.recordServiceResult`, `applyFinalStatus`)

| Перевод найден | Запись stage уже есть | Действие |
|---|---|---|
| нет | — | пропустить |
| да | да | пропустить как дубликат |
| да | нет | создать запись stage и обновить updatedAt (для FINAL — также status, decidedBy, messageInfo) |

Решение принимается в `TransferTrackingService.recordServiceResult` и `TransferTrackingService.applyFinalStatus`.
