Ты — опытный системный аналитик, который впервые видит этот проект.
К сообщению приложен исходный код проекта: все файлы в одном
текстовом файле, каждый файл начинается со строки
«===== FILE: путь =====». Изучи все файлы.

Сформируй спецификации в виде таблиц. Только структуры данных,
без описания бизнес-логики (это вне рамок этой задачи).

1. HTTP API

Для каждого эндпоинта — отдельная таблица:

Эндпоинт: [HTTP-метод] [URL]
Описание: [одно предложение]

Параметры запроса:
| Параметр | Источник (body/path/query) | Тип | Обязательный | Описание |

Параметры ответа:
| Поле | Тип | Nullable | Описание |

Коды ответа:
| Код | Условие |

2. СХЕМА БД

Для каждой таблицы:

Таблица: [имя] (база: [имя базы])
Описание: [одно предложение]

| Колонка | Тип | PK | FK | Unique | NOT NULL | Default | Index | Описание |

Ограничения уровня таблицы (составные ключи, составные UNIQUE), если есть:
| Ограничение | Колонки |

Допустимые значения (если поле содержит фиксированный набор значений):
| Колонка | Значения |

3. КОНТРАКТЫ СООБЩЕНИЙ

Для каждого канала асинхронного взаимодействия (топик, очередь):

Канал: [имя]
| Свойство | Значение |
(тип канала, число партиций, политика хранения / очистки, ключ сообщения, сериализация ключа и значения, отправители, получатели с группой потребителей)

Формат сообщения:
| Поле | Тип | Nullable | Описание | Пример |

Если асинхронного взаимодействия в проекте нет — так и напиши.

4. РАСХОЖДЕНИЯ КОНТРАКТА API С КОДОМ

Если в проекте есть файл контракта API (например, OpenAPI) — сверь
его с кодом и перечисли расхождения:
| Элемент | В контракте | В коде |

Если файла контракта нет или расхождений нет — так и напиши.

Правила:
- Никакой прозы между таблицами. Только заголовок и таблица (исключение — одна строка в разделах 3 и 4, если раздел неприменим или расхождений нет).
- Не описывай бизнес-логику, алгоритмы, аномалии — только структуры (исключение — раздел 4).
- Если несколько каналов используют одинаковый формат сообщения — опиши его один раз и сошлись на него.
- Типы данных — из кода (типы языка для сообщений, SQL-типы для БД,
  JSON-типы для HTTP API).
- Если в коде отсутствует валидация — в колонке "Обязательный"
  пиши "нет (валидация отсутствует)".

Общие правила:
- Опирайся только на приложенный код. Не додумывай и не дополняй
  по аналогии с другими проектами.
- Если чего-то в коде нет или это нельзя определить — так и пиши:
  «в коде не найдено» или «требует уточнения».
- Ссылаясь на код, указывай файл и класс/метод, а не номер строки.
- Отвечай на русском языке.
- Не используй поиск в интернете и другие внешние источники:
  вся нужная информация — в приложенном коде.
