## 1. ЦЕЛЬ ДОРАБОТКИ

Ввести ограничение на максимальную сумму одного перевода для всех отправителей с отклонением переводов, превышающих установленный порог, по понятной причине. Предоставить REST API для просмотра текущих значений всех лимитов (разового, дневного, месячного) и их динамического изменения без перезапуска сервисов.

## 2. ПРЕДПОСЫЛКИ

1. В текущей реализации проверяются только кумулятивные дневной и месячный лимиты отправителя (`limit-service/src/main/java/com/example/limit/service/LimitLedger.java`, `LimitLedger.decide`), из-за чего отправитель может израсходовать весь дневной лимит одной транзакцией.
2. Значения дневного (`50000.00`) и месячного (`200000.00`) лимитов жёстко заданы в конфигурационном файле (`limit-service/src/main/resources/application.yml`) и считываются при старте приложения (`limit-service/src/main/java/com/example/limit/service/LimitLedger.java`, `LimitLedger`), что не позволяет просматривать и изменять их в рантайме через API или сохранять изменения между перезапусками.

## 3. SCOPE ИЗМЕНЕНИЙ

* **Сервис `limit-service`** — модифицируемый: добавление веб-слоя и валидации, перенос хранения лимитов из конфигурации в БД, реализация проверки максимальной суммы одного перевода и REST API управления лимитами.
* **Таблица БД `limitdb.limit_settings`** — новая: хранение актуальных значений лимитов (максимальная сумма одного перевода, дневной лимит, месячный лимит).
* **Таблица БД `limitdb.reservations`** — модифицируемая (на уровне данных): в колонку `reason` добавляется новое допустимое значение причины отклонения `MAX_SINGLE_AMOUNT_EXCEEDED` (изменение DDL не требуется).
* **REST API управления лимитами (`/limits`)** — новый: эндпоинты получения и изменения значений лимитов.
* **Контракт сообщений Kafka (топики `limit-results`, `transfers`)** — модифицируемый (на уровне справочника значений): новое значение причины отказа `MAX_SINGLE_AMOUNT_EXCEEDED` в поле `messageInfo` (структура сообщения `Transfer` не меняется).
* **Инфраструктура (`docker-compose.yml`)** — модифицируемый: публикация HTTP-порта для `limit-service`.
* **Сервис `transfer-service`** — без изменений (либо модифицируемый при выборе варианта с проксированием API, см. раздел 4).
* **Сервис `screening-service`** — без изменений.
* **Модуль `transfer-common`** — без изменений.

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### 4.1. Размещение REST API для управления лимитами

**Вариант 1 (Рекомендуемый): Размещение REST API непосредственно в `limit-service`**
* **Описание:** Подключить веб-зависимости и валидацию в `limit-service` (сейчас в `limit-service/pom.xml` подключён только `spring-boot-starter`), опубликовать внешний порт сервиса в `docker-compose.yml` (например, `8081:8080`) и реализовать эндпоинты `/limits` внутри `limit-service`.
* **Плюсы:**
  * Высокая связность: управление лимитами и их проверка находятся в одном сервисе и работают с одной БД (`limitdb`).
  * Отсутствие синхронных межсервисных вызовов или сложной асинхронной синхронизации настроек через Kafka.
  * Мгновенная консистентность: обновлённые лимиты сразу доступны при обработке следующего сообщения из топика `transfers`.
* **Минусы:**
  * Появляется вторая внешняя HTTP-точка входа в систему (помимо `transfer-service` на порту `8080`).

**Вариант 2: Размещение REST API в `transfer-service` с проксированием в `limit-service`**
* **Описание:** Реализовать эндпоинты в `transfer-service` (где уже есть `spring-boot-starter-web` и порт `8080`), а запросы перенаправлять в `limit-service` по HTTP или через Kafka.
* **Плюсы:**
  * Единая точка входа (API Gateway) для внешних клиентов.
* **Минусы:**
  * При синхронном HTTP-вызове всё равно требуется поднимать веб-сервер в `limit-service`, появляется жёсткая временная связанность между сервисами.
  * При взаимодействии через Kafka невозможно просто реализовать синхронный `GET /limits` и валидацию `PUT /limits` без дублирования хранения лимитов в `transferdb`.

### 4.2. Способ хранения значений лимитов

**Вариант 1 (Рекомендуемый): Хранение в новой таблице БД `limitdb`**
* **Описание:** Перенести хранение лимитов из `limit-service/src/main/resources/application.yml` в новую таблицу `limit_settings` в `limitdb` с предзаполнением начальных значений через Liquibase.
* **Плюсы:**
  * Изменения, внесённые через REST API, сохраняются при перезапуске контейнера `limit-service`.
  * Обеспечивается консистентность данных при горизонтальном масштабировании `limit-service`.
* **Минусы:**
  * Требуется дополнительное чтение из БД при проверке перевода (при необходимости оптимизируется кэшированием).

**Вариант 2: Хранение в памяти (`in-memory`) с инициализацией из `application.yml`**
* **Описание:** Хранить значения в памяти сервиса и перезаписывать их при вызове REST API.
* **Плюсы:**
  * Не требуется миграция БД.
* **Минусы:**
  * Все изменения, выполненные через API, теряются при перезапуске `limit-service` и сбрасываются к значениям из `application.yml`.

*Далее в разделе 5 описание приведено для рекомендуемых вариантов (размещение API в `limit-service` и хранение лимитов в БД `limitdb`).*

### 5.1. limit-service

#### Изменения в БД

1. Добавить в `limit-service/src/main/resources/db/changelog/changelog-master.yaml` новую миграцию для создания таблицы `limit_settings` (хранит одну строку с глобальными настройками лимитов для всех отправителей):

   * `monthly_max` — `DECIMAL(15,2) NOT NULL`, ограничение `CHECK (monthly_max > 0)`.
   * `updated_at` — `TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP`.
   * Ограничение целостности соотношения лимитов на уровне таблицы: `CHECK (max_single_amount <= daily_max AND daily_max <= monthly_max)`.
2. Миграция начальных данных:
   * Добавить в таблицу `limit_settings` начальную запись с текущими значениями из `limit-service/src/main/resources/application.yml`:
     * `id = 1`
     * `daily_max = 50000.00`
     * `monthly_max = 200000.00`
     * `max_single_amount = 50000.00` (конкретное стартовое значение требует подтверждения бизнеса, см. раздел 8; до уточнения равно дневному лимиту, чтобы не менять текущее поведение при деплое).
3. Удалить статические свойства `limits.daily-max` и `limits.monthly-max` из `limit-service/src/main/resources/application.yml`, чтобы избежать рассинхронизации источника истины.

| `monthlyMax` | `body` | `number (decimal)` | Да | Месячный лимит (`> 0`, максимум 13 знаков до запятой и 2 после, `>= dailyMax`) |

Параметры ответа:
| Поле | Тип | Nullable | Описание |
| :--- | :--- | :--- | :--- |
| `maxSingleAmount` | `number (decimal)` | `false` | Обновлённая максимальная сумма одного перевода |
| `dailyMax` | `number (decimal)` | `false` | Обновлённый дневной лимит |
| `monthlyMax` | `number (decimal)` | `false` | Обновлённый месячный лимит |
| `updatedAt` | `string (datetime)` | `false` | Дата и время применения изменений |

| `500 Internal Server Error` | Внутренняя ошибка сервера |

#### Изменения в бизнес-логике

* При получении события о новом переводе (`status = NEW`) из топика `transfers` система должна считывать актуальные значения `maxSingleAmount`, `dailyMax` и `monthlyMax` из таблицы `limit_settings` в БД, а не из конфигурационного файла.
* При получении повторного события `status = NEW` для уже обработанного `transferId` система должна возвращать ранее сохранённое в таблице `reservations` решение без повторного пересчёта по новым лимитам (сохранение текущей логики идемпотентности в `limit-service/src/main/java/com/example/limit/service/LimitLedger.java`, `LimitLedger.decide`).
* При проверке нового перевода после валидации положительности суммы (`amount > 0`) система должна в первую очередь (до проверки дневного и месячного лимитов) сравнивать сумму перевода `amount` с `maxSingleAmount`.
* При условии `amount > maxSingleAmount` система должна:
  * отклонить перевод с решением `decision = DECLINED`, состоянием `state = NONE` и причиной `reason = MAX_SINGLE_AMOUNT_EXCEEDED`;
  * сохранить запись в таблицу `reservations`;
  * не увеличивать счётчики `daily_used` и `monthly_used` в таблице `sender_usage`;
  * отправить сообщение с результатом проверки (`status = DECLINED`, `decidedBy = limit`, `messageInfo = MAX_SINGLE_AMOUNT_EXCEEDED`) в топик `limit-results`.
* При условии `amount <= maxSingleAmount` система должна выполнить проверку дневного (`dailyUsed + amount > dailyMax` → `DAILY_LIMIT_EXCEEDED`) и месячного (`monthlyUsed + amount > monthlyMax` → `MONTHLY_LIMIT_EXCEEDED`) лимитов по существующим правилам, используя значения `dailyMax` и `monthlyMax` из таблицы `limit_settings`.
* При вызове `PUT /limits` система должна проверять выполнение всех условий:
  * все три параметра (`maxSingleAmount`, `dailyMax`, `monthlyMax`) переданы, строго больше нуля (`> 0`) и имеют не более 13 цифр в целой части и не более 2 в дробной;
  * соблюдается иерархия лимитов: `maxSingleAmount <= dailyMax` и `dailyMax <= monthlyMax`.
* При нарушении любого из условий валидации в `PUT /limits` система должна возвращать статус `400 Bad Request` (в формате `ProblemDetail`) и не изменять значения в БД.
* При успешном обновлении лимитов через `PUT /limits` система должна обновить запись в `limit_settings` (включая `updated_at`) и применять новые пороги ко всем последующим проверяемым переводам со статусом `NEW`. Ранее созданные резервирования (`RESERVED`, `COMMITTED`, `RELEASED`) и накопленные суммы в `sender_usage` не пересчитываются.

#### Изменения в контрактах сообщений

* Топик `limit-results` (объект `Transfer`, `transfer-common/src/main/java/com/example/common/Transfer.java`):
  * Структура сообщения не изменяется.
  * Для поля `messageInfo` (при `status = DECLINED` и `decidedBy = limit`) добавляется новое значение причины отклонения: `MAX_SINGLE_AMOUNT_EXCEEDED`.
* Топик `transfers`:
  * В результирующем событии после объединения потоков (`transfer-service/src/main/java/com/example/transfer/service/TransferDecisionService.java`, `TransferDecisionService.decide`) поле `messageInfo` будет содержать:
    * `MAX_SINGLE_AMOUNT_EXCEEDED` (при `status = CANCELLED`, `decidedBy = limit`, если `screening-service` одобрил перевод);
    * `MAX_SINGLE_AMOUNT_EXCEEDED; SENDER_BLOCKED` (при `status = DENIED`, `decidedBy = null`, если `screening-service` также отклонил перевод).

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

1. **Игнорирование валюты перевода при проверке лимитов:**
   В `transfer-service` при создании перевода (`transfer-service/src/main/java/com/example/transfer/controller/TransferRequest.java`, `TransferRequest`) допускается любая трёхбуквенная валюта (`[A-Z]{3}`, по умолчанию `RUB`). Однако в `limit-service` (`limit-service/src/main/java/com/example/limit/service/LimitLedger.java`, `LimitLedger.decide`) поле `transfer.currency()` полностью игнорируется: суммы переводов в разных валютах суммируются напрямую в `sender_usage` и сравниваются с безвалютными порогами. Новый лимит `maxSingleAmount` и эндпоинты `/limits` будут работать аналогично (без учёта валюты), пока бизнес не определит правила мультивалютности.
2. **Безусловная запись в `sender_usage` при отклонении перевода:**
   В `limit-service` (`limit-service/src/main/java/com/example/limit/service/LimitLedger.java`, `LimitLedger.decide`) объект `SenderUsage` загружается (или создаётся) и сохраняется через `usageRepository.save(usage)` даже тогда, когда перевод отклоняется (`DAILY_LIMIT_EXCEEDED`, `MONTHLY_LIMIT_EXCEEDED`).
   * Если оставить проверку `MAX_SINGLE_AMOUNT_EXCEEDED` внутри того же потока с сохранением `SenderUsage`, то при первом переводе нового отправителя на сумму больше разового лимита в БД будет создаваться лишняя запись `sender_usage` с нулевыми счётчиками, а при конкурентных запросах одного отправителя возможны конфликты оптимистичной блокировки (`@Version` в `SenderUsage`) или `DataIntegrityViolationException` по первичному ключу `sender_id`.
   * Рекомендуется выполнять проверку `amount > maxSingleAmount` до обращения к `sender_usage` (по аналогии с проверкой `INVALID_AMOUNT` в `LimitLedger.decide`), чтобы при превышении разового лимита таблица `sender_usage` не затрагивалась.
3. **Уменьшение дневного или месячного лимита ниже уже накопленного расхода:**
   Если через новый эндпоинт `PUT /limits` уменьшить `dailyMax` или `monthlyMax` до значения, которое меньше уже накопленного `daily_used` / `monthly_used` конкретного отправителя за текущий день/месяц, то:
   * существующие зарезервированные (`RESERVED`) и завершённые (`COMMITTED`) переводы затронуты не будут;
   * при отмене (`CANCELLED` / `DENIED`) ранее зарезервированного перевода сумма корректно вычтется из `daily_used` и `monthly_used` (`limit-service/src/main/java/com/example/limit/domain/SenderUsage.java`, `SenderUsage.release`);
   * любые новые переводы этого отправителя в текущем периоде будут отклоняться по `DAILY_LIMIT_EXCEEDED` / `MONTHLY_LIMIT_EXCEEDED`.

## 7. КРИТЕРИИ ПРИЁМКИ

*Предусловие для кейсов проверки переводов (если не указано иное): установлены лимиты `maxSingleAmount = 15000.00`, `dailyMax = 50000.00`, `monthlyMax = 200000.00`, отправитель не заблокирован в `screening-service`, текущее использование лимитов отправителя равно `0.00`.*

### Проверка максимальной суммы одного перевода
1. **Сумма меньше максимальной суммы одного перевода:**
   Создан перевод на сумму `14999.99` → в `limit-service` создаётся резервирование со статусом `APPROVED` и `state = RESERVED`, `daily_used` и `monthly_used` увеличиваются на `14999.99`, итоговый статус перевода в `transfer-service` становится `COMPLETED` (в `reservations` `state = COMMITTED`).
2. **Граничное значение — сумма равна максимальной сумме одного перевода:**
   Создан перевод на сумму `15000.00` → перевод успешно проходит проверку лимитов (`APPROVED`), резервируется сумма `15000.00`, итоговый статус перевода — `COMPLETED`.
3. **Граничное значение — сумма на 0.01 превышает максимальную сумму одного перевода:**
   Создан перевод на сумму `15000.01` → `limit-service` отклоняет перевод (`decision = DECLINED`, `state = NONE`, `reason = MAX_SINGLE_AMOUNT_EXCEEDED`), счётчики `daily_used` и `monthly_used` отправителя остаются равными `0.00`, итоговый статус перевода в `transfer-service` — `CANCELLED`, `decidedBy = limit`, `messageInfo = MAX_SINGLE_AMOUNT_EXCEEDED`.
4. **Одновременное превышение разового и дневного лимитов:**
   У отправителя уже использовано `40000.00` за день (остаток дневного лимита `10000.00`), создаётся перевод на сумму `20000.00` (`> maxSingleAmount`) → перевод отклоняется с причиной `MAX_SINGLE_AMOUNT_EXCEEDED` (проверка разового лимита срабатывает раньше дневного), `daily_used` остаётся `40000.00`.
5. **Сумма в пределах разового лимита, но превышает остаток дневного лимита:**
   У отправителя уже использовано `40000.00` за день, создаётся перевод на сумму `15000.00` (`<= maxSingleAmount`, но `40000.00 + 15000.00 > 50000.00`) → перевод отклоняется с причиной `DAILY_LIMIT_EXCEEDED`, `daily_used` остаётся `40000.00`.
6. **Одновременный отказ по разовому лимиту и скринингу:**
   Отправитель из списка заблокированных (например, `senderId = 5`) создаёт перевод на сумму `15000.01` → итоговый статус перевода в `transfer-service` становится `DENIED`, `decidedBy = null`, `messageInfo = "MAX_SINGLE_AMOUNT_EXCEEDED; SENDER_BLOCKED"`.

### REST API управления лимитами
7. **Просмотр лимитов по умолчанию (`GET /limits`):**
   После запуска системы без предварительных вызовов `PUT /limits` выполняется `GET /limits` → возвращается `200 OK` с полями `maxSingleAmount`, `dailyMax = 50000.00`, `monthlyMax = 200000.00`, `updatedAt` (не пустой).
8. **Успешное изменение всех лимитов (`PUT /limits`):**
   Выполняется `PUT /limits` с телом `{"maxSingleAmount": 25000.00, "dailyMax": 100000.00, "monthlyMax": 300000.00}` → возвращается `200 OK` с обновлёнными значениями; последующий `GET /limits` возвращает те же значения; новый перевод на сумму `20000.00` (ранее отклонявшийся при лимите `15000.00`) теперь успешно проходит проверку (`COMPLETED`).
9. **Граничное значение при изменении лимитов — равенство порогов:**
   Выполняется `PUT /limits` с телом `{"maxSingleAmount": 50000.00, "dailyMax": 50000.00, "monthlyMax": 50000.00}` → возвращается `200 OK`, лимиты успешно сохраняются.
10. **Сохранение лимитов при перезапуске:**
    После изменения лимитов через `PUT /limits` контейнер `limit-service` перезапускается → `GET /limits` возвращает изменённые через API значения, а не исходные из первой миграции.
11. **Ошибка валидации — разовый лимит больше дневного:**
    Выполняется `PUT /limits` с `maxSingleAmount = 60000.00`, `dailyMax = 50000.00`, `monthlyMax = 200000.00` → возвращается `400 Bad Request` (`application/problem+json`), значения лимитов в БД не изменяются.
12. **Ошибка валидации — дневной лимит больше месячного:**
    Выполняется `PUT /limits` с `maxSingleAmount = 15000.00`, `dailyMax = 250000.00`, `monthlyMax = 200000.00` → возвращается `400 Bad Request`, значения лимитов в БД не изменяются.
13. **Ошибка валидации — нулевые, отрицательные или некорректные по разрядности значения:**
    Выполняется `PUT /limits` со значением `0`, `-100.00`, `null` или `100.123` (более 2 знаков после запятой) в любом из трёх полей → возвращается `400 Bad Request`, значения лимитов в БД не изменяются.
