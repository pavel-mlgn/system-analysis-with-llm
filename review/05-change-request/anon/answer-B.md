# Постановка на доработку: лимит на один перевод и API управления лимитами

## 1. ЦЕЛЬ ДОРАБОТКИ

Для всех отправителей вводится третий лимит — максимальная сумма одного перевода: перевод сверх порога отклоняется сервисом лимитов с отдельной причиной, отличной от причин дневного и месячного лимитов. Все три лимита (дневной, месячный, на один перевод) становятся доступны для просмотра и изменения через REST API. Новые значения начинают действовать без правки конфигурации и перезапуска сервиса.

## 2. ПРЕДПОСЫЛКИ

Доработка закрывает два пробела: нет ограничения на сумму одного перевода, а лимиты нельзя посмотреть и изменить без правки конфигурации и перезапуска.

- Сейчас действуют только накопительные лимиты — дневной 50000.00 и месячный 200000.00, одинаковые для всех отправителей (limit-service, application.yml: `limits.daily-max`, `limits.monthly-max`; проверка в LimitLedger.decide). Отказ происходит только при строгом превышении, поэтому отправитель без переводов за сутки может одним переводом на 50000.00 исчерпать весь дневной лимит.
- Значения лимитов фиксируются при старте limit-service (поля LimitLedger, внедрение через @Value). Изменить их можно только правкой конфигурации и перезапуском, а посмотреть действующие значения средствами системы нельзя. Перезапуск limit-service к тому же небезопасен для переводов в обработке (п. 6.1).
- В limit-service нет HTTP-слоя: в limit-service/pom.xml нет web-стартера, в docker-compose.yml порт сервиса не опубликован. API управления лимитами создаётся с нуля.

## 3. SCOPE ИЗМЕНЕНИЙ

Меняются только limit-service, его БД и окружение; контракты сообщений получают новое значение причины без изменения структуры.

| Компонент | Характер | Описание изменения |
| --- | --- | --- |
| limit-service | модифицируемый | Новая проверка суммы одного перевода; значения лимитов читаются из БД вместо конфигурации; добавляется REST API |
| limitdb: таблица `limit_settings` | новый | Действующие значения трёх лимитов, общие для всех отправителей |
| limitdb: таблица `reservations` | модифицируемый (только данные) | Новое значение `reason` = `SINGLE_TRANSFER_LIMIT_EXCEEDED`; структура не меняется |
| REST API limit-service: `GET /limits`, `PUT /limits` | новый | Просмотр и изменение лимитов, OpenAPI-спецификация API |
| Конфигурация limit-service (application.yml) | модифицируемый | Удаляются `limits.daily-max` и `limits.monthly-max`; задаётся порт HTTP-сервера |
| docker-compose.yml | модифицируемый | Публикуется HTTP-порт limit-service |
| Kafka-топик `limit-results` | модифицируемый (только значения) | Новое значение `messageInfo` при `status` = `DECLINED`; структура Transfer не меняется |
| Kafka-топик `transfers` (итоговые статусы) | модифицируемый (только значения) | Новый код причины транслируется в `messageInfo` статусов `CANCELLED` и `DENIED` |

Не затрагиваются: transfer-service, screening-service, transfer-common, таблица `sender_usage` (обоснование — в 5.2–5.4 и 5.1).

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

Рекомендуется хранить лимиты в limitdb одной записью, API разместить в limit-service, а новую проверку выполнять там же, вместе с дневным и месячным лимитами.

### 4.1. Где хранить лимиты и разместить API

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **А. limit-service + limitdb (рекомендуется)** | Значения хранятся там же, где применяются; изменение подхватывается следующим решением без синхронизации между сервисами; не нужны новые топики и правки transfer-service и transfer-common | В limit-service нужно добавить HTTP-слой и опубликовать порт; у клиентов появляется второй адрес API (шлюза в проекте нет); ещё одна точка входа без аутентификации (п. 6.5) |
| Б. transfer-service + transfer-db, передача значений в limit-service через новый compacted-топик | Единая точка входа (порт 8080); готовые обработка ошибок (ApiExceptionHandler, Problem Details) и OpenAPI-описание | Хранение и применение лимитов разнесены по сервисам; нужен новый контракт и топик, который придётся объявить в сервисах (автосоздание выключено: KAFKA\_AUTO\_CREATE\_TOPICS\_ENABLE=false); limit-service может решать по устаревшим значениям и должен получить их до первого NEW; правки минимум в двух сервисах вместо одного |
| В. Фасад в transfer-service, синхронно проксирующий вызовы в limit-service | Единая точка входа для клиентов | Все минусы варианта А (HTTP-слой в limit-service всё равно нужен) плюс новая синхронная связь между сервисами; имеет смысл позже, если понадобится единый адрес API |

### 4.2. Где проверять максимальную сумму одного перевода

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **А. limit-service при обработке NEW, вместе с дневным и месячным лимитами (рекомендуется)** | Одна точка решений по лимитам и один формат отказа: DECLINED + код причины, итоговый статус, история перевода; отказ виден в GET /transfers и GET /transfers/{id}, как отказы по другим лимитам; контракт POST /transfers не меняется | Отказ асинхронный: клиент узнаёт о нём, запросив статус перевода |
| Б. transfer-service синхронно при POST /transfers (ответ 4xx, перевод не создаётся) | Мгновенный ответ клиенту; заведомо отклоняемые переводы не уходят в обработку | Правило лимита живёт вне limit-service, и transfer-service нужен доступ к значению (синхронный вызов на каждый перевод или копия); отказ не попадает в историю, в отличие от других лимитов; меняется контракт POST /transfers; повтор POST с тем же id после повышения лимита создаст перевод — идемпотентность по id перестаёт распространяться на такие отказы |

### 4.3. Модель хранения значений

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| **А. Одна запись, колонка на каждый лимит (рекомендуется)** | Три значения читаются и меняются атомарно, решение всегда принимается по согласованному набору; соотношение лимитов проверяется в одном запросе и может быть закреплено ограничением БД; структура 1:1 соответствует API | Новый вид лимита потребует миграции схемы (впрочем, он в любом случае потребует доработки логики) |
| Б. Запись на каждый вид лимита («вид — значение») | Новый вид лимита добавляется записью | Согласованность при чтении и изменении нескольких записей нужно обеспечивать отдельно; межполевые проверки не выражаются ограничением БД |

Если бизнес подтвердит потребность в индивидуальных лимитах отправителей (вопрос 8.2), модель хранения нужно пересмотреть до начала разработки.

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

Вся доработка сосредоточена в limit-service; transfer-service, screening-service и transfer-common не меняются.

### 5.1. limit-service

**Изменения в БД**

Новая таблица `limit_settings` — действующие значения лимитов, общие для всех отправителей. В таблице всегда ровно одна запись, и это гарантирует ограничение БД, а не только приложение.

| Колонка | Тип | Ограничения | Описание |
| --- | --- | --- | --- |
| `id` | SMALLINT | PK, NOT NULL, допустимо только значение 1 | Обеспечивает единственность записи |
| `daily_max` | DECIMAL(15,2) | NOT NULL, > 0 | Дневной лимит |
| `monthly_max` | DECIMAL(15,2) | NOT NULL, > 0 | Месячный лимит |
| `single_transfer_max` | DECIMAL(15,2) | NOT NULL, > 0 | Максимальная сумма одного перевода |
| `updated_at` | TIMESTAMP | NOT NULL | Время последнего изменения |

- Тип DECIMAL(15,2) совпадает с суммами в `reservations` и `sender_usage`. Использование не может превысить лимит, поэтому всегда помещается в существующие колонки.
- Ограничение `single_transfer_max ≤ daily_max ≤ monthly_max` добавляется, только если бизнес подтвердит это правило (вопрос 8.3).
- Значения по умолчанию на уровне колонок не задаются: начальные значения задаёт миграция.
- Структура `sender_usage` и `reservations` не меняется; `reservations.reason` (VARCHAR(50)) вмещает новый код длиной 30 символов.

Миграция данных:

- Тестовые данные не нужны. Нужна обязательная для всех окружений миграция, создающая единственную запись: `daily_max` = 50000.00 и `monthly_max` = 200000.00 (текущие значения из application.yml), `single_transfer_max` — значение, согласованное с бизнесом (вопрос 8.1), `updated_at` — время миграции.
- В application-docker.yml и docker-compose.yml переопределений `limits.*` нет. Если на стендах значения переопределены переменными окружения, миграция должна перенести их, а не значения из application.yml; проверить до выкатки (в коде не найдено).

**Изменения в API**

Ошибки обоих эндпоинтов возвращаются в формате Problem Details (application/problem+json), как в transfer-service (ApiExceptionHandler, схема Problem в transfer-api.yaml). Поле `detail` — на русском языке, с указанием поля и нарушенного правила. API описывается OpenAPI-спецификацией по аналогии с transfer-api.yaml; предлагаемый файл — `limit-service/src/main/resources/openapi/limit-api.yaml`.

**Эндпоинт:** `GET /limits`

**Описание:** возвращает действующие значения всех трёх лимитов, общих для всех отправителей.

Параметры запроса: нет.

Параметры ответа:

| Поле | Тип | Nullable | Описание |
| --- | --- | --- | --- |
| `dailyMax` | number (decimal, 2 знака) | нет | Дневной лимит: максимальная сумма одобренных переводов отправителя за сутки |
| `monthlyMax` | number (decimal, 2 знака) | нет | Месячный лимит: максимальная сумма одобренных переводов отправителя за календарный месяц |
| `singleTransferMax` | number (decimal, 2 знака) | нет | Максимальная сумма одного перевода |
| `updatedAt` | string (дата-время, формат как у `createdAt` в API переводов) | нет | Время последнего изменения лимитов |

Коды ответа:

| Код | Условие |
| --- | --- |
| 200 | Значения возвращены |
| 500 | Внутренняя ошибка, например недоступна БД |

**Эндпоинт:** `PUT /limits`

**Описание:** заменяет значения всех трёх лимитов; новые значения применяются к переводам, решение по которым принимается после успешного ответа.

Параметры запроса:

| Параметр | Источник | Тип | Обязательный | Описание |
| --- | --- | --- | --- | --- |
| `dailyMax` | body | number | да | Новый дневной лимит: > 0, не более 13 знаков в целой части и 2 после запятой (как сумма перевода в TransferRequest) |
| `monthlyMax` | body | number | да | Новый месячный лимит, те же ограничения |
| `singleTransferMax` | body | number | да | Новая максимальная сумма одного перевода, те же ограничения |

Параметры ответа: те же поля, что у `GET /limits`, — сохранённые значения и новое `updatedAt`.

Коды ответа:

| Код | Условие |
| --- | --- |
| 200 | Значения прошли проверку и сохранены |
| 400 | Тело отсутствует или не является корректным JSON; любое из трёх полей отсутствует, равно null или не является числом; значение ≤ 0, имеет более 2 знаков после запятой или больше 9999999999999.99; нарушено соотношение лимитов (если правило подтверждено, вопрос 8.3) |
| 500 | Внутренняя ошибка, например недоступна БД |

Удаление лимитов и отключение отдельного лимита не предусматриваются.

**Изменения в бизнес-логике**

- При обработке события NEW с суммой > 0, превышающей `single_transfer_max`, система должна отклонить перевод: в `limit-results` — `status` = DECLINED, `decidedBy` = limit, `messageInfo` = SINGLE\_TRANSFER\_LIMIT\_EXCEEDED; в `reservations` — запись с этой причиной, суммой перевода и состоянием NONE; дневное и месячное использование отправителя не увеличивается.
- При сумме, равной `single_transfer_max`, система не должна отклонять перевод по этому правилу: отказ — только при строгом превышении, как у дневного и месячного лимитов (LimitLedger.decide).
- При нарушении нескольких правил система должна вернуть одну причину — первую в порядке INVALID\_AMOUNT → SINGLE\_TRANSFER\_LIMIT\_EXCEEDED → DAILY\_LIMIT\_EXCEEDED → MONTHLY\_LIMIT\_EXCEEDED (порядок требует подтверждения, вопрос 8.6). Перевод без суммы по-прежнему отклоняется с INVALID\_AMOUNT и не должен приводить к ошибке обработки.
- При принятии решения система должна брать значения всех трёх лимитов из `limit_settings` на момент обработки NEW. Параметры `limits.daily-max` и `limits.monthly-max` удаляются из конфигурации, чтобы не было второго источника значений.
- При успешном `PUT /limits` система должна применять новые значения к решениям, принятым после фиксации изменения, без перезапуска limit-service.
- При изменении лимитов система не должна пересматривать принятые решения и резервы, сбрасывать или пересчитывать `sender_usage`. Если новый дневной (месячный) лимит ниже уже использованной суммы, следующие переводы отправителя отклоняются с DAILY\_LIMIT\_EXCEEDED (MONTHLY\_LIMIT\_EXCEEDED) до смены суток (месяца).
- При повторном событии NEW по уже обработанному переводу система должна вернуть сохранённое решение, даже если лимиты изменились (существующая идемпотентность в LimitLedger.decide сохраняется).
- При итоговом статусе перевода, отклонённого по SINGLE\_TRANSFER\_LIMIT\_EXCEEDED, использование не меняется: резерв не создавался, а обработка итоговых статусов пропускает такие записи (LimitLedger.settle) — доработка не нужна.
- При ошибке валидации `PUT /limits` система не должна менять ни одного значения.
- При каждом изменении лимитов система должна записывать в лог прежние и новые значения — минимальный след изменений до решения по вопросу 8.7.

**Изменения в контрактах сообщений**

- Структура записи Transfer (transfer-common) не меняется.
- `limit-results`: новое значение `messageInfo` = `SINGLE_TRANSFER_LIMIT_EXCEEDED` при `status` = DECLINED и `decidedBy` = limit.
- `transfers`, итоговый статус (формирует transfer-service без изменения логики, TransferDecisionService.decide):
  - отправитель не заблокирован → `CANCELLED`, `decidedBy` = limit, `messageInfo` = `SINGLE_TRANSFER_LIMIT_EXCEEDED`;
  - отправитель заблокирован → `DENIED`, `decidedBy` = null, `messageInfo` = `SINGLE_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED`.
- Перечень причин отказа limit-service после доработки: INVALID\_AMOUNT, SINGLE\_TRANSFER\_LIMIT\_EXCEEDED, DAILY\_LIMIT\_EXCEEDED, MONTHLY\_LIMIT\_EXCEEDED.

**Изменения в конфигурации и развёртывании**

- limit-service получает HTTP-сервер. Порт должен отличаться от порта transfer-service (8080), иначе при локальной разработке сервисы не запустятся на одной машине; предлагается 8081.
- В docker-compose.yml публикуется порт limit-service.
- Выкатка требует перезапуска limit-service, и переводы, созданные во время простоя, могут зависнуть в NEW — порядок выкатки см. п. 6.1.

### 5.2. transfer-service

Изменений нет: код причины из `limit-results` попадает в итоговый статус без изменения логики (TransferDecisionService.decide) и хранится в `message_info` (TEXT) таблиц `transfers` и `transfer_history`; в transfer-api.yaml поле `messageInfo` — строка без перечня значений.

### 5.3. screening-service

Изменений нет: проверка блокировки отправителя не зависит от суммы перевода и лимитов (ScreeningJournal.check).

### 5.4. transfer-common

Изменений нет: причина отказа передаётся в существующем поле `messageInfo` записи Transfer, новые поля не нужны.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

Главный риск — зависание переводов в NEW при задержке или сбое limit-service: он проявится при выкатке доработки и при проблемах с таблицей лимитов (п. 6.1).

### 6.1. Переводы зависают в NEW, если результат limit-service опоздал или не пришёл

**Суть.** Итоговое решение формирует inner join топиков `limit-results` и `screening-results` в окне 10 секунд без grace (DecisionTopologyConfig). Если limit-service опубликовал результат позже чем через 10 с после screening-service (простой, перезапуск, отставание) или не опубликовал вовсе (после трёх повторов сообщение уходит в `transfers.DLT`, KafkaErrorHandlingConfig), итогового статуса не будет.

Перевод остаётся в NEW без таймаута, а если limit-service успел его одобрить, резерв остаётся в RESERVED и занимает дневной и месячный лимит до конца периода. Восстановить перевод можно только повторным `POST /transfers` с тем же id: для переводов в NEW событие публикуется повторно (TransferController).

**Влияние.**

- Выкатка требует перезапуска limit-service, а при старте выполняется миграция, поэтому переводы, созданные во время простоя, зависнут. Выкатывать нужно без входящих переводов либо после выкатки найти переводы в NEW, созданные в окно выкатки, и повторить по ним `POST /transfers`.
- Решение по каждому NEW начинает зависеть от чтения `limit_settings`: без записи или с некорректными значениями зависнут все переводы. Поэтому запись создаётся миграцией, ограничения NOT NULL и > 0 обязательны, удаление через API не предусмотрено.

### 6.2. Валюта перевода не учитывается

**Суть.** Перевод может быть в любой валюте формата \[A-Z\]{3} (TransferRequest), но limit-service сравнивает с лимитом и суммирует в `sender_usage` только сумму, без валюты (LimitLedger.decide, SenderUsage.reserve).

**Влияние.** Новый лимит унаследует эту особенность: перевод 9000.00 USD пройдёт порог 10000.00, а суммы в разных валютах складываются в одни и те же дневной и месячный лимиты. Нужно решение бизнеса (вопрос 8.4).

### 6.3. Отказ по лимиту даёт итоговый статус CANCELLED, а не DENIED

**Суть.** Если отклонил только limit-service, итоговый статус — CANCELLED с `decidedBy` = limit. DENIED бывает лишь при отказе обоих сервисов, и тогда `decidedBy` = null, а причины склеены через «; » (TransferDecisionService.decide).

**Влияние.** Формулировка бизнеса «отклонять» не совпадает со статусом CANCELLED — это нужно учесть в критериях приёмки и ожиданиях клиентов (вопрос 8.5). Потребителям, которым нужна именно причина лимита, при DENIED придётся разбирать составной `messageInfo`.

### 6.4. Причина отказа ограничена 50 символами

**Суть.** Колонка `reservations.reason` — VARCHAR(50) (limit-service, 001-create-tables.sql).

**Влияние.** Код SINGLE\_TRANSFER\_LIMIT\_EXCEEDED длиной 30 символов помещается. Если бизнес захочет причину текстом с суммой и порогом (вопрос 8.5), значение может не поместиться: ошибка записи приведёт к повторам, DLT и зависанию перевода (п. 6.1). Формат причины нужно согласовать до разработки.

### 6.5. В системе нет аутентификации и авторизации

**Суть.** Ни в одном сервисе нет механизмов аутентификации: в pom.xml сервисов соответствующих зависимостей не найдено, API переводов открыт.

**Влияние.** Любой, у кого есть сетевой доступ к limit-service, сможет изменить лимиты для всех отправителей — например, поднять их до максимума. Публикация порта в docker-compose.yml расширяет эту поверхность. Нужно решение бизнеса (вопрос 8.7).

### 6.6. Граница суток и месяца зависит от часового пояса окружения

**Суть.** LimitLedger определяет текущую дату через LocalDate.now(), а часовой пояс не задан ни в коде, ни в Dockerfile и docker-compose.yml.

**Влияние.** На новую проверку не влияет, но влияет на тесты дневного и месячного лимитов около полуночи. Дневной лимит станет виден и управляем через API, поэтому часовой пояс суток стоит зафиксировать при приёмке.

## 7. КРИТЕРИИ ПРИЁМКИ

Исходные условия, если не указано иное: через API выставлены `dailyMax` = 50000.00, `monthlyMax` = 200000.00, `singleTransferMax` = 10000.00; отправитель не заблокирован (не 5, 13, 21, 34, 42) и не имеет переводов за текущие сутки и месяц; валюта RUB.

**API управления лимитами**

- ТК-01. Сразу после выкатки `GET /limits` → 200; `dailyMax` = 50000.00, `monthlyMax` = 200000.00, `singleTransferMax` = согласованное начальное значение (вопрос 8.1), `updatedAt` заполнено.
- ТК-02. `PUT /limits` с `dailyMax` = 50000.00, `monthlyMax` = 200000.00, `singleTransferMax` = 10000.00 → 200, в ответе переданные значения и новое `updatedAt`; следующий `GET /limits` возвращает те же значения.
- ТК-03. `PUT /limits` без `singleTransferMax` или с `singleTransferMax` = null → 400, в `detail` названо поле; `GET /limits` возвращает прежние значения.
- ТК-04. `singleTransferMax` = 0 → 400; -1.00 → 400; 0.01 → 200.
- ТК-05. `singleTransferMax` = 100.001 → 400.
- ТК-06. Все три значения = 9999999999999.99 → 200; любое значение = 10000000000000.00 → 400.
- ТК-07. Нечисловое значение («abc») или некорректный JSON → 400, значения не изменились.
- ТК-08. `singleTransferMax` = 60000.00 при `dailyMax` = 50000.00 или `dailyMax` = 250000.00 при `monthlyMax` = 200000.00 → 400, если правило соотношения подтверждено (вопрос 8.3), иначе 200. Все три значения = 50000.00 → 200 в любом случае.
- ТК-09. Перезапуск limit-service → `GET /limits` возвращает значения последнего успешного `PUT /limits`.

**Максимальная сумма одного перевода**

- ТК-10. Перевод 9999.99 → в `limit-results` APPROVED; итоговый статус COMPLETED.
- ТК-11. Перевод 10000.00, равный порогу → APPROVED; итоговый статус COMPLETED.
- ТК-12. Перевод 10000 без дробной части → APPROVED: сравнение идёт по числовому значению, а не по записи числа.
- ТК-13. Перевод 10000.01 → в `limit-results` DECLINED, `decidedBy` = limit, `messageInfo` = SINGLE\_TRANSFER\_LIMIT\_EXCEEDED; итоговый статус CANCELLED с теми же `decidedBy` и `messageInfo`; в `reservations` — DECLINED, `reason` = SINGLE\_TRANSFER\_LIMIT\_EXCEEDED, `state` = NONE, `amount` = 10000.01; `daily_used` и `monthly_used` отправителя не изменились.
- ТК-14. `GET /transfers/{id}` для перевода из ТК-13 → история: NEW; LIMIT (DECLINED, limit, SINGLE\_TRANSFER\_LIMIT\_EXCEEDED); SCREENING (APPROVED); FINAL (CANCELLED, limit, SINGLE\_TRANSFER\_LIMIT\_EXCEEDED).
- ТК-15. Заблокированный отправитель (`senderId` = 5), перевод 10000.01 → итоговый статус DENIED, `decidedBy` = null, `messageInfo` = `SINGLE_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED`.
- ТК-16. Отправитель уже использовал за сутки 45000.00, перевод 10000.01 (нарушены разовый и дневной лимиты) → причина SINGLE\_TRANSFER\_LIMIT\_EXCEEDED.
- ТК-17. Событие NEW с `amount` = null, отправленное в топик `transfers` напрямую (REST такое не пропускает) → DECLINED с INVALID\_AMOUNT; сообщение не попадает в `transfers.DLT`.

**Регресс дневного и месячного лимитов**

- ТК-18. Использовано за сутки 45000.00: перевод 5000.00 → APPROVED; при тех же 45000.00 перевод 5000.01 → DAILY\_LIMIT\_EXCEEDED.
- ТК-19. Использовано за месяц 195000.00, за сутки 0: перевод 5000.00 → APPROVED; перевод 5000.01 → MONTHLY\_LIMIT\_EXCEEDED.
- ТК-20. Перевод в пределах лимитов от заблокированного отправителя → в `limit-results` APPROVED, итоговый статус CANCELLED с `decidedBy` = screening; резерв RELEASED, использование уменьшилось на сумму перевода.

**Изменение лимитов без перезапуска**

- ТК-21. Перевод 15000.00 → SINGLE\_TRANSFER\_LIMIT\_EXCEEDED. После `PUT /limits` с `singleTransferMax` = 20000.00 (остальные без изменений) новый перевод 15000.00 с новым id → APPROVED; limit-service не перезапускался.
- ТК-22. Повторный `POST /transfers` с id и параметрами первого перевода из ТК-21 после повышения лимита → 200, перевод остаётся CANCELLED, повторной проверки нет. Повторная доставка его события NEW в `transfers` → в `limit-results` то же решение: DECLINED, SINGLE\_TRANSFER\_LIMIT\_EXCEEDED.
- ТК-23. Использовано за сутки 30000.00; `PUT /limits` с `dailyMax` = 20000.00 → 200; `sender_usage` и существующие резервы не изменились; новый перевод 0.01 → DAILY\_LIMIT\_EXCEEDED.

**Выкатка**

- ТК-24. Конфигурация limit-service не содержит `limits.daily-max` и `limits.monthly-max` → сервис стартует, решения принимаются по значениям из `limit_settings`.
- ТК-25. После выкатки нет переводов в NEW, созданных в окно выкатки и оставшихся без итогового статуса; если они есть, по ним выполнен повторный `POST /transfers` (п. 6.1).

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ

Вопрос 8.1 блокирует подготовку миграции; по остальным в постановку заложено предлагаемое решение, которое нужно подтвердить или изменить до начала разработки.

- **8.1. Начальное значение максимальной суммы одного перевода.** В задаче оно не указано, а без него нельзя подготовить миграцию. Варианты: конкретная сумма или значение, равное дневному лимиту (50000.00), — тогда поведение не изменится, пока порог не выставят через API.
- **8.2. Общий порог или индивидуальные лимиты.** «Для всех отправителей» понято как одно значение на всех, как сейчас у дневного и месячного лимитов; нужны ли сейчас или в ближайших планах лимиты отдельных отправителей или групп? От ответа зависят модель данных и API (п. 4.3). Также подтвердите, что «просмотр всех лимитов» — это значения лимитов без текущего использования по отправителям.
- **8.3. Допустимые значения лимитов.** Предлагается: только > 0 (нулевой лимит как способ запретить переводы не допускается), технический максимум 9999999999999.99 и обязательное соотношение «на один перевод ≤ дневной ≤ месячный» с отказом в сохранении несогласованных значений. Нужен ли бизнес-максимум ниже технического?
- **8.4. Валюта лимитов.** Лимиты применяются к сумме без учёта валюты (п. 6.2). В какой валюте заданы лимиты и как поступать с переводами в других валютах: конвертировать, отклонять, ввести лимиты по валютам? Предлагается сохранить текущее поведение и зафиксировать его как известное ограничение.
- **8.5. Что считается «понятной причиной».** Предлагается код SINGLE\_TRANSFER\_LIMIT\_EXCEEDED в `messageInfo` по аналогии с DAILY\_LIMIT\_EXCEEDED; нужен ли клиенту текст, например с суммой порога (см. п. 6.4)? Устраивает ли, что итоговый статус такого перевода — CANCELLED, а у заблокированного отправителя — DENIED с составной причиной (п. 6.3)?
- **8.6. Приоритет причин.** Если перевод превышает и разовый, и дневной (месячный) лимит, какую причину показывать? Предлагается SINGLE\_TRANSFER\_LIMIT\_EXCEEDED: эта проверка не зависит от истории отправителя, поэтому одна и та же сумма всегда отклоняется с одной причиной.
- **8.7. Доступ и аудит.** В системе нет аутентификации (п. 6.5): кто вправе смотреть и менять лимиты, и достаточно ли закрыть API на уровне сети? Нужны ли журнал изменений (кто, когда, старое и новое значение) и согласование изменений? Без решения в доработку входит только запись изменений в лог.
- **8.8. Момент вступления в силу.** Предлагается: изменение действует сразу и только на новые решения, без пересмотра одобренных переводов и сброса накопленного использования (п. 5.1). Нужно ли планировать изменение на будущую дату?
