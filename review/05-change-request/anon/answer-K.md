# ПОСТАНОВКА НА ДОРАБОТКУ: максимальная сумма одного перевода + REST API управления лимитами

---

## 1. ЦЕЛЬ ДОРАБОТКИ

Ввести для всех отправителей третий лимит — «максимальная сумма одного перевода»: переводы, превышающие этот порог, отклоняются сервисом лимитов с понятной кодированной причиной, не расходуя дневной и месячный лимиты. Дать административный REST API для просмотра и изменения значений всех трёх лимитов без перезапуска сервисов.

## 2. ПРЕДПОСЫЛКИ

Сейчас лимиты (дневной и месячный) заданы как статические свойства `limits.daily-max` и `limits.monthly-max` в конфигурации limit-service (см. `limit-service/.../application.yml`), читаются в рантайме через `@Value` в `LimitLedger`. Ограничения текущей системы, которые устраняет доработка:

- проверяется только накопленный расход за день/месяц — один перевод может мгновенно израсходовать дневной лимит целиком;
- изменить лимит можно только редактированием конфигурации и перезапуском сервиса — программного управления лимитами нет;
- значения лимитов вообще не хранятся в БД (в limitdb нет таблицы настроек), поэтому REST API «на текущем фундаменте» невозможен.

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### 4.1. Где хранить значения лимитов

- **Вариант A (рекомендуемый): таблица настроек в limitdb.** Лимиты живут там же, где применяется логика; чтение в той же транзакции, что и решение по переводу — нет проблем консистентности. Минус: limit-service теряет конфигурацию «через файл» — дефолты переносятся в миграцию.
- **Вариант B: оставить в properties + REST, переписывающий файл/перезагружающий контекст.** Не годится: не переживёт рестарт контейнера и не масштабируется на несколько инстансов сервиса.
- **Вариант C: хранить настройки в БД transfer-service.** Нарушает границу сервиса: ограничение применяется limit-service, а данные лежали бы в чужой схеме. Отклонить.

### 4.2. Где разместить REST API

- **Вариант A (рекомендуемый): REST в limit-service** (добавить web-стартер). Плюсы: API находится у владельца данных, нет дополнительных контрактов и задержек синхронизации; изменение лимита видно следующему же обрабатываемому переводу. Минусы: у limit-service появится HTTP-поверхность, нужно пробросить порт в compose.
- **Вариант B: REST в transfer-service + команда в limit-service через Kafka-топик.** Плюсы: transfer-service уже является HTTP-фасадом с OpenAPI-документацией. Минусы: новый контракт, eventual consistency, обработка дубликатов команд и DLT ради тривиальной задачи.
- **Вариант C: transfer-service пишет прямо в limitdb.** Нарушение границ сервиса. Отклонить.

### 4.3. Момент чтения лимитов

Рекомендуется читать настройки при каждом решении по переводу (в транзакции `decide`), без кэширования — нагрузка на чтение ничтожна, а изменения применяются мгновенно. Кэш с инвалидацией — избыточен на текущем масштабе.

### 4.4. Порядок проверок лимитов

Рекомендуемый порядок в `decide`: **сумма одного перевода → дневной → месячный**. Обоснование: проверка суммы — самая специфичная и не зависит от накопленного расхода, её причина должна выигрывать, когда превышено и то и другое. Финальный порядок подтверждает бизнес (см. раздел 8).

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. limit-service

#### Изменения в БД

Новый миграционный скрипт (предложение: `db/changelog/002-limit-settings.sql`) в `limitdb`:

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | BIGINT | PK, `CHECK (id = 1)` — синглтон | Единая строка настроек для всех отправителей |
| `daily_max` | DECIMAL(15,2) | NOT NULL, CHECK > 0 | Дневной лимит |
| `monthly_max` | DECIMAL(15,2) | NOT NULL, CHECK > 0 | Месячный лимит |
| `max_single_transfer` | DECIMAL(15,2) | NOT NULL, CHECK > 0 | Максимальная сумма одного перевода |
| `updated_at` | TIMESTAMP | NOT NULL | Момент последнего изменения |

Ограничения и допущения:
- Точность и масштаб (`DECIMAL(15,2)`) соответствуют существующим колонкам `sender_usage` и `reservations`.
- Название и структура таблицы — предложение контракта.
- Миграция тестовых данных: вставить синглтон-строку со значениями из текущей конфигурации — `daily_max = 50000.00`, `monthly_max = 200000.00` (сейчас это `limits.daily-max` / `limits.monthly-max`); `max_single_transfer` — значение по умолчанию требует решения бизнеса (раздел 8), техническая заглушка — равный `daily_max`.
- Свойства `limits.*` в `application.yml` перестают быть источником значений при решении; вопрос их сохранения как seed-источника миграции — деталь реализации.

#### Изменения в API

Новые эндпоинты (base path — по соглашению проекта, например `/limits`):

**Эндпоинт:** `GET /limits`
**Описание:** возвращает текущие значения всех трёх лимитов.

Параметры запроса: нет.

Параметры ответа:

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | decimal(15,2) | нет | Дневной лимит |
| `monthlyMax` | decimal(15,2) | нет | Месячный лимит |
| `maxSingleTransfer` | decimal(15,2) | нет | Максимальная сумма одного перевода |
| `updatedAt` | timestamp | нет | Момент последнего изменения |

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Настройка получена |
| 500 | Внутренняя ошибка |

**Эндпоинт:** `PUT /limits`
**Описание:** обновляет одно, несколько или все значения лимитов; неуказанные поля не меняются.

Параметры запроса (body, JSON):

| Параметр | Источник | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `dailyMax` | body | decimal(15,2) | нет | Новый дневной лимит; если задан — положительный, ≤ 15 знаков до запятой и 2 после (как у `amount` в `TransferRequest`) |
| `monthlyMax` | body | decimal(15,2) | нет | Новый месячный лимит; аналогичные ограничения |
| `maxSingleTransfer` | body | decimal(15,2) | нет | Новый макс. сумма одного перевода; аналогичные ограничения |

Ответ: те же поля, что в `GET /limits`, с актуальными после изменения значениями.

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Лимиты обновлены |
| 400 | Ни одно поле не передано; значение ≤ 0; не проходит точность (scale > 2) |
| 500 | Внутренняя ошибка |

Примечание: эндпоинт идемпотентен (полная замена переданных значений), история изменений лимитов в первой итерации не ведётся — см. открытые вопросы.

#### Изменения в бизнес-логике

- При `amount > max_single_transfer` система должна отклонить перевод с причиной (предложение кода) `SINGLE_TRANSFER_LIMIT_EXCEEDED` и **не** резервировать сумму в `sender_usage` — так же, как ведёт себя существующая ветка отклонения по дневному/месячному лимиту (`LimitLedger.decide`).
- Существующие правила сохраняются: проверка дневного лимита (`daily_used + amount > daily_max` → `DAILY_LIMIT_EXCEEDED`), месячного (`MONTHLY_LIMIT_EXCEEDED`), обработка `amount == null || signum() <= 0` → `INVALID_AMOUNT`, механизм ленивого сброса `lazyReset`, идемпотентность по `transferId`.
- Порядок проверок: сначала максимальная сумма одного перевода, затем дневной, затем месячный (см. 4.4).
- Чтение лимитов при каждом решении из таблицы настроек в той же транзакции, что и решение по переводу (см. 4.3).
- В `settle` изменения не нужны: перевод, отклонённый по новому лимиту, имеет `state = NONE` и пропускается существующей проверкой `isReserved`; дебетовка `sender_usage` при финальных статусах не меняется.

#### Изменения в контрактах сообщений

- Запись `Transfer` (transfer-common) не меняется: новая причина отклонения передаётся существующим полем `messageInfo` через топик `limit-results`.
- Новый код причины `SINGLE_TRANSFER_LIMIT_EXCEEDED` (предложение) появится в: `reservations.reason`, `messageInfo` сообщений в `limit-results`, далее — `transfer_history.message_info` и `transfers.message_info` в transferdb. Длина кода (31 символ) укладывается в `VARCHAR(50)` колонки `reason`.

### 5.2. transfer-service

Изменений нет. Новая причина отклонения проходит по существующему конвейеру: `limit-results` → join в `DecisionTopologyConfig` → итоговый статус `CANCELLED` с `decidedBy = limit` и `messageInfo = SINGLE_TRANSFER_LIMIT_EXCEEDED` → история в `transfer_history` (stage `LIMIT`, status `DECLINED` уже входит в enum `HistoryEntry.status` в спецификации `transfer-api.yaml`). Существующие OpenAPI-контракты и REST `/transfers` не меняются.

### 5.3. screening-service

Изменений нет. Сервис не участвует в проверке лимитов; контракт `Transfer` не меняется, новые причины отклонения в его топик не попадают.

### 5.4. transfer-common

Изменений нет. Новая причина — данные, а не схема; состав полей `Transfer` достаточен.

### 5.5. Инфраструктура (docker-compose.yml)

Модифицируемая: опубликовать HTTP-порт limit-service (сейчас у сервиса нет секции `ports`); выбрать порт без конфликтов с уже занятыми 8080/5432–5434/9092.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

1. **Лимиты в свойствах, не в БД** (`LimitLedger`, `@Value limits.daily-max/monthly-max`). Это корневая причина доработки: REST API в текущем виде невозможен, поэтому значения переносятся в таблицу настроек. Не забыть, что после переноса изменение лимитов вступает в силу мгновенно, а до сих пор требовался рестарт — это изменение поведения, его нужно проговорить на приёмке.
2. **Порядок причин при множественном превышении.** В `decide` дневной лимит проверяется раньше месячного; при переводе, превышающем сразу и порог одного перевода, и дневной лимит, код причины зависит от выбранного порядка проверок (4.4). Это не баг, но контракт поведения, который нужно зафиксировать.
3. **Граничная семантика «строго больше».** Существующие проверки отклоняют только при `compareTo(...) > 0`, то есть сумма, равная лимиту, проходит. Для нового лимита логично сохранить ту же семантику («превышает порог» = строго больше), но это стоит подтвердить у бизнеса (раздел 8).
4. **Дубликаты NEW возвращают сохранённое решение** (`LimitLedger.decide`, проверка по `transferId`). Повторная обработка одного и того же перевода не пересчитывает решение даже при изменившихся лимитах. Для доработки это означает: тесты на применение нового лимита должны использовать новые `transferId`, а не повторные события.
5. **Окно join 10 секунд без grace** (`DecisionTopologyConfig`, `JoinWindows.ofTimeDifferenceWithNoGrace`). Если результат скрининга задержится больше окна, итоговое решение не будет сформировано и перевод зависнет в NEW. На приёмку новой причины это влияет только косвенно — тестовые сценарии должны гарантировать, что оба результата укладываются в окно.
6. **Топик `transfers` создан с `compact()`** (`TopicsConfig` во всех сервисах). Компакция может скрыть промежуточные записи NEW от свежесозданных consumer-групп — важно при воссоздании стенда/групп при приёмочных прогонах: часть событий может «не дойти» до limit-service как NEW.

Аномалии, не влияющие на доработку, здесь не перечислены.

## 7. КРИТЕРИИ ПРИЁМКИ

Базовая конфигурация (из миграции): `dailyMax = 50000.00`, `monthlyMax = 200000.00`, `maxSingleTransfer` — по решению бизнеса; в примерах ниже — `50000.00`.

| Условие | Ожидаемый результат |
|---|---|
| Перевод 1000.00 от нового отправителя (нет превышений) | `APPROVED` от limit, `daily_used = 1000.00`, `monthly_used = 1000.00` |
| Перевод ровно на `maxSingleTransfer` (50000.00) при нулевом расходе | `APPROVED` — порог не превышен (граничное значение) |
| Перевод 50000.01 при `maxSingleTransfer = 50000.00` | `DECLINED`, причина `SINGLE_TRANSFER_LIMIT_EXCEEDED`, `daily_used` и `monthly_used` не изменились |
| Перевод 50000.00 при уже израсходованном дневном остатке 10000.00 (`dailyMax = 50000.00`) | `DECLINED`, `DAILY_LIMIT_EXCEEDED` (проверка суммы перевода пройдена) |
| Перевод 60000.00 при `maxSingleTransfer = 50000.00`, `dailyMax = 50000.00` (превышены оба) | Причина `SINGLE_TRANSFER_LIMIT_EXCEEDED` — приоритет проверки суммы одного перевода (согласно 4.4) |
| Перевод 60000.00 при `maxSingleTransfer = 70000.00`, `dailyMax = 50000.00` | `DAILY_LIMIT_EXCEEDED` (сумма одного перевода в норме) |
| `PUT /limits {maxSingleTransfer: 1000.00}`, затем перевод 1000.01 без перезапуска сервисов | `DECLINED`, `SINGLE_TRANSFER_LIMIT_EXCEEDED` — новое значение применено немедленно |
| `GET /limits` | 200, все три значения соответствуют актуальным |
| `PUT /limits` без полей / с отрицательным значением / с 3 знаками после запятой | 400, валидационная ошибка, значения не изменены |
| `PUT /limits {dailyMax: 40000.00}`, затем перевод 45000.00 | `DECLINED`, `DAILY_LIMIT_EXCEEDED` по новому дневному лимиту |
| Перевод, отклонённый по сумме одного перевода, получает финальный статус | Итоговый статус `CANCELLED` с `decidedBy = limit`, в `transfer_history` stage `LIMIT` со статусом `DECLINED` и причиной в `message_info` |
| Регрессия: перевод в рамках всех лимитов после финальных статусов `CANCELLED` | Резерв дневного/месячного расхода освобождается, как сейчас (`settle`) |
| Повторная доставка NEW того же `transferId` при изменившихся лимитах | Возвращается сохранённое решение, пересчёта нет (существующая идемпотентность) |
| Перевод 0.00 или отрицательный | `INVALID_AMOUNT` (существующее поведение) |

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ

1. **Значение по умолчанию** для «максимальной суммы одного перевода» при первом запуске и в тестовых данных. Нужно ли оно вообще (0 = «без ограничения»), или должно быть задано явно?
2. **Граничная семантика:** подтвердить, что «превышает порог» означает строго больше — сумма, равная порогу, проходит (как для дневного/месячного лимитов в текущем коде). И нужно ли это правило отдельно оговорить для дневного/месячного.
3. **Действующие лимиты и в-flight переводы:** при снижении лимитов переводы, уже зарезервированные по старым значениям, не пересчитываются (резерв остаётся). Подтвердить, что это приемлемо.
4. **Приоритет причин отклонения** при одновременном превышении нескольких лимитов (порядок проверок из п. 4.4 — предложение, требуется подтверждение).
5. **Кросс-валидация значений:** должно ли `maxSingleTransfer` быть ≤ `dailyMax` (иначе новое ограничение недостижимо), и допустимо ли `dailyMax` > `monthlyMax`?
6. **Нулевые значения:** может ли дневной/месячный лимит быть 0 как способ полного запрета переводов, или нулевые/отрицательные значения запрещены (в предложенном контракте — запрещены)?
7. **Пер-отправительские лимиты в будущем:** бизнес формулирует настройку «для всех отправителей» — нужен ли запас на индивидуальные лимиты (сейчас синглтон-строка; переход на пер-отправительскую модель — отдельная доработка)?
8. **Разграничение доступа к limits API:** кто имеет право менять лимиты; в коде механизмы аутентификации/авторизации не найдены — требуется решение.
9. **Аудит изменений лимитов:** требуется ли хранение истории изменений значений (кто, когда, с какого на какое) или достаточно колонки `updated_at`?
