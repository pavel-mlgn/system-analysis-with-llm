## 1. ЦЕЛЬ ДОРАБОТКИ

Добавить для всех отправителей ограничение на максимальную сумму одного перевода. Предоставить REST API для просмотра и изменения дневного, месячного и нового лимита без перезапуска сервиса. Изменения должны сохраняться и применяться к последующим решениям по переводам.

## 2. ПРЕДПОСЫЛКИ

Сейчас перевод проверяется только против дневного и месячного использования отправителя. Если сумма не превышает доступный остаток по обоим периодам, перевод одобряется независимо от его размера, поэтому один перевод может израсходовать весь дневной лимит (`limit-service`, `LimitLedger.decide`).

Дневной и месячный лимиты заданы в `limit-service/src/main/resources/application.yml` и считываются как конфигурация при запуске. В коде не найдено ни постоянного хранилища настроек лимитов, ни REST API для их изменения. Следовательно, добавление только третьего конфигурационного параметра не обеспечит выполнение бизнес-задачи.

## 3. SCOPE ИЗМЕНЕНИЙ

| Компонент | Тип изменения | Характер изменения |
|---|---|---|
| `limit-service` | Модифицируемый | Добавить проверку максимальной суммы одного перевода и использовать изменяемые настройки для всех трёх проверок. |
| БД `limitdb` | Модифицируемая | Добавить постоянное хранилище глобальных настроек лимитов и начальную миграцию значений. |
| REST API `limit-service` | Новый | Добавить просмотр и атомарное изменение всех лимитов. |
| OpenAPI-документация `limit-service` | Новая | Описать новые эндпоинты, модели и ошибки. |
| Контракт сообщений `limit-results` | Модифицируемый семантически | Добавить новое значение причины отклонения в `messageInfo`; структура сообщения не меняется. |
| Финальные сообщения в `transfers` | Модифицируемый семантически | Новая причина должна проходить через существующую агрегацию решений; новые поля и статусы не требуются. |
| `docker-compose.yml` | Модифицируемый | Обеспечить внешний доступ к REST API `limit-service`; предлагаемый локальный порт — `8081`. |
| `transfer-service` | Без изменений | Существующие поля и правила агрегации уже поддерживают новую причину отклонения. |
| `screening-service` | Без изменений | Правила скрининга не зависят от лимитов. |

**Принятое допущение:** все три лимита являются общими для всех отправителей, как текущие `limits.daily-max` и `limits.monthly-max`. Если требуются индивидуальные значения по отправителям, модель БД и API необходимо пересмотреть — см. раздел 8.

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### Вариант 1. Хранение и REST API в `limit-service` — рекомендуемый

`limit-service` становится единственным владельцем настроек и предоставляет публичный REST API.

**Плюсы:**
- проверка переводов и управление лимитами используют один источник данных;
- не требуется синхронизация настроек между сервисами;
- изменения применяются без рестарта и сохраняются после него;
- отсутствует расхождение между значениями, возвращаемыми API, и значениями, используемыми при проверке.

**Минусы:**
- в `limit-service` необходимо добавить HTTP-функциональность: сейчас в нём не найдено REST API и соответствующей web-зависимости;
- требуется открыть отдельный порт и определить требования к защите управляющего API.

### Вариант 2. Внешний API в `transfer-service`, владение настройками в `limit-service`

`transfer-service` принимает внешние запросы и обращается к внутреннему API `limit-service`.

**Плюсы:**
- для потребителей сохраняется единая точка входа на уже опубликованном порту `8080`;
- `limit-service` остаётся владельцем настроек и бизнес-правил.

**Минусы:**
- появляются два API и дополнительный сетевой вызов;
- доступность управления лимитами начинает зависеть от двух сервисов;
- необходимо согласовать обработку ошибок, тайм-аутов и авторизацию между сервисами.

Вариант целесообразен, только если подтверждено требование предоставлять все внешние API исключительно через `transfer-service`.

### Вариант 3. Хранение настроек в `transfer-service` с передачей в `limit-service`

Настройки изменяются в БД `transferdb`, а затем передаются в `limit-service` через новый интерфейс или поток сообщений.

**Плюсы:**
- управляющий API размещается рядом с существующим REST API.

**Минусы:**
- возникает второй владелец данных и проблема согласованности копий;
- требуются новые контракты и обработка недоставленных или повторных обновлений;
- при временной рассинхронизации API и проверки переводов могут использовать разные значения.

**Не рекомендуется** из-за дополнительной распределённой согласованности без видимой бизнес-необходимости.

Хранение рабочих настроек только в `application.yml` также не рекомендуется: текущие значения считываются при запуске, а обновление файла через REST не обеспечивает надёжной эксплуатации, атомарности и единого поведения нескольких экземпляров сервиса.

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. `limit-service`

#### Изменения в БД

Добавить новую таблицу `limit_settings` для одной глобальной записи настроек.

| Колонка | Тип и ограничения | Назначение |
|---|---|---|
| `id` | `SMALLINT PRIMARY KEY`, `CHECK (id = 1)` | Фиксированный идентификатор единственной записи; рабочая запись имеет `id = 1`. |
| `daily_max` | `DECIMAL(15,2) NOT NULL`, `CHECK (daily_max > 0)` | Максимальная сумма переводов отправителя в сутки. |
| `monthly_max` | `DECIMAL(15,2) NOT NULL`, `CHECK (monthly_max > 0)` | Максимальная сумма переводов отправителя в месяц. |
| `max_single_transfer` | `DECIMAL(15,2) NOT NULL`, `CHECK (max_single_transfer > 0)` | Максимальная сумма одного перевода. |

Требования к миграции:

- миграция должна создавать единственную запись настроек;
- `daily_max` инициализировать значением `50000.00`, `monthly_max` — `200000.00`, перенеся текущие значения из `application.yml`;
- начальное значение `max_single_transfer` требует согласования; предлагается `50000.00`, чтобы первоначально не вводить более строгое ограничение, чем текущий дневной лимит;
- существующие записи `sender_usage` и `reservations` не пересчитывать и не изменять;
- структура `sender_usage` и `reservations` не меняется;
- после введения таблицы параметры `limits.daily-max` и `limits.monthly-max` из `application.yml` не должны оставаться независимым источником рабочих значений.

#### Изменения в API

Все URL указаны относительно `limit-service`. Для локального запуска предлагается опубликовать порт `8081`, например `http://localhost:8081/limits`.

**Эндпоинт:** `GET /limits`  
**Описание:** Возвращает текущие значения всех глобальных лимитов.

**Параметры запроса:** отсутствуют.

**Параметры ответа:**

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | `number`, до 15 цифр, из них 2 дробные | Нет | Текущий дневной лимит. |
| `monthlyMax` | `number`, до 15 цифр, из них 2 дробные | Нет | Текущий месячный лимит. |
| `maxSingleTransfer` | `number`, до 15 цифр, из них 2 дробные | Нет | Текущий максимум суммы одного перевода. |

**Коды ответа:**

| Код | Условие |
|---|---|
| `200` | Настройки успешно получены. |
| `500` | Не удалось получить настройки из постоянного хранилища или произошла внутренняя ошибка. |

**Эндпоинт:** `PUT /limits`  
**Описание:** Атомарно заменяет полный набор глобальных лимитов; для изменения одного значения клиент передаёт также актуальные значения остальных.

**Параметры запроса:**

| Параметр | Источник | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `dailyMax` | body | `number`, `DECIMAL(15,2)` | Да | Новый дневной лимит; строго больше `0`. |
| `monthlyMax` | body | `number`, `DECIMAL(15,2)` | Да | Новый месячный лимит; строго больше `0`. |
| `maxSingleTransfer` | body | `number`, `DECIMAL(15,2)` | Да | Новый максимум одного перевода; строго больше `0`. |

Дополнительные ограничения для всех полей:

- не более двух дробных цифр, без неявного округления;
- максимальное значение — `9999999999999.99`;
- неизвестные поля, `null`, отсутствующие значения и некорректный JSON считаются ошибкой запроса;
- дополнительные ограничения между значениями лимитов зависят от ответа на раздел 8.

**Параметры ответа:**

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | `number` | Нет | Сохранённый дневной лимит. |
| `monthlyMax` | `number` | Нет | Сохранённый месячный лимит. |
| `maxSingleTransfer` | `number` | Нет | Сохранённый максимум одного перевода. |

**Коды ответа:**

| Код | Условие |
|---|---|
| `200` | Все настройки успешно сохранены; ответ содержит фактически сохранённые значения. |
| `400` | Некорректный JSON, отсутствует обязательное поле или нарушено ограничение значения; прежние настройки не изменены. |
| `500` | Не удалось сохранить полный набор настроек или произошла внутренняя ошибка; частичное обновление недопустимо. |

Для ошибок предлагается формат `application/problem+json`, уже используемый в существующем API. В ответе `400` текст `detail` должен однозначно указывать некорректное поле и причину отказа.

Фактические значения `dailyUsed` и `monthlyUsed` в эти API не входят: они относятся к использованию лимитов отправителем, а не к настройкам.

#### Изменения в бизнес-логике

- При обработке любого нового перевода система должна использовать единый актуальный набор `dailyMax`, `monthlyMax` и `maxSingleTransfer` из постоянного хранилища.
- При `amount > maxSingleTransfer` система должна отклонить перевод с причиной `SINGLE_TRANSFER_LIMIT_EXCEEDED` и не увеличивать дневное или месячное использование отправителя.
- При `amount = maxSingleTransfer` система должна считать проверку одиночного перевода пройденной; окончательное решение лимитного сервиса зависит от дневного и месячного лимитов.
- При нарушении нескольких условий одновременно система должна возвращать одну причину по предлагаемому приоритету: `INVALID_AMOUNT` → `SINGLE_TRANSFER_LIMIT_EXCEEDED` → `DAILY_LIMIT_EXCEEDED` → `MONTHLY_LIMIT_EXCEEDED`.
- При сумме, не превышающей максимум одиночного перевода, система должна сохранить существующие правила проверки дневного и месячного использования, включая допустимость равенства лимиту.
- При успешном `PUT /limits` система должна применять сохранённые значения к последующим решениям без перезапуска сервиса.
- При параллельном изменении настроек и проверке перевода система должна использовать либо полный прежний, либо полный новый набор значений; сочетание части старых и части новых значений недопустимо.
- При изменении настроек система не должна пересматривать уже сохранённые решения, отменять существующие резервирования или пересчитывать `sender_usage`.
- При уменьшении дневного или месячного лимита ниже уже использованной суммы система должна отклонять последующие переводы, пока существующие правила использования и сброса не позволят их выполнить; отрицательное использование или автоматический сброс недопустимы.
- При повторном получении `NEW` для перевода, решение по которому уже сохранено, система должна вернуть прежнее решение и не пересчитывать его по новым лимитам.
- При получении финального статуса после изменения лимитов система должна завершать или освобождать прежнее резервирование по существующим правилам, независимо от нового `maxSingleTransfer`.

#### Изменения в контрактах сообщений

Для нового отклонения в `limit-results`:

| Поле | Значение |
|---|---|
| `status` | `DECLINED` |
| `decidedBy` | `limit` |
| `messageInfo` | `SINGLE_TRANSFER_LIMIT_EXCEEDED` |

Новые топики, поля и статусы не добавляются. Существующие значения `INVALID_AMOUNT`, `DAILY_LIMIT_EXCEEDED` и `MONTHLY_LIMIT_EXCEEDED` сохраняются.

При одобрении скрининга и отклонении только по новому лимиту финальное сообщение должно по-прежнему формироваться как `CANCELLED`, `decidedBy = "limit"`, с новой причиной в `messageInfo`. При одновременном отклонении лимитами и скринингом сохраняется существующий финальный статус `DENIED` и объединение причин.

#### Изменения в конфигурации и документации

- Обеспечить приём HTTP-запросов `limit-service` и доступность `/limits` извне.
- Добавить OpenAPI-описание новых эндпоинтов и схем.
- Обновить `docker-compose.yml`; предлагаемое локальное сопоставление — `8081:8080`.
- Исключить эксплуатационную возможность изменять лимиты одновременно через БД/API и через старые параметры `application.yml` с непредсказуемым приоритетом.

### 5.2. `transfer-service`

Изменений нет: существующая агрегация уже переносит `DECLINED` и произвольную причину `messageInfo` из `limit-results` в историю и финальное решение; структура REST API переводов не меняется (`TransferDecisionService.decide`, `TransferTrackingService`).

### 5.3. `screening-service`

Изменений нет: скрининг не использует суммы и настройки лимитов, а его решения продолжают независимо участвовать в агрегации.

### 5.4. `transfer-common`

Изменений нет: полей `Transfer.status`, `Transfer.decidedBy` и `Transfer.messageInfo` достаточно для нового результата.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

1. **Статический источник текущих лимитов.**  
   Значения внедряются через `@Value`, поэтому сохранение новых настроек в БД само по себе не изменит текущие проверки (`LimitLedger`, `application.yml`). Если оставить два независимых источника, API сможет возвращать одни значения, а решения приниматься по другим. В рамках доработки требуется единый источник рабочих настроек.

2. **Валюта не участвует в расчёте лимитов.**  
   Перевод допускает произвольный трёхбуквенный код валюты и по умолчанию использует `RUB`, но `LimitLedger.decide` складывает и сравнивает только `amount`, без проверки или конвертации валюты (`TransferRequest`, `Transfer`). Новый лимит унаследует ту же неоднозначность. До уточнения требований нельзя считать поведение корректным для нескольких валют.

3. **Не найдена защита управляющих API.**  
   В приложенном коде не найдено аутентификации или авторизации. Публикация API изменения лимитов без отдельного решения по доступу создаёт возможность неограниченного управления бизнес-ограничениями. Это не меняет выбранную модель данных, но может повлиять на способ публикации API.

4. **Сохранение решения и публикация результата не атомарны.**  
   Решение и резервирование сохраняются до синхронной публикации в `limit-results` (`LimitLedger.decide`, `LimitService.onNewTransfer`). При окончательной невозможности публикации перевод может остаться без финального решения, а одобренное использование — зарезервированным. Доработка не устраняет эту аномалию; при приёмке нельзя списывать её последствия на изменение настроек.

5. **Финальное решение зависит от окна объединения результатов.**  
   Результаты лимитов и скрининга объединяются только в пределах 10-секундного окна (`DecisionTopologyConfig.decisionStream`). При нарушении этого условия новая причина может присутствовать в `limit-results`, но финальный статус перевода не будет сформирован. Это существующее ограничение всего контура решений, а не только новой проверки.

## 7. КРИТЕРИИ ПРИЁМКИ

| Условие | Ожидаемый результат |
|---|---|
| Выполнена начальная миграция и вызван `GET /limits`. | Возвращаются `200` и все три ненулевых значения; дневной и месячный лимиты соответствуют перенесённым `50000.00` и `200000.00`. |
| В `PUT /limits` переданы три корректных значения. | Возвращается `200`; последующий `GET` возвращает те же значения; новые решения используют их без рестарта. |
| После успешного обновления сервис перезапущен. | `GET /limits` и проверки переводов используют сохранённые значения, а не прежние значения из `application.yml`. |
| Любое поле запроса равно `0`, отрицательно, равно `null`, отсутствует или имеет более двух дробных цифр. | Возвращается `400`; ни одно из трёх сохранённых значений не меняется. |
| Значение любого поля равно `9999999999999.99`. | Значение проходит базовую проверку диапазона; при остальных корректных полях набор сохраняется. |
| Значение любого поля превышает `9999999999999.99`. | Возвращается `400`; прежний набор сохраняется полностью. |
| `amount < maxSingleTransfer`, дневной и месячный остатки достаточны. | Лимитная проверка возвращает `APPROVED`; использование увеличивается на сумму перевода один раз. |
| `amount = maxSingleTransfer`, дневной и месячный остатки достаточны. | Перевод не отклоняется по одиночному лимиту; при прочих успешных проверках возвращается `APPROVED`. |
| `amount = maxSingleTransfer + 0.01`, периодические лимиты не нарушены. | Возвращается `DECLINED` с `SINGLE_TRANSFER_LIMIT_EXCEEDED`; `dailyUsed` и `monthlyUsed` не изменяются. |
| Перевод одновременно превышает одиночный и дневной лимиты. | Возвращается одна причина `SINGLE_TRANSFER_LIMIT_EXCEEDED` согласно принятому приоритету; повторного резервирования нет. |
| Одиночный лимит соблюдён, но дневной лимит будет превышен на `0.01`. | Сохраняется отказ `DAILY_LIMIT_EXCEEDED`; использование не увеличивается. |
| Одиночный и дневной лимиты соблюдены, но месячный лимит будет превышен на `0.01`. | Сохраняется отказ `MONTHLY_LIMIT_EXCEEDED`; использование не увеличивается. |
| После увеличения `maxSingleTransfer` повторно обрабатывается новый перевод на сумму между старым и новым порогами. | Перевод проходит одиночную проверку и принимается по остальным правилам. |
| После уменьшения `maxSingleTransfer` обрабатывается новый перевод выше нового порога. | Перевод отклоняется с новой причиной независимо от прежнего порога. |
| Дневной или месячный лимит уменьшен ниже уже использованной суммы. | Использование не обнуляется и не становится отрицательным; последующие переводы отклоняются по соответствующему периодическому лимиту. |
| Решение по переводу сохранено, затем лимиты изменены и повторно получен `NEW` с тем же `id`. | Возвращается исходное сохранённое решение; новые лимиты не применяются повторно; использование не увеличивается второй раз. |
| После изменения лимитов приходит финальный статус ранее одобренного перевода. | Прежнее резервирование корректно фиксируется или освобождается по существующим правилам; новый одиночный лимит на расчёт не влияет. |
| Новый одиночный лимит отклонил перевод, скрининг вернул `APPROVED`. | Финальный перевод имеет `CANCELLED`, `decidedBy = "limit"`, `messageInfo = "SINGLE_TRANSFER_LIMIT_EXCEEDED"`. |
| Перевод отправителя из `blocked_senders` также превышает одиночный лимит. | Финальный перевод имеет `DENIED`; `messageInfo` содержит `SINGLE_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED`. |
| Обновление настроек выполняется параллельно с проверкой перевода. | Решение использует полный прежний или полный новый набор; смешанные значения и частично сохранённое обновление отсутствуют. |
| В Kafka поступил `NEW` с `amount = null` или неположительной суммой. | Сохраняется существующий результат `INVALID_AMOUNT`; новая проверка не заменяет эту причину. |

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ

1. **Область настроек.** Подтвердить, что все три лимита едины для всех отправителей. Если нужны персональные значения, требуется другой API и модель хранения с привязкой к `senderId`.
2. **Начальный одиночный лимит.** Какое значение `maxSingleTransfer` должно быть установлено при миграции? Предлагается `50000.00`, но в исходной задаче и коде значение не определено.
3. **Связи между лимитами.** Обязательны ли условия `maxSingleTransfer ≤ dailyMax` и `dailyMax ≤ monthlyMax`, либо лимиты можно задавать независимо? Допускаются ли специальные значения `0` или «без ограничения»? В базовой постановке приняты только положительные конечные значения.
4. **Валюта.** Лимиты выражены только в RUB или должны применяться ко всем разрешённым валютам? Если валюты несколько, требуется определить валюту настроек и правило конвертации; в текущем коде такого правила не найдено.
5. **Приоритет причин.** Подтвердить предложенный порядок, при котором нарушение одиночного лимита имеет приоритет над дневным и месячным. Это влияет на видимую пользователю причину при одновременном нарушении нескольких ограничений.
6. **Обрабатываемые переводы.** Подтвердить, что изменения применяются только к решениям, которые ещё не были сохранены, и не требуют пересмотра уже принятых решений или резервирований.
7. **Уменьшение периодических лимитов.** Подтвердить предложенное поведение при `dailyUsed > dailyMax` или `monthlyUsed > monthlyMax`: существующее использование сохраняется, а новые переводы временно отклоняются.
8. **Доступ и аудит.** Кто имеет право просматривать и изменять лимиты, нужны ли аутентификация, разграничение прав и история изменений? Должен ли внешний API публиковаться отдельно на `limit-service` или обязательно проходить через существующую точку входа `transfer-service`?
