## 1. ЦЕЛЬ ДОРАБОТКИ

Добавить в систему третий глобальный лимит для отправителей — максимальную сумму одного перевода — и отклонять перевод, если его сумма превышает установленное значение. Добавить REST API для просмотра и изменения всех трёх лимитов: дневного, месячного и максимальной суммы одного перевода.

Текущая модель лимитов является глобальной: дневной и месячный пороги задаются на уровне `limit-service`, а фактическое использование учитывается отдельно по `senderId` (`limit-service/.../LimitLedger.java`, `LimitLedger.decide`).

## 2. ПРЕДПОСЫЛКИ

Сейчас `limit-service` проверяет только накопленную дневную и месячную сумму. Поэтому отправитель может выполнить один перевод размером вплоть до доступного дневного лимита, если месячный лимит также не превышен (`limit-service/.../LimitLedger.java`, `LimitLedger.decide`).

Кроме того, значения лимитов заданы статически в `application.yml` (`daily-max = 50000.00`, `monthly-max = 200000.00`) и не могут изменяться через прикладной API без изменения конфигурации/перезапуска сервиса.

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### 4.1. Где размещать REST API управления лимитами

**Вариант 1 — REST API непосредственно в `limit-service` — рекомендуется.**

Плюсы:
- настройки находятся в том же сервисе, который применяет их при проверке;
- один владелец данных и бизнес-правил;
- не требуется новый межсервисный вызов для чтения/изменения лимитов;
- исключается дублирование логики лимитов в `transfer-service`.

Минусы:
- `limit-service`, который сейчас работает через Kafka и БД, дополнительно становится HTTP-сервисом;
- требуется изменить его runtime/deployment-конфигурацию и предоставить HTTP-доступ.

**Вариант 2 — REST API в `transfer-service` с передачей управления в `limit-service`.**

Плюс: `transfer-service` уже предоставляет REST API.

Минусы:
- потребуется новый синхронный межсервисный контракт, которого в коде сейчас нет;
- `transfer-service` начнёт отвечать за операции над данными другого bounded context;
- прямой доступ `transfer-service` к `limitdb` нарушит существующее владение БД сервисами.

**Рекомендация:** размещать `/limits` непосредственно в `limit-service`.

### 4.2. Где хранить изменяемые значения лимитов

**Вариант 1 — оставить значения в `application.yml`.**

Не подходит для заявленного REST-управления: текущие значения инжектируются из конфигурации приложения и не являются изменяемым прикладным состоянием (`limit-service/.../LimitLedger.java`, `LimitLedger.decide`).

**Вариант 2 — хранить глобальные лимиты в БД `limitdb` — рекомендуется.**

Плюсы:
- изменения сохраняются после перезапуска;
- REST API и обработка переводов используют один источник значений;
- не требуется дополнительная инфраструктура, которой в проекте сейчас нет.

Минус:
- необходима миграция существующих конфигурационных значений.

**Рекомендуемая модель:** одна запись глобальных настроек в новой таблице `limit_settings`.

Динамический configuration service / external config storage в приложенном коде не найден.

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. `limit-service`

### Изменения в БД

Добавить таблицу:

`limit_settings`

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | SMALLINT | PK, NOT NULL, единственная глобальная запись | Идентификатор набора настроек |
| `daily_limit` | DECIMAL(15,2) | NOT NULL, `> 0` | Максимальная совокупная сумма переводов отправителя за день |
| `monthly_limit` | DECIMAL(15,2) | NOT NULL, `> 0` | Максимальная совокупная сумма переводов отправителя за месяц |
| `max_transfer_amount` | DECIMAL(15,2) | NOT NULL, `> 0` | Максимальная сумма одного перевода |

Точность `DECIMAL(15,2)` соответствует существующему хранению сумм переводов и расхода лимитов. Существующие `sender_usage.daily_used`, `sender_usage.monthly_used` и `reservations.amount` имеют именно такой тип.

Допустимое значение каждого лимита: больше `0`, не более `9 999 999 999 999.99`, не более двух знаков после десятичной точки. Это соответствует допустимой точности существующего `amount` в REST-контракте перевода.

Отдельные колонки в `sender_usage` добавлять не требуется: эта таблица хранит фактический расход конкретного отправителя, а не значения глобальных порогов (`SenderUsage`).

**Миграция данных:**
- `daily_limit` инициализировать текущим значением `50000.00`;
- `monthly_limit` инициализировать текущим значением `200000.00`;
- начальное значение `max_transfer_amount` в коде и бизнес-требовании отсутствует — **требует уточнения до подготовки итоговой миграции**;
- произвольное значение для `max_transfer_amount` не задавать;
- тестовые данные для лимитов в `limit-service` в текущем коде не найдены.

После перехода на БД существующие `limits.daily-max` и `limits.monthly-max` не должны оставаться вторым независимым источником актуальных значений.

### Изменения в API

#### Эндпоинт: `GET /limits`

Описание: получить текущие значения всех глобальных лимитов.

Параметры запроса: отсутствуют.

Параметры ответа:

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyLimit` | decimal | нет | Дневной лимит |
| `monthlyLimit` | decimal | нет | Месячный лимит |
| `maxTransferAmount` | decimal | нет | Максимальная сумма одного перевода |

Коды ответа:

| Код | Условие |
|---|---|
| `200` | Настройки успешно получены |
| `500` | Глобальная запись настроек отсутствует либо произошла внутренняя ошибка |

Отсутствие глобальной записи после успешного выполнения миграций считать ошибочным состоянием системы, а не отсутствующим пользовательским ресурсом.

---

#### Эндпоинт: `PUT /limits`

Описание: атомарно заменить текущие значения всех трёх глобальных лимитов.

Параметры запроса:

| Параметр | Источник | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `dailyLimit` | body | decimal | да | Новое значение дневного лимита |
| `monthlyLimit` | body | decimal | да | Новое значение месячного лимита |
| `maxTransferAmount` | body | decimal | да | Новая максимальная сумма одного перевода |

Для каждого значения:
- значение должно быть `> 0`;
- не более 13 цифр в целой части;
- не более 2 цифр после десятичной точки.

Параметры ответа:

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyLimit` | decimal | нет | Сохранённый дневной лимит |
| `monthlyLimit` | decimal | нет | Сохранённый месячный лимит |
| `maxTransferAmount` | decimal | нет | Сохранённый лимит одного перевода |

Коды ответа:

| Код | Условие |
|---|---|
| `200` | Все три значения успешно изменены |
| `400` | Отсутствует обязательное поле либо хотя бы одно значение не соответствует допустимому диапазону/точности |
| `500` | Настройки не могут быть сохранены из-за внутренней ошибки |

При ошибке в любом из трёх значений ни одно значение изменяться не должно.

Для ошибок предлагается использовать `application/problem+json`, так как такой формат уже применяется существующим REST API проекта (`transfer-service/.../ApiExceptionHandler.java`, `TransferController`). Структура ошибки в `limit-service` сейчас отсутствует и является новым контрактом.

### Изменения в бизнес-логике

Текущая последовательность проверок — корректность суммы → дневной лимит → месячный лимит (`LimitLedger.decide`).

Добавить проверку максимальной суммы одного перевода после проверки корректности суммы и до проверки накопленных лимитов.

Правила:

- При `amount > maxTransferAmount` система должна отклонить лимитную проверку с причиной `SINGLE_TRANSFER_LIMIT_EXCEEDED`.
- При `amount = maxTransferAmount` система не должна отклонять перевод по лимиту одного перевода.
- При `amount < maxTransferAmount` система должна продолжить существующие проверки дневного и месячного лимитов.
- При превышении одновременно разового и дневного/месячного лимита система должна вернуть `SINGLE_TRANSFER_LIMIT_EXCEEDED`, поскольку разовый лимит проверяется первым.
- При отклонении по `SINGLE_TRANSFER_LIMIT_EXCEEDED` система не должна увеличивать `daily_used` и `monthly_used`.
- При успешной проверке разового лимита существующая логика резервирования дневного и месячного расхода должна остаться без изменений.
- При успешном `PUT /limits` все проверки переводов, начатые после завершения обновления, должны использовать новые значения.
- Изменение лимитов не должно пересчитывать ранее сохранённые решения по переводам.
- При повторном событии `NEW` для уже обработанного `transferId` должно возвращаться ранее сохранённое решение, даже если после первоначальной обработки значения лимитов были изменены. Это сохраняет существующую идемпотентность `LimitLedger.decide`.

Существующие причины `DAILY_LIMIT_EXCEEDED`, `MONTHLY_LIMIT_EXCEEDED` и `INVALID_AMOUNT` не изменять.

`SINGLE_TRANSFER_LIMIT_EXCEEDED`

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

### 6.1. Лимиты не учитывают валюту перевода

`Transfer` содержит `currency`, а входной REST API допускает любую строку из трёх заглавных букв и использует `RUB` только как значение по умолчанию. 

При этом `LimitLedger.decide` суммирует только `amount` и не использует `currency`. Поэтому, например, суммы переводов `100 RUB` и `100 USD` попадают в один числовой дневной/месячный расход без конвертации.

Новый `maxTransferAmount` при сохранении текущей модели также будет валютонезависимым. Валютная семантика лимитов требует решения бизнеса.

### 6.2. Граница дня и месяца зависит от локального времени JVM

Дневной и месячный учёт использует `LocalDate.now()`; часовой пояс лимитного дня в конфигурации не найден (`LimitLedger.decide`, `SenderUsage.lazyReset`). 

Новая доработка это поведение не создаёт, но изменение лимитов через API может потребовать однозначного определения момента вступления значения в силу относительно дневной/месячной границы.

### 6.3. Параллельные переводы одного отправителя могут обрабатываться разными Kafka-партициями

Сообщение `transfers` публикуется с ключом `transfer.id`, а не `senderId` (`TransferController.publishNew`). Поэтому два перевода одного отправителя могут выполняться параллельно. В `SenderUsage` используется optimistic locking через `@Version`.

При высокой конкуренции возможны optimistic-lock конфликты и повторная обработка Kafka-сообщений; после исчерпания настроенных retry запись попадёт в DLT. Это существующий риск корректности/доступности лимитной проверки и относится также к новому разовому лимиту.

### 6.4. Итоговое решение зависит от 10-секундного Kafka Streams join

`transfer-service` объединяет `limit-results` и `screening-results` в окне 10 секунд без grace period.

Если один из результатов не попадёт в это окно, итоговый статус перевода может не сформироваться. Новый код причины отклонения использует тот же маршрут и отдельно эту аномалию не устраняет.

## 7. КРИТЕРИИ ПРИЁМКИ

1. Установлены `dailyLimit = D`, `monthlyLimit = M`, `maxTransferAmount = S`; сумма нового перевода `< S`, а накопленные дневной и месячный расходы после перевода не превышают `D` и `M` → limit-проверка возвращает `APPROVED`.

2. Сумма нового перевода `= S`, дневной и месячный лимиты не превышаются → перевод не отклоняется по разовому лимиту.

3. Сумма нового перевода `> S` → limit-проверка возвращает `DECLINED`, `decidedBy = limit`, `messageInfo = SINGLE_TRANSFER_LIMIT_EXCEEDED`.

4. Сумма одновременно превышает `S` и приводит к превышению дневного лимита → причина результата `SINGLE_TRANSFER_LIMIT_EXCEEDED`.

5. Перевод отклонён по `SINGLE_TRANSFER_LIMIT_EXCEEDED` → значения `daily_used` и `monthly_used` отправителя не увеличиваются.

6. `daily_used + amount = dailyLimit`, остальные проверки пройдены → дневной лимит считается соблюдённым.

7. `daily_used + amount > dailyLimit`, при этом `amount <= maxTransferAmount` → результат `DECLINED / DAILY_LIMIT_EXCEEDED`.

8. `monthly_used + amount = monthlyLimit`, остальные проверки пройдены → месячный лимит считается соблюдённым.

9. `monthly_used + amount > monthlyLimit`, при этом разовый и дневной лимиты не превышены → результат `DECLINED / MONTHLY_LIMIT_EXCEEDED`.

10. `GET /limits` после миграции → возвращает `dailyLimit = 50000.00`, `monthlyLimit = 200000.00` и согласованное с бизнесом начальное значение `maxTransferAmount`.

11. Корректный `PUT /limits` → `200`, в ответе возвращены новые значения; следующий `GET /limits` возвращает те же значения.

12. После успешного `PUT /limits` новый перевод проверяется по обновлённым значениям без перезапуска `limit-service`.

13. В `PUT /limits` хотя бы одно значение равно `0` → `400`, ни один из трёх лимитов не изменён.

14. В `PUT /limits` хотя бы одно значение отрицательное → `400`, ни один лимит не изменён.

15. В `PUT /limits` передано значение с более чем двумя десятичными знаками → `400`, настройки не изменены.

16. В `PUT /limits` отсутствует одно из обязательных полей → `400`, настройки не изменены.

17. Повторно получен `NEW` для перевода, уже отклонённого/одобренного до изменения лимитов → возвращается сохранённое первоначальное решение; перерасчёт по новым лимитам не выполняется.

18. Limit-проверка отклонила перевод по `SINGLE_TRANSFER_LIMIT_EXCEEDED`, screening одобрил → итоговый перевод получает существующий статус `CANCELLED`, `decidedBy = limit`, `messageInfo = SINGLE_TRANSFER_LIMIT_EXCEEDED`.

19. Limit-проверка отклонила перевод по `SINGLE_TRANSFER_LIMIT_EXCEEDED`, screening также отклонил → итоговый статус `DENIED`, причины обоих сервисов сохраняются согласно существующей логике `TransferDecisionService`.

20. После перезапуска `limit-service` → значения, ранее изменённые через REST API, сохраняются и продолжают использоваться.

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ

1. **Каково начальное значение `maxTransferAmount`?** Значение в постановке бизнеса и текущем коде отсутствует. Без него нельзя однозначно подготовить начальную запись миграции.

2. **Лимиты действительно остаются едиными глобальными для всех отправителей или требуется индивидуальная настройка по `senderId`?** Текущий код реализует единые значения лимитов и индивидуальный только расход. Данная постановка сохраняет именно эту модель.

3. **В какой валюте задаются лимиты?** Сейчас `currency` присутствует у перевода, но лимитная логика полностью её игнорирует. Нужно определить: лимиты действуют только для RUB, отдельно для каждой валюты либо требуется пересчёт.

4. **Нужно ли требовать соотношение `maxTransferAmount <= dailyLimit <= monthlyLimit`?** В текущем коде ограничений между дневным и месячным значениями нет. В данной постановке такое ограничение не вводится без решения бизнеса.

5. **Что должно происходить при уменьшении дневного/месячного лимита ниже уже использованной суммы?** Возможные варианты: разрешить изменение и блокировать следующие переводы до сброса/освобождения расхода либо запрещать такое изменение. В коде соответствующего правила нет.
