## 1. ЦЕЛЬ ДОРАБОТКИ
Необходимо ввести глобальное ограничение на максимальную сумму одного перевода для всех отправителей, чтобы снизить риски вывода крупных сумм за одну операцию. Также требуется предоставить возможность динамического управления всеми глобальными лимитами (разовым, дневным, месячным) через REST API без необходимости перезапуска сервисов.

## 2. ПРЕДПОСЫЛКИ
В текущей реализации (`limit-service`) лимиты заданы жестко в конфигурационном файле (`application.yml` через `@Value`), что делает невозможным их оперативное изменение. Кроме того, система проверяет только накопленный объем за день и месяц, позволяя исчерпать весь дневной лимит одной транзакцией.

## 3. SCOPE ИЗМЕНЕНИЙ
- **limit-service (pom.xml):** Модифицируемый — добавление зависимости для REST API.
- **limit-service (БД limitdb):** Новый — добавление таблицы для хранения глобальных лимитов.
- **limit-service (application.yml):** Модифицируемый — удаление хардкод-лимитов.
- **limit-service (API):** Новый — создание контроллера для управления лимитами.
- **limit-service (бизнес-логика):** Модифицируемый — изменение логики проверки (`LimitLedger`) на чтение лимитов из БД и добавление нового правила.

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ
**Где разместить REST API и хранилище лимитов?**
- *Вариант 1:* Разместить API в `transfer-service` (так как там уже есть веб-слой), а изменения транслировать в `limit-service` через Kafka.
- *Вариант 2:* Разместить API и хранилище непосредственно в `limit-service`.

**Рекомендуемый вариант:** Вариант 2.
*Обоснование:* Сервис `limit-service` является владельцем домена лимитов. Размещение API управления лимитами в нем сохраняет инкапсуляцию и избегает ненужного размазывания логики. Для этого потребуется добавить зависимость `spring-boot-starter-web` в `limit-service/pom.xml`.

**Как хранить глобальные лимиты?**
Так как лимиты действуют "для всех отправителей", рекомендуется создать таблицу с единственной строкой (паттерн Singleton Table) со столбцами под каждый тип лимита. Это обеспечит строгую типизацию по сравнению с форматом "ключ-значение".

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. limit-service

**Изменения в зависимостях:**
- В `limit-service/pom.xml` добавить зависимость `spring-boot-starter-web`.

**Изменения в БД:**
- Добавить новую таблицу `global_limits`:
  - `id` (INT, PRIMARY KEY, всегда 1)
  - `single_transfer_max` (DECIMAL(15,2), NOT NULL)
  - `daily_max` (DECIMAL(15,2), NOT NULL)
  - `monthly_max` (DECIMAL(15,2), NOT NULL)
- В миграциях (Liquibase) добавить скрипт создания таблицы и вставки дефолтной строки (ID=1). Текущие значения из `application.yml` (`50000.00` и `200000.00`) перенести в миграцию как начальные значения. Значение для `single_transfer_max` необходимо запросить у бизнеса (см. п.8).

**Изменения в API:**
Добавить новый контроллер для управления лимитами.

  **Эндпоинт 1:** `GET /limits`
  Описание: Получение текущих значений глобальных лимитов.

  Параметры ответа:
  | Поле | Тип | Nullable | Описание |
  |---|---|---|---|
  | singleTransferMax | BigDecimal | Нет | Максимальная сумма одного перевода |
  | dailyMax | BigDecimal | Нет | Дневной лимит |
  | monthlyMax | BigDecimal | Нет | Месячный лимит |

  Коды ответа:
  | Код | Условие |
  |---|---|
  | 200 | Успешный возврат данных |

  **Эндпоинт 2:** `PUT /limits`
  Описание: Обновление глобальных лимитов.

  Параметры запроса:
  | Параметр | Источник (body/path/query) | Тип | Обязательный | Описание |
  |---|---|---|---|---|
  | singleTransferMax | body | BigDecimal | Да | Максимальная сумма одного перевода |
  | dailyMax | body | BigDecimal | Да | Дневной лимит |
  | monthlyMax | body | BigDecimal | Да | Месячный лимит |

  Параметры ответа: Те же, что и в `GET /limits` (возвращает обновленные значения).

  Коды ответа:
  | Код | Условие |
  |---|---|
  | 200 | Лимиты успешно обновлены |
  | 400 | Ошибка валидации (отрицательные суммы) |

**Изменения в бизнес-логике:**
- Убрать чтение лимитов через `@Value` в классе `LimitLedger`.
- При вызове метода принятия решения `LimitLedger.decide()` система должна считывать текущие лимиты из таблицы `global_limits`. *(Примечание: для оптимизации допускается кэширование, но при получении PUT запроса кэш должен инвалидироваться/обновляться).*
- Существующее правило: При превышении суммы операции над `dailyMax` или `monthlyMax` из БД — резервация отклоняется.
- **Новое правило:** При поступлении перевода, если его сумма (`amount`) строго больше значения `single_transfer_max` из БД, система должна отклонить резервацию без обновления счетчиков `SenderUsage`.
- Для нового правила использовать код причины отклонения (reason): `SINGLE_LIMIT_EXCEEDED`.

**Изменения в контрактах сообщений:**
- В контракте самого сообщения `Transfer` изменений нет (поле `messageInfo` имеет тип String).
- Новая причина отклонения `SINGLE_LIMIT_EXCEEDED` будет передаваться в `messageInfo` ответа в топик `limit-results`.

### 5.2. transfer-service
Изменений нет. Сервис прозрачно пробрасывает причину отмены из `limit-results` в поле `messageInfo` (логика в `TransferDecisionService` и `TransferTrackingService` уже обрабатывает любые строковые причины).

### 5.3. screening-service
Изменений нет. Скрининг не зависит от сумм.

### 5.4. transfer-common
Изменений нет.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ
- **Отсутствие транзакционной целостности с Kafka:** В `LimitService.sendAndWait` (и в `TransferController`) отправка в Kafka выполняется после коммита БД. Если Kafka недоступна, транзакция в БД уже зафиксирована. При обновлении лимитов через REST API это не влияет напрямую, но если перевод зависнет в статусе NEW и будет переотправлен, он проверится по *новым* лимитам, даже если был создан до их изменения. Это ожидаемое поведение, но о нем нужно помнить.
- **Минимальная сумма:** В `LimitLedger` есть проверка `amount.signum() <= 0` (INVALID_AMOUNT). REST API `transfer-service` тоже валидирует это (`@Positive`). Конфликта нет, новая логика должна срабатывать после базовых проверок на валидность суммы.

## 7. КРИТЕРИИ ПРИЁМКИ
1. **Чтение лимитов:** `GET /limits` возвращает 200 OK с текущими лимитами из БД.
2. **Изменение лимитов:** `PUT /limits` с корректными данными изменяет настройки в БД и возвращает 200 OK. Сразу после этого новые переводы проверяются по новым правилам (проверить без рестарта приложения).
3. **Проверка разового лимита (отказ):** Создание перевода на сумму, превышающую `single_transfer_max` → перевод получает финальный статус `CANCELLED`, `decidedBy = limit`, `messageInfo = SINGLE_LIMIT_EXCEEDED`. Текущие `SenderUsage` для отправителя не увеличиваются.
4. **Проверка разового лимита (граничное значение):** Создание перевода на сумму, точно равную `single_transfer_max` (и не превышающую остальные) → перевод одобряется (лимитами).
5. **Сохранение старой логики:** Создание двух переводов, каждый из которых меньше `single_transfer_max`, но в сумме они превышают `daily_max` → первый одобряется, второй отклоняется с причиной `DAILY_LIMIT_EXCEEDED`.
