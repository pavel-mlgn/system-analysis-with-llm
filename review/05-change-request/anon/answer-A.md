# Постановка на доработку: ограничение суммы одного перевода и REST API управления лимитами

---

## 1. ЦЕЛЬ ДОРАБОТКИ

Ввести общий для всех отправителей лимит «максимальная сумма одного перевода». Перевод, сумма которого превышает этот порог, должен отклоняться с отдельным кодом причины. Все три лимита (дневной, месячный, на один перевод) должны просматриваться и изменяться через REST API, без перевыпуска и перезапуска сервиса.

## 2. ПРЕДПОСЫЛКИ

- **Нет проверки суммы одного перевода.** Решение по лимитам учитывает только накопленную сумму за день и за месяц. Сумма, равная дневному лимиту (50 000.00), проходит одним переводом (`LimitLedger.decide`). В transfer-service сумма проверяется только по формату: положительная, не более 13 знаков в целой части и 2 в дробной (`TransferRequest`). Бизнесового верхнего порога нет.
- **Лимиты нельзя менять на лету.** Дневной и месячный лимиты заданы как параметры конфигурации `limits.daily-max` и `limits.monthly-max` (`limit-service/application.yml`). Они считываются один раз при старте (`LimitLedger`, поля с `@Value`). Чтобы изменить значение, нужно править конфигурацию и перезапускать сервис.
- **В limit-service нет HTTP-интерфейса.** В `limit-service/pom.xml` нет web-стартера, в `docker-compose.yml` порт для limit-service не опубликован. Посмотреть действующие значения лимитов можно только в конфигурационном файле.

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### 4.1. Где хранить значения лимитов

| Вариант | Плюсы | Минусы |
|---|---|---|
| А. Оставить в `application.yml` | Ничего не меняется | Изменение через API невозможно: значения читаются один раз при старте |
| Б. Таблица в limit-db | Изменения применяются сразу, переживают рестарт, одинаковы для всех экземпляров сервиса; данные лежат рядом с логикой решения | Нужны миграция и начальная запись |
| В. Конфигурация плюс переопределение в памяти через API | Не нужна миграция | Значения теряются при рестарте. При нескольких экземплярах (consumer group `limit`, 3 партиции) значения расходятся между экземплярами |

**Рекомендация: вариант Б.** БД становится единственным источником значений, параметры `limits.*` перестают использоваться.

### 4.2. В каком сервисе разместить REST API управления лимитами

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. limit-service (с собственным HTTP-интерфейсом) | Данные и API у сервиса-владельца лимитов. Изменение сразу видно при принятии решения. GET всегда возвращает фактически применяемые значения | Нужны web-зависимость, новый порт и обработка ошибок в limit-service; появляется вторая HTTP-точка входа в системе |
| B. transfer-service, доставка изменений в limit-service через новый Kafka-топик | Одна HTTP-точка входа | Новый топик и новый контракт, лимиты хранятся дважды, согласованность только «в конечном счёте». GET может показывать значения, которые limit-service ещё не применил |
| C. transfer-service, общая БД с limit-service | Одна точка входа, нет нового топика | Нарушение принципа «у каждого сервиса своя БД» (сейчас у сервисов раздельные БД), связность сервисов по схеме данных |

**Рекомендация: вариант A.**

### 4.3. Где проверять максимальную сумму одного перевода

| Вариант | Плюсы | Минусы |
|---|---|---|
| а. limit-service при обработке NEW, вместе с дневным и месячным лимитами | Вся логика лимитов в одном месте. Причина отказа приходит тем же путём, что и сейчас (DECLINED → CANCELLED/DENIED с `messageInfo`). Перевод и история сохраняются | Клиент узнаёт об отказе асинхронно |
| б. Синхронно в transfer-service при `POST /transfers` (ответ 4xx) | Мгновенная обратная связь | transfer-service не владеет лимитами: нужен синхронный вызов limit-service или копия значений. Логика лимитов размазывается по двум сервисам. Отклонённый перевод не попадает в историю, что расходится с поведением дневного и месячного лимитов |

**Рекомендация: вариант а.**

### 4.4. Структура хранения лимитов

| Вариант | Плюсы | Минусы |
|---|---|---|
| Одна строка с тремя колонками | Атомарное изменение всех лимитов; соотношение лимитов между собой проверяется CHECK-ограничением | Новый тип лимита требует новой колонки |
| Строка на каждый тип лимита (ключ–значение) | Легко добавлять типы и персональные переопределения | Проверку соотношения между строками нельзя выразить простым CHECK |

**Рекомендация: одна строка**, так как задача касается общих лимитов для всех отправителей. Если бизнес планирует персональные лимиты (см. вопрос 8.8), решение нужно пересмотреть.

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. limit-service

**Изменения в БД**

Новая таблица `limit_settings`:

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | SMALLINT | PK, CHECK (`id = 1`) | Гарантирует единственную запись |
| `daily_max` | DECIMAL(15,2) | NOT NULL, CHECK (> 0) | Дневной лимит суммы переводов отправителя |
| `monthly_max` | DECIMAL(15,2) | NOT NULL, CHECK (> 0) | Месячный лимит суммы переводов отправителя |
| `per_transfer_max` | DECIMAL(15,2) | NOT NULL, CHECK (> 0) | Максимальная сумма одного перевода |
| `updated_at` | TIMESTAMP | NOT NULL, DEFAULT NOW() | Момент последнего изменения |

- Ограничение на соотношение лимитов `per_transfer_max <= daily_max AND daily_max <= monthly_max` добавляется, только если бизнес подтвердит правило (вопрос 8.4).
- Тип DECIMAL(15,2) выбран для совместимости с `sender_usage.daily_used`, `reservations.amount` и ограничением суммы перевода в API (13 знаков в целой части + 2 в дробной).

Начальные данные (отдельный changeset, подключается в `changelog-master.yaml`):

- одна запись: `daily_max = 50000.00`, `monthly_max = 200000.00` (текущие значения из `application.yml`);
- `per_transfer_max` — значение задаёт бизнес (вопрос 8.1). Если решения нет к моменту релиза, используется `50000.00`, равное дневному лимиту: поведение для клиентов тогда не изменится;
- если в каком-либо окружении `limits.*` переопределены (в коде и `docker-compose.yml` переопределений нет), начальная запись должна содержать фактически действующие там значения.

Миграция тестовых данных не нужна: в limit-db тестовых данных нет. Таблицы `sender_usage` и `reservations` не меняются.

**Изменения в API**

Ошибки возвращаются в формате `application/problem+json`, как в transfer-service (`spring.mvc.problemdetails.enabled`, `ApiExceptionHandler`). HTTP-порт limit-service — 8081: порт 8080 занят transfer-service, и при локальном запуске сервисы конфликтовали бы.

---

Эндпоинт: GET /limits
Описание: возвращает действующие значения всех лимитов.

Параметры запроса: нет.

Параметры ответа:

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | number (decimal, 2 знака) | нет | Дневной лимит |
| `monthlyMax` | number (decimal, 2 знака) | нет | Месячный лимит |
| `perTransferMax` | number (decimal, 2 знака) | нет | Максимальная сумма одного перевода |
| `updatedAt` | string (date-time) | нет | Момент последнего изменения |

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Значения успешно возвращены |
| 500 | Запись настроек отсутствует или БД недоступна |

---

Эндпоинт: PUT /limits
Описание: полностью заменяет значения всех трёх лимитов и возвращает сохранённые значения.

Параметры запроса:

| Параметр | Источник | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `dailyMax` | body | number (decimal) | да | Новый дневной лимит: > 0, не более 13 знаков в целой и 2 в дробной части |
| `monthlyMax` | body | number (decimal) | да | Новый месячный лимит, те же ограничения формата |
| `perTransferMax` | body | number (decimal) | да | Новая максимальная сумма одного перевода, те же ограничения формата |

Параметры ответа: как у `GET /limits`.

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Лимиты изменены |
| 400 | Поле отсутствует или равно null; значение ≤ 0; более 2 знаков после запятой; более 13 знаков в целой части; нарушено соотношение лимитов (если правило подтверждено, вопрос 8.4); тело не разбирается. В `detail` указывается поле и причина |
| 500 | Внутренняя ошибка или недоступность БД |

Выбрана полная замена (PUT), а не частичная (PATCH): все три значения проверяются и сохраняются вместе, и не возникает неоднозначности, что означает пропущенное поле. Если бизнесу нужно менять лимиты по одному, см. вопрос 8.10.

Также нужно описать оба эндпоинта в новой OpenAPI-спецификации limit-service, по аналогии с `transfer-service/.../openapi/transfer-api.yaml`.

**Изменения в бизнес-логике**

Новые правила:

- При обработке события NEW, если сумма перевода строго больше `per_transfer_max`, система должна отклонить перевод: решение `DECLINED`, причина `PER_TRANSFER_LIMIT_EXCEEDED`. Резерв не создаётся, использование отправителя (`daily_used`, `monthly_used`) не меняется.
- При сумме, равной `per_transfer_max`, проверка максимальной суммы должна считаться пройденной. Это согласуется с текущей семантикой дневного и месячного лимитов: отказ только при строгом превышении (`LimitLedger.decide`).
- Проверки должны выполняться в порядке: некорректная сумма (`INVALID_AMOUNT`) → максимальная сумма одного перевода (`PER_TRANSFER_LIMIT_EXCEEDED`) → дневной лимит → месячный лимит. Возвращается первая сработавшая причина, как и сейчас.
- При обработке NEW система должна брать значения всех трёх лимитов из `limit_settings`, действующие на момент принятия решения. Параметры конфигурации `limits.*` больше не используются.
- После успешного ответа `PUT /limits` новые значения должны применяться ко всем событиям NEW, которые обрабатываются после этого момента, на всех экземплярах limit-service, без перезапуска.
- Если значения лимитов не удаётся прочитать (записи нет, БД недоступна), система не должна одобрять перевод: обработка события завершается ошибкой по существующей схеме (повторы, затем DLT). Последствия описаны в п. 6.3.
- При изменении через API система должна сохранить все три значения атомарно: либо все, либо ни одного. При ошибке валидации прежние значения не меняются.

Затрагиваемые существующие правила:

- Дневной и месячный лимиты проверяются как раньше, но значения берутся из БД.
- При повторном событии NEW для перевода, по которому решение уже принято, система должна вернуть сохранённое решение, даже если лимиты с тех пор изменились (текущее поведение `LimitLedger.decide`).
- При снижении лимитов система не должна пересматривать уже созданные резервы (состояния RESERVED и COMMITTED). Их фиксация и освобождение (`LimitLedger.settle`) работают без изменений.
- Если после снижения дневного или месячного лимита накопленное использование отправителя уже выше нового значения, система должна отклонять его новые переводы с `DAILY_LIMIT_EXCEEDED` / `MONTHLY_LIMIT_EXCEEDED` до ближайшего сброса.

**Изменения в контрактах сообщений**

Структура `Transfer` (transfer-common) не меняется. Появляются новые значения:

| Топик | status | decidedBy | messageInfo |
|---|---|---|---|
| `limit-results` | `DECLINED` | `limit` | `PER_TRANSFER_LIMIT_EXCEEDED` |
| `transfers` (финальный), отправитель не заблокирован | `CANCELLED` | `limit` | `PER_TRANSFER_LIMIT_EXCEEDED` |
| `transfers` (финальный), отправитель заблокирован | `DENIED` | `null` | `PER_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED` |

Финальные значения формирует существующая логика `TransferDecisionService.decide`, доработка в ней не нужна. Потребителей, которые разбирают коды причин по перечню, в коде не найдено.

**Изменения в конфигурации и развёртывании**

- В `application.yml` limit-service убираются параметры `limits.daily-max` и `limits.monthly-max`, добавляется HTTP-порт 8081.
- В `docker-compose.yml` публикуется порт limit-service `8081:8081`.

### 5.2. transfer-service

Изменений в коде нет. Новый код причины проходит транзитом через `limit-results` → join → `transfers` → `transfers.message_info` и `transfer_history.message_info`. Колонки имеют тип TEXT и ограничений длины не имеют.

Опционально можно дополнить описание поля `messageInfo` в `transfer-api.yaml` перечнем возможных кодов причин. Сейчас поле описано как произвольная строка.

### 5.3. screening-service

Изменений нет: проверка блокировки отправителя не зависит от лимитов.

### 5.4. transfer-common

Изменений нет: причина передаётся в существующем строковом поле `messageInfo`.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

**6.1. Лимиты не учитывают валюту.** `TransferRequest` принимает любую валюту формата `[A-Z]{3}`, а `LimitLedger.decide` сравнивает номинальную сумму с лимитами без учёта `currency`. Дневное и месячное использование тоже суммируется по номиналу из разных валют. Новый лимит унаследует это поведение: 50 000 USD и 50 000 RUB будут сравниваться с одним и тем же порогом. Бизнес должен определить валюту лимитов (вопрос 8.2).

**6.2. Окно join 10 секунд без grace-периода.** Окно задано в `DecisionTopologyConfig.decisionStream` через `ofTimeDifferenceWithNoGrace`. Если результат limit-service опоздал больше чем на 10 секунд относительно результата screening, финальный статус не формируется. Перевод остаётся в NEW, а при одобрении лимитом резерв остаётся RESERVED и занимает дневное и месячное использование. Для этой доработки это существенно в трёх случаях:
- выкладка требует перезапуска limit-service, и переводы, принятые во время простоя, не пройдут join;
- если лимиты не прочитались из БД, срабатывают повторы `FixedBackOff(1000, 3)` (`KafkaErrorHandlingConfig`) и затем отправка в `transfers.DLT`, перевод остаётся в NEW;
- лишнее чтение из БД при каждом решении увеличивает задержку.

Перевод можно восстановить повторным `POST /transfers` с тем же id: transfer-service заново публикует NEW (`TransferController.duplicate`), а оба сервиса возвращают сохранённые решения. Выкладку limit-service рекомендуется делать при остановленном приёме переводов.

**6.3. Повторный NEW возвращает сохранённое решение.** Так работает `LimitLedger.decide`. Изменение лимитов не пересматривает уже принятые решения. Перевод, отклонённый по `PER_TRANSFER_LIMIT_EXCEEDED`, нельзя повторить с тем же id после повышения лимита: нужен новый перевод.

**6.4. Длина причины ограничена 50 символами.** Колонка `reservations.reason` имеет тип VARCHAR(50). Код `PER_TRANSFER_LIMIT_EXCEEDED` (27 символов) помещается. Если бизнес захочет человекочитаемый текст с суммами (вопрос 8.3), колонку придётся расширять, либо формировать текст в другом месте.

**6.5. Ленивый сброс использования и часовой пояс.** `SenderUsage.lazyReset` обнуляет `daily_used` и `monthly_used` только при следующем переводе отправителя, поэтому значения в `sender_usage` могут быть устаревшими. Дата определяется через `LocalDate.now()`, часовой пояс в коде явно не задан: используется пояс JVM или контейнера. Это важно, если API просмотра должен показывать текущее использование (вопрос 8.7): хранимые значения нельзя отдавать как есть. Кроме того, бизнесу нужно знать, в какой момент суток фактически сбрасывается дневной лимит.

**6.6. В проекте нет аутентификации и авторизации.** В коде не найдено ни Spring Security, ни иных механизмов. Новый `PUT /limits` позволит любому, у кого есть сетевой доступ, снять ограничения для всех отправителей (вопрос 8.5).

## 7. КРИТЕРИИ ПРИЁМКИ

Условия по умолчанию:
- лимиты установлены через `PUT /limits` в значения `perTransferMax = 10000.00`, `dailyMax = 50000.00`, `monthlyMax = 200000.00`;
- отправитель 1 не заблокирован, на сегодня использования нет;
- отправитель 5 заблокирован (тестовые данные screening-service).

**Проверка суммы одного перевода**

1. Перевод 10000.00 от отправителя 1 → `COMPLETED`.
2. Перевод 10000.01 от отправителя 1 → `CANCELLED`, `decidedBy = limit`, `messageInfo = PER_TRANSFER_LIMIT_EXCEEDED`. В истории на этапе LIMIT: `DECLINED` с той же причиной.
3. После кейса 2 перевод 10000.00 от отправителя 1 → `COMPLETED`: отклонённый перевод не занял использование.
4. Перевод 0.01 → `COMPLETED`.
5. Перевод 10000.01 от отправителя 5 → `DENIED`, `decidedBy = null`, `messageInfo = PER_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED`.
6. Использование отправителя за день 45000.00, перевод 10000.01 → причина `PER_TRANSFER_LIMIT_EXCEEDED`, а не `DAILY_LIMIT_EXCEEDED`.
7. Использование отправителя за день 45000.00, перевод 6000.00 → `DAILY_LIMIT_EXCEEDED`.
8. Использование отправителя за месяц 195000.00 при `dailyMax = 50000.00`, перевод 6000.00 → `MONTHLY_LIMIT_EXCEEDED`.

**API просмотра и изменения**

9. Сразу после миграции `GET /limits` → 200, `dailyMax = 50000.00`, `monthlyMax = 200000.00`, `perTransferMax` равно согласованному начальному значению.
10. Корректный `PUT /limits` → 200, в ответе новые значения; последующий `GET` возвращает их же, `updatedAt` обновлён.
11. `PUT` без одного из полей или с `null` → 400, значения не изменились.
12. `PUT` с `perTransferMax = 0` или отрицательным значением → 400.
13. `PUT` с `perTransferMax = 100.001` → 400.
14. `PUT` с `dailyMax = 10000000000000.00` (14 знаков в целой части) → 400. С `9999999999999.99` при соблюдении соотношения лимитов → 200.
15. Если правило соотношения подтверждено: `perTransferMax > dailyMax` → 400; `perTransferMax = dailyMax` → 200; `dailyMax > monthlyMax` → 400; `dailyMax = monthlyMax` → 200.
16. После любого отклонённого `PUT` → `GET` возвращает прежние значения.

**Применение изменений**

17. `PUT perTransferMax = 5000.00`, затем без перезапуска перевод 6000.00 → `PER_TRANSFER_LIMIT_EXCEEDED`.
18. Использование за день 50000.00, перевод 0.01 → `DAILY_LIMIT_EXCEEDED`. Затем `PUT dailyMax = 60000.00`, перевод 10000.00 → `COMPLETED`.
19. Использование за день 30000.00 (резервы в RESERVED). `PUT dailyMax = 20000.00` → новый перевод 0.01 отклоняется с `DAILY_LIMIT_EXCEEDED`. Ранее созданные резервы фиксируются и освобождаются как обычно.
20. Перевод отклонён по `PER_TRANSFER_LIMIT_EXCEEDED`, затем лимит повышен, затем `POST /transfers` с тем же id и параметрами → возвращается существующий перевод в статусе `CANCELLED`, повторного решения нет.
21. Перезапуск limit-service → `GET /limits` возвращает последние сохранённые значения, решения принимаются по ним.
22. Миграция на БД с данными → `sender_usage` и `reservations` не изменились, в `limit_settings` ровно одна запись.

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ

1. **Начальное значение лимита одного перевода.** Какое значение `per_transfer_max` установить при запуске? Без ответа будет 50 000.00 (равно дневному лимиту), и фактически поведение не изменится.
2. **Валюта лимитов.** В какой валюте заданы лимиты? Как поступать с переводами в других валютах: сравнивать по номиналу как сейчас, конвертировать или отклонять?
3. **Формат «понятной причины».** Достаточно ли кода `PER_TRANSFER_LIMIT_EXCEEDED`, аналогичного существующим `DAILY_LIMIT_EXCEEDED` и `MONTHLY_LIMIT_EXCEEDED`? Или нужен текст для клиента, например с указанием порога, и на каком языке?
4. **Соотношение лимитов.** Должна ли система запрещать значения, при которых лимит одного перевода больше дневного или дневной больше месячного?
5. **Права на изменение лимитов.** Кто имеет право менять лимиты? Нужна ли аутентификация и разграничение доступа для `PUT /limits`, если в проекте их нет совсем (п. 6.6)?
6. **Журнал изменений.** Нужно ли хранить историю изменений: кто, когда, старое и новое значение?
7. **Объём просмотра.** «Просмотр значений всех лимитов» — это только настройки, или также текущее использование конкретного отправителя (сколько израсходовано и сколько осталось)? Если второе, нужно учесть п. 6.5 и определить часовой пояс сброса.
8. **Персональные лимиты.** Лимиты остаются только общими, или в перспективе нужны персональные значения для отдельных отправителей? Ответ влияет на структуру хранения (п. 4.4).
9. **Момент вступления в силу.** Изменения применяются сразу, или, например, снижение дневного лимита должно действовать со следующего дня?
10. **Способ изменения через API.** Устраивает ли изменение всех трёх лимитов одним запросом, или нужна возможность менять каждый лимит по отдельности?
11. **Приоритет причин.** Подтвердите порядок: если одновременно превышены лимит одного перевода и дневной или месячный лимит, клиент видит `PER_TRANSFER_LIMIT_EXCEEDED`.
