# Бизнес-логика системы переводов: точки входа, правила, решения, аномалии

> Основа анализа — исходный код из файла `code.txt`, прочитанный полностью. Описание опирается только на код. То, чего в коде нет, помечено «в коде не найдено» или «требует уточнения».

## Общие сведения

Бизнес-логика есть в трёх сервисах:

- **Сервис переводов** (`transfer-service`) принимает заявки на перевод, выдаёт сведения о переводах, сводит ответы двух проверок в итоговое решение, ведёт статус и историю перевода.
- **Сервис лимитов** (`limit-service`) проверяет дневной и месячный лимит отправителя, резервирует сумму и закрывает резерв по итогу перевода.
- **Сервис проверки отправителя** (`screening-service`) сверяет отправителя со списком заблокированных.

В модуле `transfer-common` описан только общий формат события о переводе. Своей бизнес-логики в нём нет. Единственное правило: событие о новом переводе всегда создаётся со статусом NEW (`Transfer.newTransfer()`).

**Статусы и состояния в этом описании**

| Понятие | Значение | Смысл |
|---|---|---|
| Статус перевода | NEW | перевод зарегистрирован, итогового решения ещё нет |
| | COMPLETED | обе проверки одобрили перевод |
| | CANCELLED | одна из проверок отказала либо пришёл неожиданный ответ |
| | DENIED | обе проверки отказали |
| Ответ проверки (лимиты или отправитель) | APPROVED / DECLINED | одобрено / отклонено |
| Причина отказа | DAILY_LIMIT_EXCEEDED, MONTHLY_LIMIT_EXCEEDED, INVALID_AMOUNT | отказ сервиса лимитов |
| | SENDER_BLOCKED | отказ проверки отправителя |
| Состояние резерва лимита | RESERVED | сумма зарезервирована (уже учтена в лимитах) и ждёт итога |
| | COMMITTED | резерв подтверждён, перевод выполнен |
| | RELEASED | резерв снят, сумма возвращена в лимит |
| | NONE | резерва нет (отказ по лимитам) |
| Этап истории перевода | NEW, LIMIT, SCREENING, FINAL | создание; ответ лимитов; ответ проверки отправителя; итог |

## Сервис переводов

### ТВ-1. Приём заявки на перевод

**ТОЧКА ВХОДА:** `TransferController.create()`

**Триггер:** HTTP-запрос «Создать перевод» (POST /transfers). В запросе передаются идентификатор перевода (его назначает сам клиент), отправитель, получатель, сумма и, по желанию, валюта.

**Алгоритм:**
1. Проверить заполнение заявки: есть все обязательные реквизиты, сумма положительная, в целой части не больше 13 знаков, в дробной не больше 2, код валюты в правильном формате. Если что-то нарушено, заявка отклоняется как некорректная.
2. Найти перевод с тем же идентификатором.
3. Если такой перевод уже есть, заявка считается повторной:
   1. Её параметры сравниваются с существующим переводом: отправитель, получатель, сумма (по значению) и валюта (если в заявке валюта не указана, считается RUB).
   2. Если хоть один параметр отличается, клиент получает отказ «конфликт»: перевод с таким идентификатором уже существует с другими параметрами.
   3. Если параметры совпадают, а перевод всё ещё ждёт решения (NEW), он ещё раз отправляется на проверки.
   4. Клиенту возвращается текущее состояние существующего перевода.
4. Если перевода нет, регистрируется новый: статус NEW, время создания и время изменения — текущие, в историю пишется этап «Создание» (NEW). Регистрация и запись истории выполняются как одно целое: либо обе, либо ни одной.
5. Если при регистрации оказалось, что параллельный запрос только что создал такой же перевод, система ещё раз ищет этот перевод и обрабатывает заявку как повторную (шаг 3). Если перевод найти не удалось, клиент получает внутреннюю ошибку.
6. Новый перевод отправляется на обе проверки, лимитов и отправителя. Подтверждение отправки ждут до 10 секунд.
7. Если отправить не удалось, клиенту сообщают о временной недоступности: перевод сохранён, запрос нужно повторить с тем же идентификатором. Регистрация перевода при этом не отменяется.
8. Клиент получает данные созданного перевода в статусе NEW. Итоговое решение он узнаёт позже, когда запросит перевод (ТВ-3). Уведомлений клиенту об итоге в коде не найдено.

В коде не найдено проверок того, что отправитель и получатель различаются, что оба существуют, что инициатор вправе распоряжаться средствами отправителя и что валюта есть в справочнике (см. АН-04, АН-17).

**Бизнес-правила:**
- БП-1: Если в заявке нет идентификатора перевода, отправителя, получателя или суммы, то заявка отклоняется как некорректная (400) и перевод не создаётся.
- БП-2: Если сумма не больше нуля, то заявка отклоняется (400).
- БП-3: Если в целой части суммы больше 13 цифр или после запятой больше 2 знаков, то заявка отклоняется (400).
- БП-4: Если валюта указана, но это не ровно три заглавные латинские буквы, то заявка отклоняется (400). Существует ли такая валюта на самом деле, не проверяется.
- БП-5: Если валюта не указана, то перевод оформляется в RUB.
- БП-6: Если перевод с таким идентификатором уже есть и у него другой отправитель, получатель, сумма (сравнивается по значению: 100 и 100.00 равны) или валюта (с учётом RUB по умолчанию), то клиент получает отказ «конфликт» (409) с текстом «Перевод с id=… уже существует с другими параметрами». Существующий перевод не меняется.
- БП-7: Если перевод с таким идентификатором уже есть с теми же параметрами, то новый не создаётся, а клиент получает текущее состояние существующего перевода (200) при любом его статусе.
- БП-8: Если повторная заявка совпала с переводом, который ещё в статусе NEW, то перевод ещё раз отправляется на проверки. Перевод с итоговым статусом повторно не отправляется.
- БП-9: Если перевода с таким идентификатором нет, то он регистрируется в статусе NEW, в историю пишется этап «Создание», перевод уходит на проверки, а клиент получает данные перевода (201).
- БП-10: Если отправить перевод на проверки не удалось (ошибка или нет подтверждения за 10 секунд), то клиент получает ответ 503 «Kafka недоступна, перевод сохранён — повторите запрос с тем же id». Сохранённый перевод не удаляется и остаётся в статусе NEW.
- БП-11: Если две заявки с одним идентификатором пришли одновременно и вторую не удалось сохранить, потому что запись уже создана, то вторая обрабатывается как повторная (БП-6 – БП-8). Если после этого перевод найти не удалось, клиент получает внутреннюю ошибку (500).
- БП-12: Если при обработке HTTP-запроса произошла любая другая непредвиденная ошибка, то клиент получает 500 «Внутренняя ошибка сервера, повторите запрос позже» (`ApiExceptionHandler.handleUnexpected()`). Правило действует для ТВ-1 – ТВ-3.

**Данные:**
- Читается: переводы (`transfers`) — поиск по `id`; для повторной заявки — `sender_id`, `recipient_id`, `amount`, `currency`, `status`.
- Создаётся: перевод (`transfers`: `id`, `sender_id`, `recipient_id`, `amount`, `currency`, `status` = NEW, `created_at`, `updated_at`) и запись истории (`transfer_history`: `transfer_id`, `stage` = NEW, `status` = NEW, `changed_at`).
- Изменяется: ничего, существующие переводы не меняются.
- Отправляется: событие «новый перевод» со статусом NEW, на проверки.

**Исходы:**
- 201 Created: новый перевод зарегистрирован в статусе NEW и отправлен на проверки.
- 200 OK: повторная заявка с теми же параметрами. Возвращается текущее состояние перевода, NEW или итоговое. Если статус NEW, перевод ещё раз отправлен на проверки.
- 400 Bad Request: нарушены БП-1 – БП-4 либо тело запроса не читается.
- 409 Conflict: идентификатор уже занят переводом с другими параметрами.
- 503 Service Unavailable: отправить на проверки не удалось. Новый перевод при этом сохранён в NEW, а при повторной заявке перевод уже существовал.
- 500 Internal Server Error: непредвиденная ошибка, например недоступна база данных или при конфликте сохранения перевод так и не нашёлся.

### ТВ-2. Просмотр списка переводов

**ТОЧКА ВХОДА:** `TransferController.all()`

**Триггер:** HTTP-запрос «Получить все переводы» (GET /transfers).

**Алгоритм:**
1. Выбрать все зарегистрированные переводы.
2. Упорядочить их по времени создания, новые первыми.
3. Вернуть список без истории.

Фильтра по клиенту, постраничной выдачи и разграничения доступа в коде не найдено (см. АН-04, АН-18).

**Бизнес-правила:**
- БП-13: Если запрошен список переводов, то возвращаются все переводы всех отправителей, от новых к старым по времени создания, без ограничения количества и без фильтров.

**Данные:**
- Читается: `transfers` — все записи, упорядоченные по `created_at` по убыванию.
- Изменяется: ничего.

**Исходы:**
- 200 OK: список переводов, возможно пустой.
- 500: непредвиденная ошибка (БП-12).

### ТВ-3. Просмотр перевода с историей

**ТОЧКА ВХОДА:** `TransferController.getById()`

**Триггер:** HTTP-запрос «Получить перевод по ID с историей» (GET /transfers/{id}).

**Алгоритм:**
1. Найти перевод по идентификатору.
2. Если перевода нет, ответить «не найдено».
3. Получить все записи истории перевода.
4. Упорядочить историю по этапам — «Создание», «Лимиты», «Проверка отправителя», «Итог», — а внутри этапа по времени записи.
5. Вернуть перевод вместе с историей.

**Бизнес-правила:**
- БП-14: Если перевод с запрошенным идентификатором не найден, то клиент получает ответ 404 без тела.
- БП-15: Если перевод найден, то возвращаются его данные и история. История упорядочена по этапам («Создание» → «Лимиты» → «Проверка отправителя» → «Итог»), а не по времени. Время учитывается только внутри одного этапа.

**Данные:**
- Читается: `transfers` (по `id`); `transfer_history` (по `transfer_id`; поля `stage`, `status`, `decided_by`, `message_info`, `changed_at`).
- Изменяется: ничего.

**Исходы:**
- 200 OK: перевод и его история.
- 404 Not Found: перевода нет.
- 400 Bad Request: идентификатор в адресе не число.
- 500: непредвиденная ошибка (БП-12).

### ТВ-4. Сведение ответов проверок в итоговое решение

**ТОЧКА ВХОДА:** `DecisionTopologyConfig.decisionStream()`, правила решения — в `TransferDecisionService.decide()`

**Триггер:** потоковая обработка. Срабатывает, когда по одному переводу есть и ответ сервиса лимитов (поток `limit-results`), и ответ сервиса проверки отправителя (поток `screening-results`), причём отправлены они с разницей не больше 10 секунд.

**Алгоритм:**
1. Принимать ответы обеих проверок по мере их поступления. Каждый ответ хранится 10 секунд, пока для него ищется пара.
2. Для каждого ответа искать ответ другой проверки по тому же переводу, отправленный не раньше чем за 10 секунд до него и не позже чем через 10 секунд после.
3. Для каждой найденной пары определить итоговый статус, инициатора решения и пояснение (БП-17 – БП-21). Реквизиты перевода в итоговом сообщении берутся из ответа сервиса лимитов.
4. Записать решение в журнал и опубликовать итоговый статус перевода. Его обрабатывают ТВ-5, ТВ-6 и ТВ-7.
5. Если пары за отведённое время нет, ничего не делать: ответ без пары по истечении окна отбрасывается. Повторного запроса ответа, ограничения времени ожидания для перевода и уведомлений в коде не найдено.
6. Ответ, который невозможно прочитать, пропускается с записью в журнал.

**Бизнес-правила:**
- БП-16: Если по переводу пришли ответы обеих проверок и время их отправки различается не больше чем на 10 секунд, то формируется итоговое решение. Если одного из ответов нет или разница больше 10 секунд, итоговое решение не формируется никогда.
- БП-17: Если обе проверки ответили «одобрено», то итоговый статус COMPLETED. Инициатор решения и пояснение не заполняются.
- БП-18: Если обе проверки ответили «отклонено», то итоговый статус DENIED. Инициатор не указывается, пояснение — «<причина отказа по лимитам>; <причина отказа проверки отправителя>».
- БП-19: Если сервис лимитов отказал, а проверка отправителя одобрила, то итоговый статус CANCELLED, инициатор — limit, пояснение — причина отказа по лимитам.
- БП-20: Если сервис лимитов одобрил, а проверка отправителя отказала, то итоговый статус CANCELLED, инициатор — screening, пояснение — причина отказа проверки.
- БП-21: Если хотя бы один ответ не равен ни «одобрено», ни «отклонено», то итоговый статус CANCELLED. Инициатор не указывается, пояснение — «UNEXPECTED_RESULT: limit=<ответ лимитов>, screening=<ответ проверки>».
- БП-22: Если ответ проверки невозможно прочитать, то он пропускается с записью в журнал, и итоговое решение по нему не формируется.

**Данные:**
- Читается: ответы проверок (ответ, инициатор, пояснение, реквизиты перевода). Таблицы базы данных не используются. Ответы хранятся 10 секунд во внутреннем хранилище потоковой обработки.
- Изменяется: таблицы не меняются.
- Отправляется: итоговый статус перевода (COMPLETED / CANCELLED / DENIED) с инициатором и пояснением.

**Исходы:**
- Опубликован итоговый статус COMPLETED, CANCELLED (отказ лимитов, отказ проверки или неожиданный ответ) или DENIED.
- Итоговое решение не сформировано, потому что одного ответа нет или ответы разошлись больше чем на 10 секунд. Перевод остаётся в NEW (см. АН-01, АН-02).
- По одному переводу сформировано несколько одинаковых итоговых решений: так бывает, если какая-то проверка ответила повторно в пределах окна. Решение формируется для каждой пары ответов (см. АН-11).
- Нечитаемый ответ пропущен, решение по нему не сформировано.
- Сбой при публикации итогового решения: обработка такого сбоя в коде не настроена, поведение требует уточнения.

### ТВ-5. Учёт ответов проверок и итоговых статусов

**ТОЧКА ВХОДА:** `TransferEventListener.onEvent()`. Работа выполняется в `TransferTrackingService.recordServiceResult()` и `TransferTrackingService.applyFinalStatus()`.

**Триггер:** входящие сообщения трёх видов:
- ответ сервиса лимитов (поток `limit-results`) обрабатывается всегда;
- ответ проверки отправителя (поток `screening-results`) обрабатывается всегда;
- событие из общего потока переводов (`transfers`) обрабатывается, только если его статус не NEW, то есть это итоговый статус.

**Алгоритм:**

*А. Ответ проверки (лимиты или отправитель)*
1. Найти перевод. Если его нет, пропустить ответ с предупреждением в журнале.
2. Проверить, записан ли уже в историю перевода ответ этой проверки. Если записан, пропустить: учитывается только первый ответ.
3. Записать в историю этап «Лимиты» (LIMIT) или «Проверка отправителя» (SCREENING): ответ, инициатор, пояснение, время.
4. Обновить время изменения перевода. Статус перевода не меняется.

*Б. Событие из общего потока переводов*
1. Если статус NEW, ничего не делать: это событие о новом переводе, которое отправил сам сервис.
2. Иначе найти перевод. Если его нет, пропустить событие с предупреждением.
3. Если итоговый статус уже применён (в истории есть этап «Итог»), пропустить: действует первый итоговый статус.
4. Записать в перевод статус, инициатора решения и пояснение из события и обновить время изменения.
5. Записать в историю этап «Итог» (FINAL).

Варианты А и Б выполняются как одно целое: либо все изменения, либо ни одного. Если обработка не удалась, работают общие правила БП-51 и БП-52.

**Бизнес-правила:**
- БП-23: Если ответ проверки пришёл по переводу, которого нет в сервисе переводов, то ответ пропускается с предупреждением в журнале.
- БП-24: Если ответ этой проверки по переводу уже записан в историю, то повторный ответ пропускается: учитывается первый.
- БП-25: Если ответ проверки пришёл впервые, то в историю добавляется этап «Лимиты» или «Проверка отправителя» с ответом, инициатором и пояснением, и обновляется время изменения перевода. Статус перевода не меняется.
- БП-26: Если в общем потоке переводов пришло событие со статусом NEW, то сервис переводов его не обрабатывает.
- БП-27: Если итоговый статус пришёл по несуществующему переводу, то он пропускается с предупреждением.
- БП-28: Если итоговый статус по переводу уже применён (в истории есть этап «Итог»), то повторный итоговый статус пропускается: действует первый.
- БП-29: Если итоговый статус пришёл впервые, то перевод получает этот статус, инициатора и пояснение, время изменения обновляется, в историю добавляется этап «Итог». Допустимость статуса не проверяется: итоговым считается любой статус, кроме NEW.

**Данные:**
- Читается: `transfers` (по `id`); `transfer_history` (есть ли запись с данным `transfer_id` и `stage`).
- Изменяется: `transfers` — для ответа проверки `updated_at`; для итогового статуса `status`, `decided_by`, `message_info`, `updated_at`.
- Создаётся: `transfer_history` (`transfer_id`, `stage` = LIMIT / SCREENING / FINAL, `status`, `decided_by`, `message_info`, `changed_at`). По одному этапу у перевода может быть только одна запись, это ограничение базы данных.

**Исходы:**
- Ответ проверки записан в историю.
- Повторный ответ проверки или повторный итоговый статус пропущен.
- Сообщение по несуществующему переводу пропущено.
- Итоговый статус применён к переводу и записан в историю.
- Событие NEW пропущено.
- Ошибка обработки (например, недоступна база данных): ещё до 3 попыток, затем сообщение уходит в очередь неразобранных. Перевод может навсегда остаться в NEW, хотя в других сервисах уже закрыт (см. АН-05).
- Две одновременные записи одного этапа: вторая нарушает ограничение уникальности и завершается ошибкой, при повторной попытке пропускается как дубль.

## Сервис лимитов

### ТВ-6. Проверка лимитов отправителя и закрытие резерва

**ТОЧКА ВХОДА:** `TransferEventsListener.onEvent()` (limit-service). Новый перевод обрабатывают `LimitService.onNewTransfer()` и `LimitLedger.decide()`, итоговый статус — `LimitService.onFinalStatus()` и `LimitLedger.settle()`.

**Триггер:** событие из общего потока переводов (`transfers`). При статусе NEW проверяются лимиты (ветка А). При любом другом статусе событие считается итоговым и закрывается резерв (ветка Б).

**Алгоритм.**

*Ветка А. Новый перевод*
1. Проверить, принималось ли уже решение по этому переводу. Если да, взять сохранённое решение без пересчёта и перейти к шагу 9.
2. Определить текущую дату по часам сервера.
3. Если сумма не указана или не больше нуля, отказать с причиной INVALID_AMOUNT. Решение сохраняется с суммой 0 и без резерва, учёт лимитов отправителя не трогается. Перейти к шагу 9.
4. Найти учёт использования лимитов отправителя. Если его нет, завести новый с нулевыми суммами.
5. Привести счётчики к текущей дате: если наступил новый день, обнулить дневную использованную сумму, если новый месяц — месячную.
6. Если дневная использованная сумма плюс сумма перевода больше дневного лимита (50 000,00), отказать с причиной DAILY_LIMIT_EXCEEDED.
7. Иначе, если месячная использованная сумма плюс сумма перевода больше месячного лимита (200 000,00), отказать с причиной MONTHLY_LIMIT_EXCEEDED.
8. Иначе одобрить: прибавить сумму к дневной и месячной использованной сумме и оформить резерв (RESERVED) с датой резерва, равной текущей дате. Затем сохранить учёт использования (при отказе тоже, уже с обнулёнными счётчиками) и решение. Шаги 1–8 выполняются как одно целое. Если учёт того же отправителя одновременно изменился в другой обработке, срабатывает контроль версий: обработка завершается ошибкой и повторяется (БП-51).
9. Отправить решение (APPROVED или DECLINED, инициатор limit, причина) на сведение решений и до 10 секунд ждать подтверждения. Если отправить не удалось, обработка считается неуспешной (БП-51), а сохранённое решение и резерв не отменяются.

*Ветка Б. Итоговый статус перевода*
1. Найти решение по переводу. Если его нет, пропустить событие с предупреждением.
2. Если резерв не в состоянии RESERVED, пропустить: перевод был отклонён по лимитам или резерв уже закрыт.
3. Если итоговый статус COMPLETED, подтвердить резерв (COMMITTED). Использованные суммы не меняются, сумма перевода остаётся в лимитах.
4. Если итоговый статус CANCELLED или DENIED, снять резерв:
   1. Найти учёт отправителя. Он обязан существовать, иначе обработка завершается ошибкой.
   2. Привести счётчики к текущей дате (как в шаге А5).
   3. Вычесть сумму из дневной использованной суммы, только если резерв сделан сегодня, и из месячной, только если резерв сделан в текущем месяце. Ни одна сумма не может стать меньше нуля.
   4. Перевести резерв в состояние RELEASED.
5. При любом другом итоговом статусе записать предупреждение и ничего не менять.
6. Сохранить изменения. Шаги 1–6 выполняются как одно целое.

**Бизнес-правила:**
- БП-30: Если пришло событие со статусом NEW, то проверяются лимиты. При любом другом статусе событие считается итоговым и закрывается резерв.
- БП-31: Если решение по лимитам для этого перевода уже принималось, то повторно оно не принимается: ещё раз отправляется сохранённое решение. Пересчёта нет, даже если изменились дата или использованные суммы.
- БП-32: Если сумма перевода не указана или не больше нуля, то перевод отклоняется с причиной INVALID_AMOUNT. Учёт лимитов отправителя не меняется, а решение сохраняется с суммой 0 и состоянием резерва NONE.
- БП-33: Если у отправителя ещё нет учёта использования лимитов, то он заводится с нулевыми суммами, а даты последнего обнуления становятся текущей датой.
- БП-34: Если текущая дата отличается от даты последнего обнуления дневного счётчика, то дневная использованная сумма обнуляется, а дата обнуления становится текущей. Дата определяется по часам сервера лимитов.
- БП-35: Если текущий календарный месяц отличается от месяца последнего обнуления месячного счётчика, то месячная использованная сумма обнуляется.
- БП-36: Если дневная использованная сумма плюс сумма перевода больше дневного лимита (50 000,00, настройка `limits.daily-max`), то перевод отклоняется с причиной DAILY_LIMIT_EXCEEDED. Дневной лимит проверяется первым, поэтому при превышении обоих лимитов причина — дневной. Лимит одинаков для всех отправителей и валют.
- БП-37: Если дневной лимит не превышен, а месячная использованная сумма плюс сумма перевода больше месячного лимита (200 000,00, настройка `limits.monthly-max`), то перевод отклоняется с причиной MONTHLY_LIMIT_EXCEEDED.
- БП-38: Если оба лимита соблюдены (ровно достичь лимита можно), то перевод одобряется: сумма прибавляется к дневной и месячной использованной сумме, резерв оформляется в состоянии RESERVED с датой резерва, равной текущей дате.
- БП-39: Если перевод отклонён по лимитам, то использованные суммы не растут и резерв не создаётся (состояние NONE).
- БП-40: Если решение принято, то оно отправляется на сведение решений с инициатором limit и причиной отказа (при одобрении без причины). Если отправить не удалось за 10 секунд, обработка события считается неуспешной (БП-51), а сохранённое решение и резерв остаются.
- БП-41: Если пришёл итоговый статус по переводу, решения по которому в сервисе лимитов нет, то статус пропускается с предупреждением.
- БП-42: Если резерв перевода не в состоянии RESERVED, то итоговый статус пропускается.
- БП-43: Если итоговый статус COMPLETED, то резерв подтверждается (COMMITTED), и сумма остаётся учтённой в лимитах.
- БП-44: Если итоговый статус CANCELLED или DENIED, то резерв снимается (RELEASED). Сначала счётчики приводятся к текущей дате (БП-34, БП-35). Затем сумма возвращается в дневной лимит, только если резерв сделан сегодня, и в месячный, только если резерв сделан в текущем месяце. Использованная сумма не может стать отрицательной.
- БП-45: Если итоговый статус не COMPLETED, не CANCELLED и не DENIED, то резерв не меняется, в журнал пишется предупреждение.

**Данные:**
- Читается: `reservations` (по `transfer_id`: `decision`, `reason`, `state`, `amount`, `reserved_on`, `sender_id`); `sender_usage` (по `sender_id`).
- Изменяется:
  - `sender_usage`: `daily_used`, `monthly_used`, `last_daily_reset`, `last_monthly_reset`, `version`. Запись создаётся для нового отправителя.
  - `reservations`: создаётся с полями `transfer_id`, `sender_id`, `amount`, `decision`, `reason`, `state`, `reserved_on`, `created_at`, `updated_at`; при закрытии меняются `state` и `updated_at`.
- Настройки: `limits.daily-max` = 50000.00, `limits.monthly-max` = 200000.00 (`application.yml`).
- Отправляется: ответ сервиса лимитов (APPROVED / DECLINED, инициатор limit, причина).

**Исходы:**
- Ветка А:
  - APPROVED: сумма зарезервирована (RESERVED) и учтена в дневном и месячном лимите.
  - DECLINED с причиной DAILY_LIMIT_EXCEEDED, MONTHLY_LIMIT_EXCEEDED или INVALID_AMOUNT: резерва нет.
  - Ещё раз отправлено ранее сохранённое решение.
  - Ошибка (база данных, конфликт версий, не удалось отправить): ещё до 3 попыток, затем очередь неразобранных. Если не удалась отправка, решение остаётся сохранённым, а резерв — в RESERVED без итога (см. АН-02).
- Ветка Б:
  - Резерв подтверждён (COMMITTED).
  - Резерв снят (RELEASED): сумма возвращена полностью, частично (только в месячный лимит) или не возвращена вовсе, в зависимости от даты резерва.
  - Событие пропущено: решения нет, резерв не в RESERVED или статус неизвестный.
  - Ошибка (нет учёта отправителя, сбой базы данных): ещё до 3 попыток, затем очередь неразобранных. Резерв остаётся в RESERVED, хотя перевод уже отменён (см. АН-05).

## Сервис проверки отправителя

### ТВ-7. Проверка отправителя по списку заблокированных

**ТОЧКА ВХОДА:** `TransferEventsListener.onEvent()` (screening-service). Работа выполняется в `ScreeningService.onNewTransfer()` и `ScreeningJournal.check()`.

**Триггер:** событие из общего потока переводов (`transfers`). Обрабатывается только статус NEW. Итоговые статусы только записываются в журнал.

**Алгоритм:**
1. Если статус не NEW, записать в журнал, что резервов у проверки нет и действий не требуется, и завершить обработку.
2. Проверить, проводилась ли уже проверка этого перевода. Если да, взять сохранённый результат и перейти к шагу 5.
3. Найти отправителя в списке заблокированных.
4. Если отправитель найден, результат DECLINED с причиной SENDER_BLOCKED, иначе APPROVED без причины. Сохранить результат в журнал проверок вместе со временем проверки.
5. Отправить результат на сведение решений (инициатор screening) и до 10 секунд ждать подтверждения. Если отправить не удалось, обработка считается неуспешной (БП-51), а сохранённый результат не отменяется.

Получатель, сумма и валюта не проверяются. Ведения списка заблокированных (добавления и снятия блокировки) в коде не найдено: список только заполняется при развёртывании (см. АН-06 – АН-08).

**Бизнес-правила:**
- БП-46: Если пришло событие со статусом NEW, то проверяется отправитель. При любом другом статусе ничего не делается.
- БП-47: Если этот перевод уже проверялся, то ещё раз отправляется сохранённый результат без повторной сверки со списком.
- БП-48: Если отправитель есть в списке заблокированных, то результат DECLINED с причиной SENDER_BLOCKED.
- БП-49: Если отправителя в списке нет, то результат APPROVED без причины.
- БП-50: Если результат проверки получен, то он сохраняется в журнал проверок и отправляется на сведение решений с инициатором screening. Если отправить не удалось за 10 секунд, обработка события считается неуспешной (БП-51), а сохранённый результат остаётся.

**Данные:**
- Читается: `screening_checks` (по `transfer_id`); `blocked_senders` (по `sender_id`). Причина и дата блокировки в решении не используются.
- Создаётся: `screening_checks` (`transfer_id`, `sender_id`, `result`, `reason`, `checked_at`).
- Исходное содержимое `blocked_senders` (`002-insert-test-data.sql`): отправители 5 (Fraud detected), 13 (Sanctions list), 21 (Suspicious activity), 34 (Identity theft report), 42 (Court order).
- Отправляется: результат проверки (APPROVED / DECLINED, инициатор screening, причина).

**Исходы:**
- APPROVED: отправитель не заблокирован.
- DECLINED с причиной SENDER_BLOCKED.
- Ещё раз отправлен сохранённый результат.
- Пришёл итоговый статус: действий нет, только запись в журнал.
- Ошибка (база данных, не удалось отправить): ещё до 3 попыток, затем очередь неразобранных. Перевод остаётся в NEW (см. АН-02).

## Общие правила обработки входящих сообщений (ТВ-5, ТВ-6, ТВ-7)

Правила заданы в `KafkaErrorHandlingConfig.kafkaErrorHandler()`, своя копия есть в каждом сервисе, и в настройках чтения сообщений в `application.yml`.

- БП-51: Если обработка входящего сообщения завершилась ошибкой, то она повторяется ещё до 3 раз с паузой 1 секунда. Если все 4 попытки не удались, сообщение уходит в очередь неразобранных («<имя потока>.DLT») и система переходит к следующему сообщению. Если и в очередь неразобранных сообщение передать не удалось, оно пропускается без следа.
- БП-52: Если входящее сообщение невозможно прочитать (нарушен формат), то оно сразу, без повторов, уходит в очередь неразобранных.

Разбора очереди неразобранных сообщений, их повторной обработки и оповещения о них в коде не найдено. Задач по расписанию (контроль зависших переводов, снятие просроченных резервов, сверки) в коде тоже не найдено.

### АН-01. Итоговое решение теряется, если ответы проверок разошлись больше чем на 10 секунд
- **Описание:** итоговое решение формируется, только если ответы сервиса лимитов и сервиса проверки отправителя отправлены с разницей не больше 10 секунд. Опоздавшие ответы не принимаются. Если окно пропущено, решение не формируется никогда (БП-16).
- **Сценарий:** сервис проверки отправителя перезапускается дольше 10 секунд или временно недоступен, а сервис лимитов отвечает сразу. После восстановления проверка отвечает по всем накопившимся переводам с текущим временем, и разница с ответом лимитов больше 10 секунд. Тот же результат даёт задержка в одном сервисе: медленная база данных, повторы обработки (до 3 раз по 1 с) вместе с ожиданием подтверждения отправки до 10 с, отставание в обработке очереди событий.
- **Последствие для бизнеса:**
  - Перевод навсегда остаётся в NEW, клиент не получает результата.
  - Если лимиты одобрили перевод, сумма висит в резерве (RESERVED). Она занимает дневной лимит до конца суток и месячный до конца месяца, резерв не подтверждается и не снимается. Последующие законные переводы клиента могут получить отказ по лимиту.
  - В карточке перевода видны ответы обеих проверок (этапы LIMIT и SCREENING), а итога нет. Это вводит в заблуждение поддержку.
  - При сбое страдают все переводы, созданные за время сбоя.
- **Серьёзность:** критичная.
- **Затронутые сервисы:** переводов, лимитов, проверки отправителя.
- **Где в коде:** transfer-service, `config/DecisionTopologyConfig.java`, `DecisionTopologyConfig.decisionStream()` (окно 10 с без допуска опоздания).

### АН-02. Нет механизма, который доводит зависший перевод до итога
- **Описание:** у ожидания решения нет ограничения по времени. Нет задач по расписанию, автоматической повторной отправки перевода на проверки и срока действия резерва. Довести перевод до итога можно, только если клиент повторит заявку с тем же идентификатором (БП-8). Подсказку об этом клиент получает лишь при ответе 503.
- **Сценарий:**
  - (а) При создании пришёл ответ 503, а клиент не повторил запрос или повторил с новым идентификатором. Первый перевод навсегда остаётся в NEW и на проверки так и не ушёл.
  - (б) Решение не сформировано (АН-01).
  - (в) Сервис лимитов или проверки 4 раза подряд не смог обработать новый перевод (сбой базы данных, сбой отправки ответа), и событие ушло в очередь неразобранных.
  - (г) Итоговый статус не применён в сервисе переводов (АН-05).
- **Последствие для бизнеса:** в списке копятся «вечные» переводы в NEW. Зависшие резервы уменьшают доступный клиенту лимит. Отчётность по переводам и резервам недостоверна. Разбирать такие случаи приходится вручную, без инструментов.
- **Серьёзность:** критичная.
- **Затронутые сервисы:** все.
- **Где в коде:**
  - transfer-service: `TransferController.create()` и `TransferController.publishNew()` — регистрация перевода и отправка на проверки не связаны;
  - limit-service: `LimitService.onNewTransfer()`;
  - screening-service: `ScreeningService.onNewTransfer()`;
  - `KafkaErrorHandlingConfig.kafkaErrorHandler()` во всех трёх сервисах.

  Задач по расписанию в коде не найдено.

### АН-03. Лимиты считаются без учёта валюты
- **Описание:** дневной (50 000,00) и месячный (200 000,00) лимиты сравниваются с номинальной суммой перевода без учёта валюты. Суммы в разных валютах складываются в один счётчик. При этом принимается любая валюта (АН-17).
- **Сценарий:** клиент переводит 50 000 USD, и перевод одобряется так же, как 50 000 RUB. Другой случай: клиент в один день переводит 30 000 RUB и 30 000 EUR, второй перевод отклоняется с DAILY_LIMIT_EXCEEDED, потому что рубли и евро сложены как одинаковые единицы.
- **Последствие для бизнеса:** если лимиты задуманы в рублях (по умолчанию валюта RUB), переводы в иностранной валюте фактически превышают лимит в десятки раз. Это финансовый и регуляторный риск. При смешанных валютах возможны необоснованные отказы.
- **Серьёзность:** критичная. Требует уточнения, в какой валюте задуманы лимиты.
- **Затронутые сервисы:** лимитов, переводов.
- **Где в коде:** limit-service, `LimitLedger.decide()`, `SenderUsage.reserve()`; transfer-service, `TransferRequest`.

### АН-04. Нет проверки полномочий инициатора и разграничения доступа
- **Описание:** в коде не найдено проверки, что инициатор запроса вправе распоряжаться средствами указанного отправителя. Отправитель берётся из тела запроса как есть. Разграничения доступа к сведениям о переводах тоже нет: список и карточки доступны любому, кто обратится к сервису.
- **Сценарий:**
  - (а) Посторонний создаёт переводы от имени отправителя X, и при соблюдении лимитов они получают COMPLETED.
  - (б) Посторонний исчерпывает дневной или месячный лимит X переводами на 50 000. После этого законные переводы X отклоняются с DAILY_LIMIT_EXCEEDED или MONTHLY_LIMIT_EXCEEDED.
  - (в) Любой получает список всех переводов всех клиентов: суммы, отправители, получатели.
- **Последствие для бизнеса:** несанкционированные переводы, отказ в обслуживании законному клиенту, раскрытие конфиденциальных данных.
- **Серьёзность:** критичная, если такой контроль не выполняется за пределами сервиса. Требует уточнения.
- **Затронутые сервисы:** переводов; последствия затрагивают лимиты.
- **Где в коде:** transfer-service, `TransferController.create()`, `TransferController.all()`, `TransferController.getById()`.

### АН-05. Сообщения из очереди неразобранных не обрабатываются, состояния сервисов расходятся
- **Описание:** сообщение, которое не удалось обработать за 4 попытки, уходит в очередь неразобранных, и дальше его никто не обрабатывает (в коде не найдено). Если не удалось и это, сообщение пропускается без следа: результат передачи в очередь неразобранных не контролируется. Шаги в разных сервисах выполняются независимо, поэтому состояния расходятся.
- **Сценарий:**
  - (а) Когда приходит итоговый статус CANCELLED, недоступна база сервиса лимитов. Перевод отменён, а резерв остаётся RESERVED. Повторная заявка клиента не поможет: перевод уже не в NEW, повторной отправки не будет. Сумма занимает лимит до конца дня и месяца.
  - (б) Когда приходит итоговый статус, недоступна база сервиса переводов. Перевод остаётся в NEW, а резерв в сервисе лимитов уже COMMITTED или RELEASED. Исправить это можно только повторной заявкой клиента.
  - (в) Не записался ответ проверки, и в истории нет этапа LIMIT или SCREENING.
- **Последствие для бизнеса:** доступный клиенту лимит несправедливо уменьшен. Статус, который видит клиент, не совпадает с фактическим итогом. История неполная. Без ручного вмешательства ничего из этого не исправляется.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** все.
- **Где в коде:** `KafkaErrorHandlingConfig.kafkaErrorHandler()` в каждом сервисе; limit-service, `LimitLedger.settle()`; transfer-service, `TransferTrackingService.applyFinalStatus()`, `TransferTrackingService.recordServiceResult()`.

### АН-06. Тестовые блокировки отправителей попадают во все окружения
- **Описание:** миграция базы сервиса проверки, названная «тестовые данные», вносит в список заблокированных отправителей 5, 13, 21, 34 и 42. Ограничения по окружению у неё нет.
- **Сценарий:** при развёртывании в рабочем окружении клиенты с этими идентификаторами получают отказ SENDER_BLOCKED по всем переводам.
- **Последствие для бизнеса:** законным клиентам отказывают, а реальным людям приписываются причины блокировки вроде «Sanctions list» и «Court order».
- **Серьёзность:** средняя.

### АН-07. Список блокировок нельзя вести, блокировка бессрочная
- **Описание:** точки входа для ведения списка заблокированных нет. Добавить или снять блокировку можно только прямым изменением базы данных. Дата блокировки хранится, но не используется: срока действия у блокировки нет, история изменений не ведётся.
- **Сценарий:** мошенника выявили, но заблокировать его штатными средствами нельзя. Ошибочная блокировка или блокировка по отменённому решению суда тоже не снимается.
- **Последствие для бизнеса:** на мошенничество система реагирует с задержкой, список меняют вручную без контроля и следа.
- **Серьёзность:** средняя.
- **Затронутые сервисы:** проверки отправителя.
- **Где в коде:** screening-service, `BlockedSenderRepository` (умеет только искать), `ScreeningJournal.check()`. Точки входа для ведения списка в коде не найдено.

### АН-08. Получатель не проверяется
- **Описание:** со списком заблокированных сверяется только отправитель. Получатель не проверяется, сумма и валюта в проверке не участвуют.
- **Сценарий:** клиент переводит деньги получателю 13 (в списке с причиной «Sanctions list»). Проверка одобряет перевод, и при соблюдении лимитов он получает COMPLETED.
- **Последствие для бизнеса:** возможны переводы в пользу лиц из санкционного списка или под судебным запретом. Это регуляторный риск.
- **Серьёзность:** средняя. Требует уточнения, должен ли проверяться получатель.
- **Затронутые сервисы:** проверки отправителя.
- **Где в коде:** screening-service, `ScreeningJournal.check()`.

### АН-09. Повторная заявка по зависшему переводу получает устаревшие решения
- **Описание:** на повторное событие о том же переводе сервисы лимитов и проверки возвращают сохранённое решение без пересчёта (БП-31, БП-47), а сервис переводов по повторной заявке снова отправляет перевод на проверки (БП-8). Поэтому решение, принятое однажды, применяется через любое время. Параметры повторного события с сохранёнными не сверяются. Для заявок это закрыто правилом БП-6, а для событий, пришедших другим путём, — нет.
- **Сценарий:**
  - (а) Перевод завис (АН-01), после этого отправителя заблокировали. Клиент повторяет заявку, проверка возвращает сохранённое APPROVED, и перевод получает COMPLETED, хотя отправитель уже в списке.
  - (б) Перевод отклонён по дневному лимиту, но итог не сформировался. На следующий день клиент повторяет заявку и снова получает DECLINED DAILY_LIMIT_EXCEEDED, хотя лимит уже восстановился. Чтобы провести перевод, нужно создавать новый с новым идентификатором.
- **Последствие для бизнеса:** заблокированный отправитель может провести перевод; клиент получает необоснованный отказ.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** лимитов, проверки отправителя, переводов.
- **Где в коде:** limit-service, `LimitLedger.decide()`; screening-service, `ScreeningJournal.check()`; transfer-service, `TransferController.duplicate()`.

### АН-10. Отказы классифицируются несогласованно
- **Описание:** если отказали обе проверки, статус DENIED и инициатор не указывается. Если отказала одна, статус CANCELLED с инициатором. Технический сбой (неожиданный ответ проверки) тоже даёт CANCELLED, как и обычный отказ, и различить их можно только по тексту пояснения. Кроме того, CANCELLED обычно означает отмену клиентом, а здесь это отказ системы.
- **Сценарий:** отправитель из санкционного списка получает CANCELLED с инициатором screening, если лимит не превышен, и DENIED без инициатора, если превышен. Один и тот же факт блокировки даёт два разных статуса.
- **Последствие для бизнеса:** отчётность по причинам отказов искажена, клиенту сообщают неточную причину, разбирать случаи сложнее.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** переводов.
- **Где в коде:** transfer-service, `TransferDecisionService.decide()`.

### АН-11. По одному переводу возникают дублирующие итоговые решения
- **Описание:** событие о новом переводе уходит на проверки несколько раз в трёх случаях: повторная заявка по переводу в NEW (БП-8), две одновременные одинаковые заявки (БП-11), ответ 503 при событии, которое на самом деле дошло (ожидание подтверждения — 10 с, предельное время доставки тоже 10 с). Каждая проверка снова отправляет сохранённый ответ, а сведение формирует решение на каждую пару ответов (ТР-3, строка 5).
- **Сценарий:** клиент за 10 секунд дважды повторяет заявку. Каждая проверка отвечает 2–3 раза, и получается до 9 одинаковых итоговых статусов.
- **Последствие для бизнеса:** лишняя нагрузка и повторы в журналах. Итог не искажается: повторные итоги пропускаются (БП-28, БП-42).
- **Серьёзность:** низкая.
- **Затронутые сервисы:** все.
- **Где в коде:** transfer-service, `TransferController.duplicate()`, `TransferController.publishNew()`, `DecisionTopologyConfig.decisionStream()`.

### АН-12. Итоговый статус может перезаписаться при параллельной обработке
- **Описание:** записывая ответ проверки, сервис переводов сохраняет перевод целиком, вместе со статусом, а контроля версий у перевода нет. Если ответ проверки и итоговый статус по одному переводу обрабатываются одновременно, запись ответа может вернуть статус NEW поверх только что применённого итога. Этап FINAL в истории к этому моменту уже есть, поэтому все повторные итоги пропускаются (БП-28).
- **Сценарий:** возможно, если запущено несколько экземпляров сервиса переводов или сообщения обрабатываются параллельно. Ответы проверок и итоговые статусы идут разными потоками и могут попасть в разные экземпляры одновременно. В текущей конфигурации (один экземпляр, последовательная обработка) не проявляется.
- **Последствие для бизнеса:** перевод навсегда показывает NEW, хотя в истории есть итог, а резерв в сервисе лимитов уже закрыт.
- **Серьёзность:** низкая, проявляется только при нескольких экземплярах.
- **Затронутые сервисы:** переводов.
- **Где в коде:** transfer-service, `TransferTrackingService.recordServiceResult()`, `TransferTrackingService.applyFinalStatus()`, `TransferEntity` (нет контроля версий).

### АН-13. Границы суток и месяца берутся по часам сервера, лимит учитывается в день решения
- **Описание:** «сегодня» и «текущий месяц» определяются по системным часам и часовому поясу сервера лимитов. Часовой пояс явно не задан (требует уточнения). Сумма идёт в лимит того дня, когда сервис лимитов принял решение, а не того, когда создан перевод. Счётчик обнуляется при любом расхождении дат, в том числе когда часы уходят назад.
- **Сценарий:**
  - (а) Сервер работает по UTC, и для клиентов в Москве сутки лимита начинаются в 03:00.
  - (б) Перевод создан 31 января в 23:59:59, решение принято 1 февраля, и сумма учтена в лимитах февраля.
  - (в) Часы сервера перевели на сутки назад. Дневной счётчик обнуляется, и при возврате часов обнуляется ещё раз: клиент получает лишний дневной лимит.
- **Последствие для бизнеса:** поведение лимитов расходится с ожиданиями клиента и, возможно, с требованиями; при сбое часов лимит можно превысить.
- **Серьёзность:** низкая (требует уточнения).
- **Затронутые сервисы:** лимитов.
- **Где в коде:** limit-service, `LimitLedger.decide()`, `LimitLedger.settle()`, `SenderUsage.lazyReset()`.

### АН-14. Нештатные сообщения отбрасываются без следа, итоговым считается любой статус
- **Описание:** часть сообщений только пишется в журнал и пропускается, в очередь неразобранных они не попадают:
  - ответы проверок и итоговые статусы по неизвестному переводу;
  - итоговые статусы без решения по лимитам;
  - итоговые статусы с неизвестным значением.

  Кроме того, сервис переводов считает итоговым любой статус, кроме NEW (например, APPROVED), и не сверяет его с допустимыми COMPLETED, CANCELLED и DENIED. Сервис лимитов при таком статусе резерв не трогает.
- **Сценарий:** в общий поток переводов попало событие со статусом APPROVED, например из-за ошибки смежной системы или ручной публикации. Перевод получает итоговый статус APPROVED, которого нет в описании API, а резерв навсегда остаётся RESERVED.
- **Последствие для бизнеса:** у переводов появляются недопустимые статусы, резервы зависают, сведения о сбоях теряются.
- **Серьёзность:** низкая: текущий код таких сообщений не порождает.
- **Затронутые сервисы:** переводов, лимитов.
- **Где в коде:** transfer-service, `TransferEventListener.onEvent()`, `TransferTrackingService.applyFinalStatus()`, `TransferTrackingService.recordServiceResult()`; limit-service, `LimitLedger.settle()`.

### АН-15. Отказ INVALID_AMOUNT сохраняется с суммой 0
- **Описание:** при отказе из-за некорректной суммы в журнал резервов пишется 0 вместо фактической суммы.
- **Сценарий:** приходит событие о новом переводе с отрицательной суммой. Через заявку это невозможно (БП-2), только через сообщение, пришедшее другим путём. В журнале резервов остаётся сумма 0.
- **Последствие для бизнеса:** при разборе инцидента не хватает сведений.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** лимитов.
- **Где в коде:** limit-service, `LimitLedger.decide()`.

### АН-16. Ветка снятия резерва при DENIED недостижима
- **Описание:** снятие резерва предусмотрено и для итогового статуса DENIED. Но DENIED формируется только при отказе сервиса лимитов, а тогда резерва нет (NONE). Сработать ветка может только на нештатных данных.
- **Сценарий:** при штатной работе не проявляется.
- **Последствие для бизнеса:** прямого ущерба нет, но несогласованные правила мешают понимать и сопровождать систему.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** лимитов.
- **Где в коде:** limit-service, `LimitLedger.settle()`, в связке с transfer-service, `TransferDecisionService.decide()`.

### АН-17. Заявка проверяется недостаточно
- **Описание:**
  - (а) Валютой считаются любые три заглавные латинские буквы («AAA», «ZZZ»), справочник валют не используется.
  - (б) Отправитель может совпадать с получателем.
  - (в) Идентификатор перевода назначает клиент, разрешены 0 и отрицательные значения. Уникальность между разными клиентами не обеспечена: если идентификатор занят чужим переводом, клиент получает отказ 409.
  - (г) Существование отправителя и получателя не проверяется (в коде не найдено).
- **Сценарий:** клиент создаёт перевод самому себе в несуществующей валюте «ZZZ», перевод проходит проверки, получает COMPLETED и расходует лимиты. Другой клиент получает 409 из-за чужого перевода с тем же идентификатором.
- **Последствие для бизнеса:** некорректные данные о переводах, напрасный расход лимитов, непонятные клиенту отказы.
- **Серьёзность:** низкая (требования требуют уточнения).
- **Затронутые сервисы:** переводов.
- **Где в коде:** transfer-service, `TransferRequest`, `TransferController.create()`, `TransferController.duplicate()`.

### АН-18. Список переводов отдаётся без постраничной выдачи
- **Описание:** все переводы возвращаются одним ответом, без ограничения количества и без фильтров.
- **Сценарий:** с ростом числа переводов ответ становится всё больше.
- **Последствие для бизнеса:** выдача списка замедляется и начинает сбоить, растёт нагрузка на базу данных. Вместе с АН-04 это означает массовое раскрытие данных.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** переводов.
- **Где в коде:** transfer-service, `TransferController.all()`, `TransferRepository.findAllByOrderByCreatedAtDesc()`.

### АН-19. История перевода показывается не в хронологическом порядке
- **Описание:** история упорядочена по этапам, а не по времени. Ответы проверок и итоговый статус приходят разными потоками, поэтому итог может записаться раньше ответов проверок.
- **Сценарий:** итоговый статус записан в 12:00:00.100, ответ лимитов — в 12:00:00.300. В карточке ответ лимитов стоит выше итога, и время в истории идёт назад.
- **Последствие для бизнеса:** путаница при разборе обращений клиентов.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** переводов.
- **Где в коде:** transfer-service, `TransferController.getById()`.

### АН-20. Поведение расходится с описанием API
- **Описание:** ответ 500 («Внутренняя ошибка сервера, повторите запрос позже») реально возвращается, но в описании API его нет ни у одного запроса. Ответ 404 приходит без тела, тогда как остальные ошибки возвращаются в формате описания проблемы.
- **Сценарий:** клиентская система, построенная строго по описанию API, не обрабатывает ответ 500 и не получает тела у 404.
- **Последствие для бизнеса:** ошибки на стороне клиентских систем при сбоях.
- **Серьёзность:** низкая.
- **Затронутые сервисы:** переводов.
- **Где в коде:** transfer-service, `openapi/transfer-api.yaml`, `ApiExceptionHandler.handleUnexpected()`, `TransferController.getById()`.

## Чего в коде нет: сводно

- Задач по расписанию нет: ни контроля зависших переводов, ни снятия просроченных резервов, ни сверок (АН-02).
- Разбора и повторной обработки очереди неразобранных сообщений нет (АН-05).
- Ведения списка заблокированных отправителей нет (АН-07).
- Проверки полномочий инициатора и разграничения доступа нет (АН-04).
- Проверки остатка средств и фактического списания или зачисления нет. Статус COMPLETED означает только, что обе проверки одобрили перевод. Где проводятся деньги, требует уточнения.
- Отмены перевода клиентом нет. Статус CANCELLED выставляет только система (АН-10).
- Уведомления клиента об итоговом решении нет: итог можно узнать только запросом перевода (ТВ-3).
- Индивидуальных лимитов нет: лимиты одинаковы для всех отправителей и валют (БП-36, БП-37, АН-03).
