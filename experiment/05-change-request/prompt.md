К сообщению приложен исходный код проекта: все файлы в одном
текстовом файле, каждый файл начинается со строки
«===== FILE: путь =====». Изучи все файлы.

Поступила задача от бизнеса:

"Сейчас для всех отправителей есть только дневной и месячный лимит на общую сумму 
переводов. Но нет ограничения на сумму одного перевода — отправитель может 
совершить один перевод на всю сумму дневного лимита. 

Нужно:
1. Добавить для всех отправителей настройку «максимальная сумма одного 
   перевода». Если сумма перевода превышает этот порог — отклонять с 
   понятной причиной.
2. Добавить REST API для управления лимитами: просмотр 
   значений всех лимитов, 
   изменение лимитов (дневной, месячный, максимальная сумма одного перевода)."

На основе анализа кода составь ПОСТАНОВКУ НА ДОРАБОТКУ
в следующем формате:

---

## 1. ЦЕЛЬ ДОРАБОТКИ
Краткое описание того, что должно измениться с точки зрения бизнеса (2–3 предложения).

## 2. ПРЕДПОСЫЛКИ
Почему доработка нужна: какое ограничение текущей системы она устраняет.

## 3. SCOPE ИЗМЕНЕНИЙ
Перечисли все затронутые компоненты: сервисы, таблицы БД,
контракты сообщений, API. Для каждого — одна строка с описанием
характера изменения (новый / модифицируемый).

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ
Если доработка требует выбора между несколькими вариантами
реализации (например, в каком сервисе разместить новый функционал) —
опиши варианты, плюсы и минусы каждого, и укажи рекомендуемый.

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

Разбей по сервисам. Для каждого сервиса — отдельная секция:

### 5.1. [имя сервиса]

Изменения в БД:
- Какие таблицы/колонки добавить или изменить
- Ограничения (NOT NULL, default, допустимые значения)
- Миграция тестовых данных (если нужна)

Изменения в API (если есть):
- Новые или изменённые эндпоинты, для каждого — в формате:

  Эндпоинт: [HTTP-метод] [URL]
  Описание: [одно предложение]

  Параметры запроса:
  | Параметр | Источник (body/path/query) | Тип | Обязательный | Описание |

  Параметры ответа:
  | Поле | Тип | Nullable | Описание |

  Коды ответа:
  | Код | Условие |

Изменения в бизнес-логике:
- Какие новые правила должны быть реализованы
- Какие существующие правила затрагиваются
- Формат: "При [условие] система должна [действие]"

Изменения в контрактах сообщений (если есть):
- Новые значения полей, новые статусы, новые причины отклонения

### 5.2. [следующий сервис]
...

Для сервисов без изменений — одна строка «изменений нет» с кратким обоснованием.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ
Если в текущем коде есть баги или аномалии, которые могут повлиять
на реализацию данной доработки — перечисли их и опиши, как
они связаны с задачей.

## 7. КРИТЕРИИ ПРИЁМКИ
Тест-кейсы в формате «условие → ожидаемый результат», включая
граничные значения.

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ
Что в задаче не определено и требует решения бизнеса до начала
разработки.

---

Правила:
- Постановка пишется для разработчика, который знает проект.
  Не нужно объяснять, как устроена система и как работают
  используемые фреймворки и брокеры.
- Уровень детализации: ЧТО нужно сделать, а не КАК.
  Не указывай конкретные классы и методы для изменения, не пиши
  псевдокод. Имена таблиц, колонок, полей API и кодов причин
  отклонения — предлагай: это часть контракта. Имена классов,
  методов и переменных — нет. Разработчик сам решает, как реализовать.
- Ссылки на существующий код как обоснование (файл, класс/метод) — допустимы, в скобках. Запрещено предписывать, какие классы и методы менять.
- Не дублируй описание текущей архитектуры — разработчик её знает.

Общие правила:
- Опирайся только на приложенный код. Не додумывай и не дополняй
  по аналогии с другими проектами.
- Если чего-то в коде нет или это нельзя определить — так и пиши:
  «в коде не найдено» или «требует уточнения».
- Ссылаясь на код, указывай файл и класс/метод, а не номер строки.
- Отвечай на русском языке.
- Не используй поиск в интернете и другие внешние источники:
  вся нужная информация — в приложенном коде.
