Разберу приложенный код и соберу постановку на доработку отдельным документом — строго по вашему шаблону.

Claude Docs в режиме инкогнито создавать и менять нельзя — они остаются в аккаунте после завершения чата (в новом чате без инкогнито это доступно), поэтому постановка целиком ниже.

---

## 1. ЦЕЛЬ ДОРАБОТКИ

К дневному и месячному лимитам добавляется третий — максимальная сумма одного перевода, единая для всех отправителей. Перевод на сумму выше порога отклоняется с отдельной причиной. Все три лимита становятся управляемыми через REST API: значения можно посмотреть и изменить без правки конфигурации и перезапуска сервиса.

## 2. ПРЕДПОСЫЛКИ

- **Нет ограничения на сумму одного перевода.** Проверяются только накопленные суммы за день и месяц (limit-service, `LimitLedger.decide`). Сама сумма ограничена лишь условием «больше нуля» (`INVALID_AMOUNT`) и техническим максимумом 9999999999999.99 (`TransferRequest`). Отправитель без использования лимита может одним переводом выбрать весь дневной лимит — 50000.00.
- **Лимиты меняются только через конфигурацию и перезапуск.** Значения заданы параметрами `limits.daily-max: 50000.00` и `limits.monthly-max: 200000.00` (limit-service, `application.yml`) и считываются при старте (`LimitLedger`, поля с `@Value`).
- **Лимиты нельзя посмотреть или изменить через API.** У limit-service нет HTTP-интерфейса (`limit-service/pom.xml` — без web-стартера; в `docker-compose.yml` у сервиса нет портов). API transfer-service (`transfer-api.yaml`) операций с лимитами не содержит.

| Компонент | Характер | Суть изменения |

| `docker-compose.yml` | модифицируемый | Публикация HTTP-порта limit-service |

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

**4.1. Где хранить значения лимитов**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Таблица в БД limit-service — рекомендуется** | Значение меняется без перезапуска и сохраняется после него; едино для всех экземпляров сервиса; лежит в той же БД, где принимается решение | Новая таблица и миграция; каждое решение зависит от чтения настроек (см. 6.5) |
| B. Параметры `limits.*` + изменение значения в памяти сервиса | Минимум изменений | Изменение теряется при перезапуске и расходится между экземплярами — «изменение через API» по сути не выполняется |
| C. Хранить в transfer-service и передавать значения в сообщении `Transfer` | REST API остаётся в одном сервисе | Меняется контракт `Transfer` для всех сервисов; лимит хранится не там, где применяется |

При варианте A значения берутся из БД при каждом решении, поэтому изменение действует со следующего обрабатываемого перевода.

**4.2. В каком сервисе разместить REST API управления лимитами**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. limit-service — рекомендуется** | API работает с данными своего сервиса; изменение и проверка идут над одной БД, без синхронизации и задержки | У сервиса нет HTTP: нужны web-слой, порт, обработка ошибок и OpenAPI; в системе появляется вторая точка входа REST |
| B. transfer-service + передача настроек в limit-service через новый топик Kafka | Одна точка входа (8080); готовы web-слой, обработка ошибок (`ApiExceptionHandler`) и OpenAPI | Новый топик и контракт; `GET` может показать значение, которое limit-service ещё не применил; две копии настроек; несвойственная transfer-service ответственность |
| C. transfer-service как прокси с синхронным вызовом limit-service | Одна точка входа | HTTP в limit-service всё равно нужен, плюс HTTP-клиент; синхронных межсервисных вызовов в проекте сейчас нет |

**4.3. Где отклонять перевод, превышающий максимальную сумму**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. В limit-service, вместе с дневным и месячным лимитом — рекомендуется** | Все лимиты ведут себя одинаково; `Transfer` и transfer-service не меняются; отказ фиксируется в истории перевода | Клиент узнаёт об отказе из итогового статуса перевода, а не из ответа `POST /transfers` (201, `NEW`) |
| B. Синхронно в transfer-service при `POST /transfers` (ответ 4xx) | Немедленный отказ | transfer-service должен знать значение лимита; перевод не создаётся и отказ не попадает в историю; поведение отличается от остальных лимитов |

Выбор варианта A нужно подтвердить у бизнеса (вопрос 5).

**4.4. Модель настроек и форма API**

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Один ресурс `/limits` с тремя полями; в БД одна строка с тремя колонками — рекомендуется** | Несколько лимитов меняются одним атомарным запросом; просто проверять соотношение лимитов между собой | Новый вид лимита потребует новой колонки и поля |
| B. Ресурс на каждый вид лимита (`/limits/{type}`); в БД строка на вид лимита | Новый вид лимита добавляется без изменения схемы | Нет атомарного изменения нескольких лимитов; при проверке соотношений важен порядок вызовов |

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. limit-service

**Изменения в БД**

Новая таблица `limit_settings` — единственная строка с действующими значениями лимитов.

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | SMALLINT | PK; допустимо только значение 1 | Гарантия единственной строки |
| `daily_max` | DECIMAL(15,2) | NOT NULL; > 0 | Дневной лимит на общую сумму переводов отправителя |
| `monthly_max` | DECIMAL(15,2) | NOT NULL; > 0 | Месячный лимит на общую сумму переводов отправителя |
| `single_transfer_max` | DECIMAL(15,2) | NOT NULL; > 0 | Максимальная сумма одного перевода |
| `updated_at` | TIMESTAMP | NOT NULL | Время последнего изменения лимитов |

- Тип сумм совпадает с существующими колонками (`sender_usage.daily_used`, `reservations.amount` в `001-create-tables.sql`). Default у колонок лимитов не задаётся.
- Начальные значения вносятся миграцией (это обязательные данные, не тестовые):
  - `daily_max = 50000.00`, `monthly_max = 200000.00` — текущие `limits.daily-max` и `limits.monthly-max`;
  - `single_transfer_max = 50000.00` — предложение: равно начальному `daily_max`, чтобы выпуск не вводил нового ограничения до решения бизнеса (вопрос 1);
  - `updated_at` — момент миграции.
- Переопределяются ли `limits.*` на стендах внешней конфигурацией — в коде не найдено (`docker-compose.yml` и `application-docker.yml` их не переопределяют). Требует уточнения перед миграцией.
- Структура `reservations` и `sender_usage` не меняется. `reservations.reason` (VARCHAR(50)) вмещает новый код (30 символов). Перенос существующих данных не нужен.
- Миграция тестовых данных не нужна: в limit-service их нет (`changelog-master.yaml` подключает только `001-create-tables.sql`).

**Изменения в API**

Оба эндпоинта новые. Общие правила:

- Суммы — JSON-числа с точностью до 2 знаков, как `amount` в `transfer-api.yaml`.
- Ошибки — в формате `application/problem+json`, как в transfer-service (схема `Problem` в `transfer-api.yaml`).
- Аутентификация не предусмотрена: в проекте её нет ни в одном сервисе (см. 6.4, вопрос 7).

Эндпоинт: GET /limits
Описание: Возвращает действующие значения всех лимитов.

Параметры запроса: нет.

Параметры ответа:

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | number (decimal) | нет | Дневной лимит на общую сумму переводов отправителя |
| `monthlyMax` | number (decimal) | нет | Месячный лимит на общую сумму переводов отправителя |
| `singleTransferMax` | number (decimal) | нет | Максимальная сумма одного перевода |
| `updatedAt` | string (дата-время, формат как у `createdAt` перевода) | нет | Время последнего изменения лимитов |

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Значения возвращены |
| 500 | Внутренняя ошибка сервиса |

Эндпоинт: PATCH /limits
Описание: Изменяет один или несколько лимитов; непереданные лимиты сохраняют текущие значения.

Параметры запроса:

| Параметр | Источник (body/path/query) | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `dailyMax` | body | number (decimal) | нет* | Новый дневной лимит |
| `monthlyMax` | body | number (decimal) | нет* | Новый месячный лимит |
| `singleTransferMax` | body | number (decimal) | нет* | Новая максимальная сумма одного перевода |

\* В запросе должно быть хотя бы одно из трёх полей. Отсутствующее поле не изменяется; `null` — недопустимое значение.

Допустимые значения каждого поля: больше 0, не более 13 цифр в целой части и 2 в дробной (как у `amount` в `TransferRequest`), то есть до 9999999999999.99.

Параметры ответа (состояние после изменения):

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | number (decimal) | нет | Действующий дневной лимит |
| `monthlyMax` | number (decimal) | нет | Действующий месячный лимит |
| `singleTransferMax` | number (decimal) | нет | Действующая максимальная сумма одного перевода |
| `updatedAt` | string (дата-время) | нет | Время этого изменения |

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Изменение применено, в том числе если новые значения совпали с текущими |
| 400 | Тело не является корректным JSON; не передано ни одного из трёх полей; значение равно `null`, не является числом, ≤ 0, содержит более 2 знаков в дробной или более 13 цифр в целой части |
| 422 | Итоговые значения нарушают соотношение `singleTransferMax ≤ dailyMax ≤ monthlyMax` (правило — предложение, вопрос 10) |
| 500 | Внутренняя ошибка сервиса |

При ответах 400 и 422 ни одно значение не изменяется.

**Изменения в бизнес-логике**

Новые правила:

1. При получении нового перевода, сумма которого строго больше действующего `single_transfer_max`, система должна отклонить его: решение `DECLINED`, причина `SINGLE_TRANSFER_LIMIT_EXCEEDED`.
2. При сумме перевода, равной `single_transfer_max`, система должна пропустить перевод к проверкам дневного и месячного лимитов.
3. При нарушении нескольких ограничений сразу система должна вернуть одну причину — первую по порядку: `INVALID_AMOUNT` → максимальная сумма одного перевода → дневной лимит → месячный лимит. Порядок существующих проверок не меняется (`LimitLedger.decide`); место новой — предложение (вопрос 6).
4. При отклонении по новому правилу система не должна увеличивать использованные суммы отправителя и создавать резерв. Решение сохраняется так же, как прочие отказы по лимитам.
5. При повторном получении `NEW` по переводу с уже принятым решением система должна вернуть сохранённое решение, не перепроверяя его по текущим лимитам. Это существующее поведение, оно распространяется на новую причину.
6. При принятии каждого решения система должна использовать значения трёх лимитов, сохранённые на этот момент. Изменение через API действует со следующего решения, без перезапуска сервиса.
7. При изменении лимитов система не должна пересматривать ранее принятые решения и пересчитывать использованные суммы отправителей.
8. При уменьшении дневного или месячного лимита ниже уже использованной отправителем суммы система должна отклонять его следующие переводы с существующими причинами до очередного сброса использования. Ранее одобренные переводы не затрагиваются.
9. При запросе на изменение система должна применить все переданные значения атомарно: либо все, либо ни одного.
10. При запросе на изменение система должна проверить соотношение `singleTransferMax ≤ dailyMax ≤ monthlyMax` на итоговом наборе значений (переданные плюс сохранённые) и при нарушении отказать с кодом 422 (вопрос 10).
11. При параллельных запросах на изменение система не должна терять изменение одного лимита из-за одновременного изменения другого и не должна допускать состояния, нарушающего правило 10.
12. При каждом успешном изменении система должна обновить `updated_at` и записать в журнал приложения прежние и новые значения (расширенный аудит — вопрос 8).

Затрагиваемые существующие правила:

- Дневной и месячный лимиты: условие отклонения прежнее (использовано + сумма > лимит), меняется источник значений — `limit_settings` вместо `limits.daily-max` и `limits.monthly-max`.
- Обработка итоговых статусов не меняется: у перевода, отклонённого по новому правилу, резерва нет, освобождать нечего (`LimitLedger.settle`).

**Изменения в конфигурации и развёртывании**

- limit-service получает HTTP-порт; предлагается 8081, так как 8080 занят transfer-service (`docker-compose.yml`). Порт публикуется в `docker-compose.yml`.
- Параметры `limits.*` удаляются из `application.yml`, чтобы у лимитов не было двух источников.
- Для нового API добавляется OpenAPI-описание по образцу `transfer-service/src/main/resources/openapi/transfer-api.yaml`.

**Изменения в контрактах сообщений**

Структура `Transfer` и набор статусов не меняются. Появляется новое значение причины:

| Топик | `status` | `decidedBy` | `messageInfo` | Когда |
|---|---|---|---|---|
| `limit-results` | `DECLINED` | `limit` | `SINGLE_TRANSFER_LIMIT_EXCEEDED` | Сумма перевода больше `single_transfer_max` |
| `transfers` (итог) | `CANCELLED` | `limit` | `SINGLE_TRANSFER_LIMIT_EXCEEDED` | Отказ по новому правилу, screening одобрил |
| `transfers` (итог) | `DENIED` | `null` | `SINGLE_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED` | Отказ по новому правилу и отказ screening |

Итоговые сообщения формирует существующая логика transfer-service (`TransferDecisionService.decide`).

### 5.2. transfer-service

Изменений нет: причина отказа передаётся и сохраняется как строка без разбора (`TransferDecisionService.decide`, `TransferTrackingService.recordServiceResult` и `applyFinalStatus`). Колонки `message_info` имеют тип TEXT, а `messageInfo` в `transfer-api.yaml` — строка без перечня значений.

### 5.3. screening-service

Изменений нет: сервис не использует сумму перевода и лимиты (`ScreeningJournal.check` проверяет только `blocked_senders`).

### 5.4. transfer-common

Изменений нет: новая причина передаётся в существующем поле `messageInfo` записи `Transfer`.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

**6.1. Лимиты не учитывают валюту перевода.** `LimitLedger.decide` сравнивает с лимитом только `amount`; `Transfer.currency` в limit-service не используется, хотя `TransferRequest` принимает любую валюту формата `[A-Z]{3}` (по умолчанию RUB). Новый порог унаследует это: 10000 USD и 10000 RUB будут сравниваться с одним числом. Смысл лимита для переводов не в рублях не определён (вопрос 3); в постановке валюта не учитывается, как и сейчас.

**6.2. Причина отказа — технический код длиной до 50 символов.** `reservations.reason` имеет тип VARCHAR(50), все действующие причины — коды (`DAILY_LIMIT_EXCEEDED`, `MONTHLY_LIMIT_EXCEEDED`, `INVALID_AMOUNT`). «Понятная причина» в постановке — тоже код. Если бизнесу нужен развёрнутый текст или значение лимита в причине (вопрос 4), колонку придётся расширять; иначе сохранение решения завершится ошибкой и перевод попадёт в сценарий 6.5.

**6.3. При отказе обоих сервисов причины склеиваются, а `decidedBy` пуст.** Для статуса `DENIED` `messageInfo` собирается как «причина limit; причина screening», `decidedBy = null` (`TransferDecisionService.decide`). Новая причина не всегда приходит отдельным значением: потребитель, сравнивающий `messageInfo` на точное совпадение, её не распознает. Учтено в кейсе 4 раздела 7.

**6.4. В системе нет аутентификации и авторизации.** Ни в одном `pom.xml` нет зависимостей безопасности, `TransferController` открыт. `PATCH /limits` позволит изменить лимиты любому, у кого есть сетевой доступ к порту limit-service, а порт предлагается опубликовать (вопрос 7).

**6.5. Перевод навсегда остаётся в `NEW`, если limit-service не опубликовал решение.** Причин две:

- Ошибка обработки в limit-service после 3 повторных попыток уводит сообщение в `transfers.DLT` (`KafkaErrorHandlingConfig.kafkaErrorHandler`); обработчика DLT в коде не найдено.
- transfer-service формирует итог только при наличии обоих результатов в окне 10 секунд (`DecisionTopologyConfig.decisionStream`); механизма завершения перевода без одного из результатов в коде не найдено.

После доработки каждое решение зависит от чтения `limit_settings`: отсутствие строки или ошибка чтения приведут к «зависшим» переводам. Отсюда требования: строка создаётся миграцией, колонки NOT NULL, операции удаления настроек в API нет.

**6.6. Принятое решение по переводу не пересматривается (не ошибка, но влияет на ожидания).** При повторном `NEW` возвращается сохранённое решение (`LimitLedger.decide`), а повторный `POST /transfers` заново публикует `NEW` только для переводов в статусе `NEW` (`TransferController.duplicate`). Повышение лимита не «оживит» ранее отклонённый перевод — нужен новый перевод с новым `id`. Зафиксировано в правилах 5 и 7, вопрос 11.
