# Постановка на доработку: максимальная сумма одного перевода и REST API управления лимитами

## 1. ЦЕЛЬ ДОРАБОТКИ

Ввести единое для всех отправителей ограничение «максимальная сумма одного перевода»: перевод, сумма которого превышает порог, отклоняется с отдельной, однозначно распознаваемой причиной. Дать бизнесу REST API для просмотра и изменения всех трёх лимитов (дневного, месячного и максимальной суммы одного перевода), чтобы новые значения начинали действовать без правки конфигурации и перезапуска сервисов.

## 2. ПРЕДПОСЫЛКИ

1. **Сумма одного перевода не ограничена.** limit-service проверяет только накопительные лимиты: `daily_used + amount` сравнивается с дневным лимитом, `monthly_used + amount` — с месячным. Саму сумму он проверяет лишь на «больше нуля» (причина `INVALID_AMOUNT`) (`LimitLedger.java` → `decide`). transfer-service проверяет сумму только по формату: положительная, до 13 знаков целой части и 2 дробной, т. е. не больше 9999999999999.99 (`TransferRequest.java`). Поэтому один перевод на 50000.00, то есть на весь дневной лимит, одобряется.
2. **Лимиты заданы статической конфигурацией.** Значения записаны в `limit-service/src/main/resources/application.yml` (`limits.daily-max: 50000.00`, `limits.monthly-max: 200000.00`) и считываются один раз при старте сервиса (`LimitLedger.java`, поля с `@Value`). Посмотреть их можно только в конфигурации. Изменить — только правкой конфигурации и перезапуском limit-service, а перезапуск может «подвесить» переводы, которые в этот момент в обработке (см. 6.1). Значения никак не проверяются.
3. **API для лимитов нет.** limit-service работает только через Kafka, HTTP-слоя у него нет: в `limit-service/pom.xml` нет web-зависимостей, в `docker-compose.yml` порт limit-service не опубликован. Единственный REST API — `/transfers` в transfer-service — работает только с переводами.

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### 4.1. Где хранить значения лимитов

- **А. Оставить в `application.yml`, а через API менять значения в памяти процесса.**
  Плюсы: минимум изменений.
  Минусы: изменения теряются при перезапуске. При нескольких экземплярах limit-service значения расходятся: API изменит только тот экземпляр, который принял запрос. `GET` может показывать не то, что применяется на деле.
- **Б. Хранить в таблице БД limit-service (limitdb).**
  Плюсы: значения сохраняются после перезапуска; источник один для всех экземпляров; изменения действуют без перезапуска; корректность значений можно закрепить ограничениями БД.
  Минусы: нужна миграция с начальными значениями; настройки читаются при каждом решении.
- **В. Внешний сервис конфигурации с «горячим» обновлением.**
  Плюсы: типовой механизм управления настройками.
  Минусы: таких компонентов в проекте нет (в коде не найдено) — новая инфраструктура ради трёх значений. К тому же изменение, сделанное через REST API, всё равно нужно где-то сохранять.

**Рекомендуется вариант Б.**

### 4.2. В каком сервисе разместить REST API

- **А. В limit-service.**
  Плюсы: сервис владеет и данными, и логикой лимитов. API и проверка работают с одной таблицей, дублирования нет. Изменение действует уже на следующее решение. Новые топики и контракты не нужны. Административный API отделён от клиентского API переводов, поэтому доступ к нему проще ограничить сетевыми средствами — это важно, пока нет аутентификации (см. 6.5).
  Минусы: в limit-service нет HTTP-слоя. Понадобятся веб-слой, валидация запросов, обработка ошибок в формате ProblemDetail (как в transfer-service) и опубликованный порт. У системы появляется вторая HTTP-точка входа.
- **Б. В transfer-service; настройки хранятся в transferdb и доставляются в limit-service через новый компактный топик (например, `limit-settings`).**
  Плюсы: одна точка входа; используется готовая REST-инфраструктура transfer-service (обработчик ошибок, ProblemDetail, OpenAPI-описание).
  Минусы: логика лимитов расползается по двум сервисам, копий настроек становится две. Согласованность — только в конечном счёте: успешный ответ на `PUT` не гарантирует, что limit-service уже применяет новые значения, а `GET` показывает желаемые значения, а не применённые. Нужны новый топик (автосоздание топиков отключено — `KAFKA_AUTO_CREATE_TOPICS_ENABLE: "false"` в `docker-compose.yml`) и новый контракт. Пока Kafka недоступна, лимиты не изменить. Пока настройки не получены, limit-service не может принимать решения.
- **В. В transfer-service как прокси к внутреннему HTTP API limit-service.**
  Плюсы: одна точка входа.
  Минусы: HTTP-слой в limit-service нужен всё равно (как в варианте А), а сверху добавляются лишний сетевой переход и синхронная зависимость между сервисами. Вариант оправдан, только если единая точка входа обязательна. Его можно добавить позже, не меняя API limit-service.
- **Г. transfer-service читает и пишет limitdb напрямую.**
  Плюсы: HTTP-слой в limit-service не нужен.
  Минусы: нарушает принцип «у каждого сервиса своя БД» (в `docker-compose.yml` у каждого сервиса отдельная БД); transfer-service начинает зависеть от схемы limitdb.

**Рекомендуется вариант А.**

### 4.3. Где проверять максимальную сумму одного перевода

- **А. В limit-service — при принятии решения по событию `NEW`, вместе с дневным и месячным лимитами.**
  Плюсы: все проверки лимитов в одном месте и по одним и тем же настройкам. Перевод проходит обычный поток: причина попадает в историю (этап `LIMIT`) и в финальный статус так же, как `DAILY_LIMIT_EXCEEDED` и `MONTHLY_LIMIT_EXCEEDED`. transfer-service и структура сообщений не меняются.
  Минусы: клиент узнаёт об отклонении асинхронно (через `GET /transfers/{id}`) — так же, как сейчас для остальных лимитов.
- **Б. В transfer-service — синхронной проверкой при `POST /transfers` (ответ 400).**
  Плюсы: клиент сразу получает ответ.
  Минусы: transfer-service должен знать актуальный порог, а значит, синхронизироваться с limit-service (см. минусы вариантов Б и В в 4.2). Перевод не создаётся, поэтому не остаётся ни истории, ни следа попытки. Логика лимитов оказывается в двух сервисах, и поведение расходится с остальными лимитами.

**Рекомендуется вариант А.**

### 4.4. Модель хранения и способ изменения

- **Структура хранения.**
  Одна запись с тремя колонками своих типов: соотношение лимитов можно закрепить ограничением БД, все три значения меняются атомарно. Новый вид лимита потребует миграции, а индивидуальные лимиты (если понадобятся, вопрос 8.2) — другой модели.
  Записи вида «код лимита — значение»: новые виды лимитов добавляются без изменения схемы. Но соотношения тогда проверяются только в коде, а изменить несколько лимитов — значит изменить несколько записей.
  **Рекомендуется одна запись**: набор лимитов задача фиксирует.
- **Способ изменения.**
  `PUT` (замена всех трёх значений): соотношения проверяются однозначно, оператор всегда видит и подтверждает полный набор; передавать нужно все три значения.
  `PATCH` (частичное изменение): одно значение менять удобнее, но соотношения приходится проверять против сохранённых значений, и семантика сложнее.
  **Рекомендуется `PUT` с защитой от одновременного изменения (поле `version`)**: без неё, если лимиты правят два оператора одновременно, последний запрос молча затрёт изменения первого.

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. limit-service

#### Изменения в БД (limitdb)

Новая таблица `limit_settings` — общие лимиты для всех отправителей:

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | SMALLINT | PRIMARY KEY, CHECK (`id = 1`) | Гарантирует, что запись настроек одна |
| `daily_max` | DECIMAL(15,2) | NOT NULL, CHECK (`daily_max > 0`) | Дневной лимит на общую сумму переводов отправителя |
| `monthly_max` | DECIMAL(15,2) | NOT NULL, CHECK (`monthly_max > 0`) | Месячный лимит на общую сумму переводов отправителя |
| `single_transfer_max` | DECIMAL(15,2) | NOT NULL, CHECK (`single_transfer_max > 0`) | Максимальная сумма одного перевода |
| `version` | BIGINT | NOT NULL, DEFAULT 0 | Версия записи для защиты от одновременного изменения |
| `updated_at` | TIMESTAMP | NOT NULL, DEFAULT текущее время | Дата и время последнего изменения |

- Ограничение на уровне таблицы: CHECK (`single_transfer_max <= daily_max AND daily_max <= monthly_max`) — если бизнес подтвердит это правило (вопрос 8.4).
- Тип DECIMAL(15,2) — тот же, что у сумм в `sender_usage` и `reservations` (`limit-service/src/main/resources/db/changelog/001-create-tables.sql`) и у суммы перевода в transfer-service.
- Начальная запись создаётся миграцией и обязательна во всех окружениях: это справочные данные, а не тестовые. Значения: `id = 1`, `daily_max = 50000.00`, `monthly_max = 200000.00` (текущие значения из `application.yml`), `single_transfer_max = 50000.00`, `version = 0`, `updated_at` — момент миграции. Значение `single_transfer_max` временное, до ответа на вопрос 8.1: пока оно равно дневному лимиту, поведение системы не меняется.
- Если в каком-то окружении `limits.daily-max` / `limits.monthly-max` переопределены внешней конфигурацией (в репозитории не найдено), начальная запись должна содержать значения, которые там действуют на самом деле.
- `reservations`: структура не меняется; в `reason` появляется новое значение `SINGLE_TRANSFER_LIMIT_EXCEEDED` (30 символов при VARCHAR(50)).
- `sender_usage`: без изменений.
- Мигрировать существующие данные не нужно. Тестовых данных в limit-service нет (`changelog-master.yaml` подключает только `001-create-tables.sql`), и добавлять их не требуется: для сценариев с заблокированным отправителем хватает тестовых данных screening-service.

#### Конфигурация и инфраструктура

- После переноса лимитов в БД параметры `limits.daily-max` и `limits.monthly-max` удаляются из `limit-service/src/main/resources/application.yml`: значения берутся только из `limit_settings`.
- limit-service должен принимать HTTP-запросы. Его порт должен отличаться от порта transfer-service (8080) и в `docker-compose.yml`, и при локальном запуске: конфигурация обоих сервисов рассчитана на запуск на одном хосте (`application.yml` ссылается на `localhost`). Предлагается порт 8081; он публикуется в `docker-compose.yml`.
- API описывается в OpenAPI по образцу `transfer-service/src/main/resources/openapi/transfer-api.yaml` (предлагается файл `limit-service/src/main/resources/openapi/limit-api.yaml`), вместе с правилами валидации и кодами ответов.

#### Изменения в API (limit-service)

**Эндпоинт:** `GET /limits`
**Описание:** возвращает текущие значения всех лимитов, действующих для всех отправителей.

Параметры запроса: отсутствуют.

Параметры ответа:

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | number (decimal, 2 знака после запятой) | нет | Дневной лимит на общую сумму переводов отправителя |
| `monthlyMax` | number (decimal, 2 знака после запятой) | нет | Месячный лимит на общую сумму переводов отправителя |
| `singleTransferMax` | number (decimal, 2 знака после запятой) | нет | Максимальная сумма одного перевода |
| `version` | integer (int64) | нет | Текущая версия настроек; передаётся в `PUT /limits` |
| `updatedAt` | string (дата-время ISO-8601 без часового пояса, как `createdAt` в API переводов) | нет | Дата и время последнего изменения |

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Значения лимитов возвращены |
| 500 | Внутренняя ошибка: например, недоступна БД или нет записи настроек (тело — ProblemDetail) |

**Эндпоинт:** `PUT /limits`
**Описание:** заменяет значения всех трёх лимитов; новые значения применяются ко всем решениям, принятым после успешного ответа.

Параметры запроса:

| Параметр | Источник (body/path/query) | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `dailyMax` | body | number (decimal) | да | Новый дневной лимит: больше 0, не более 2 знаков после запятой и не более 13 знаков в целой части |
| `monthlyMax` | body | number (decimal) | да | Новый месячный лимит; правила те же |
| `singleTransferMax` | body | number (decimal) | да | Новая максимальная сумма одного перевода; правила те же |
| `version` | body | integer (int64) | да | Версия настроек, полученная из `GET /limits` |

Параметры ответа (состояние после изменения):

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | number (decimal, 2 знака после запятой) | нет | Новый дневной лимит |
| `monthlyMax` | number (decimal, 2 знака после запятой) | нет | Новый месячный лимит |
| `singleTransferMax` | number (decimal, 2 знака после запятой) | нет | Новая максимальная сумма одного перевода |
| `version` | integer (int64) | нет | Новая версия настроек (предыдущая + 1) |
| `updatedAt` | string (дата-время ISO-8601 без часового пояса) | нет | Дата и время этого изменения |

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Лимиты изменены; в ответе новые значения и новая версия |
| 400 | Тело не читается как JSON или значение не число; любое поле отсутствует или равно null; значение меньше или равно 0; больше 2 знаков после запятой; больше 13 знаков в целой части; нарушено соотношение `singleTransferMax ≤ dailyMax ≤ monthlyMax` (если правило подтверждено, вопрос 8.4) |
| 409 | `version` не совпадает с текущей: настройки уже изменил другой запрос |
| 500 | Внутренняя ошибка, например недоступна БД |

Общие требования к API:
- Ошибки возвращаются в формате ProblemDetail (`application/problem+json`, поля `type`, `title`, `status`, `detail`, `instance`) — так же, как в transfer-service (`spring.mvc.problemdetails.enabled: true`, `ApiExceptionHandler.java`). При ответе 400 в `detail` понятным оператору текстом указывается, какое поле и какое правило нарушено.
- Нарушения, которые обнаруживает БД (CHECK-ограничения, конфликт версий), должны возвращаться как 400 и 409, а не как 500. Обоснование: в transfer-service любое необработанное исключение превращается в ответ 500 (`ApiExceptionHandler.java` → `handleUnexpected`), и если перенести этот подход как есть, такие ошибки тоже станут ответом 500.
- Создавать и удалять настройки через API нельзя: запись создаёт только миграция.

#### Изменения в бизнес-логике

Новые правила принятия решения по переводу:

1. При поступлении события `NEW` с суммой больше `single_transfer_max` система должна отклонить перевод: решение `DECLINED`, причина `SINGLE_TRANSFER_LIMIT_EXCEEDED`.
2. При сумме, равной `single_transfer_max`, система должна считать проверку пройденной. Отклоняется только строгое превышение — как сейчас для дневного и месячного лимитов (`LimitLedger.java` → `decide`, сравнение «больше»).
3. При отклонении по правилу 1 система не должна изменять `daily_used` и `monthly_used` отправителя. Она должна сохранить в `reservations` запись с `decision = DECLINED`, `reason = SINGLE_TRANSFER_LIMIT_EXCEEDED`, `state = NONE` и фактической суммой перевода в `amount` (а не 0, как для `INVALID_AMOUNT`, см. 6.4). Эта запись нужна в том числе для идемпотентности (правило 16).
4. При принятии нового решения система должна выполнять проверки в порядке `INVALID_AMOUNT` → `SINGLE_TRANSFER_LIMIT_EXCEEDED` → `DAILY_LIMIT_EXCEEDED` → `MONTHLY_LIMIT_EXCEEDED` и возвращать одну причину — первую сработавшую. Порядок нужно подтвердить у бизнеса (вопрос 8.6). Обоснование: перевод с суммой больше порога не пройдёт ни сегодня, ни завтра, а причина «дневной лимит» подсказала бы отправителю повторить его на следующий день.
5. При принятии решения система должна брать текущие значения всех трёх лимитов из `limit_settings`. Изменение, на которое API вернул успешный ответ, должно действовать на все решения, принятые после этого ответа, во всех экземплярах limit-service и без их перезапуска. Решение, которое уже принималось в момент изменения, может быть принято по прежним значениям.
6. При проверке лимитов система должна применять значения, действующие в момент обработки события `NEW` в limit-service, а не в момент создания перевода в transfer-service.
7. Если записи в `limit_settings` нет, система не должна одобрять переводы и должна записывать в лог ошибку конфигурации.

Новые правила управления лимитами:

8. При запросе `GET /limits` система должна возвращать значения из `limit_settings`.
9. При запросе `PUT /limits` с некорректными данными (см. условия для кода 400) система должна вернуть 400 и не менять значения. Значения с более чем двумя знаками после запятой не округляются, а отклоняются. Верхняя граница — 9999999999999.99, как у суммы перевода (`TransferRequest.java`) и у типа DECIMAL(15,2).
10. При запросе `PUT /limits`, который нарушает соотношение `singleTransferMax ≤ dailyMax ≤ monthlyMax`, система должна вернуть 400 и не менять значения (если правило подтверждено, вопрос 8.4); равенство допускается.
11. При запросе `PUT /limits` с `version`, не совпадающей с текущей, система должна вернуть 409 и не менять значения.
12. При успешном `PUT /limits` система должна атомарно заменить все три значения, увеличить `version` на 1, записать в `updated_at` текущее время и вернуть новое состояние.
13. При успешном изменении лимитов система должна записывать в лог прежние и новые значения всех трёх лимитов.

Затрагиваемые существующие правила:

14. При проверке дневного и месячного лимитов система должна брать пороги из `limit_settings` (сейчас — `limits.daily-max` и `limits.monthly-max` из `application.yml`). Формула и строгое сравнение не меняются.
15. При изменении лимитов система не должна пересматривать ранее принятые решения: одобренные переводы остаются одобренными, резервы сохраняются. Резерв фиксируется или освобождается по финальному статусу (`LimitLedger.java` → `settle`) на сумму резерва, независимо от текущих лимитов. Если дневной или месячный лимит снизили ниже того, что отправитель уже израсходовал, его новые переводы отклоняются с `DAILY_LIMIT_EXCEEDED` / `MONTHLY_LIMIT_EXCEEDED` до сброса периода — по существующей формуле, без особой обработки.
16. При повторном событии `NEW` по переводу, решение по которому уже принято, система должна вернуть сохранённое решение, даже если лимиты с тех пор изменились. Это текущее поведение (`LimitLedger.java` → `decide`), его нужно сохранить.
17. Проверка `INVALID_AMOUNT` остаётся первой и не меняется.

#### Изменения в контрактах сообщений

- Топик `limit-results`, сообщение `Transfer` (transfer-common): структура не меняется. Появляется новое значение `messageInfo = "SINGLE_TRANSFER_LIMIT_EXCEEDED"` при `status = "DECLINED"` и `decidedBy = "limit"`.
- Транзитивно меняются значения в финальном статусе в топике `transfers` (его формирует transfer-service, `TransferDecisionService.java` → `decide`), а значит, и в `transfers.message_info` и истории перевода в transfer-service:
  - limit `DECLINED` (`SINGLE_TRANSFER_LIMIT_EXCEEDED`) + screening `APPROVED` → `status = CANCELLED`, `decidedBy = "limit"`, `messageInfo = "SINGLE_TRANSFER_LIMIT_EXCEEDED"`;
  - limit `DECLINED` (`SINGLE_TRANSFER_LIMIT_EXCEEDED`) + screening `DECLINED` → `status = DENIED`, `decidedBy = null`, `messageInfo = "SINGLE_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED"`.
- Причины отклонения limit-service после доработки: `INVALID_AMOUNT`, `SINGLE_TRANSFER_LIMIT_EXCEEDED`, `DAILY_LIMIT_EXCEEDED`, `MONTHLY_LIMIT_EXCEEDED`. Новых статусов нет.

### 5.2. transfer-service

Изменений нет: новая причина проходит транзитом. Финальный статус берёт `messageInfo` из результата limit-service (`TransferDecisionService.java` → `decide`); перевод и история хранят его в колонках `message_info` типа TEXT (`TransferTrackingService.java`); в `openapi/transfer-api.yaml` поле `messageInfo` — свободная строка без перечня значений, поэтому схема API `/transfers` не меняется.

### 5.3. screening-service

Изменений нет: сервис не работает с суммами и лимитами, его результат объединяется с результатом limit-service как раньше.

### 5.4. transfer-common

Изменений нет: структура `Transfer` не меняется, новая причина передаётся в существующем строковом поле `messageInfo`.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

### 6.1. Перезапуск limit-service «подвешивает» переводы, которые в этот момент в обработке

**Суть.** Лимиты считываются только при старте (`LimitLedger.java`, поля с `@Value`), поэтому сейчас изменить их можно только перезапуском limit-service. Финальное решение формируется объединением (join) топиков `limit-results` и `screening-results` с окном 10 секунд без grace-периода (transfer-service, `DecisionTopologyConfig.java` → `decisionStream`, `JoinWindows.ofTimeDifferenceWithNoGrace(Duration.ofSeconds(10))`). Если результат limit-service публикуется больше чем через 10 секунд после результата screening-service, объединение не срабатывает. Так бывает при перезапуске, при перебалансировке группы потребителей или при повторах обработчика ошибок (limit-service, `KafkaErrorHandlingConfig.java`, `FixedBackOff(1000L, 3L)`). Если же повторы исчерпаны, сообщение уходит в `transfers.DLT`, и результата limit-service нет вовсе. В обоих случаях финальный статус не формируется и перевод навсегда остаётся в `NEW`. Если limit-service успел одобрить перевод, резерв остаётся `RESERVED`, а сумма — в `daily_used` / `monthly_used`: резерв освобождается только при финальном статусе. Механизма тайм-аута или компенсации в коде не найдено.

**Связь с задачей.**
- Это ещё один аргумент за то, чтобы менять лимиты без перезапуска (правило 5 в 5.1).
- Чтобы развернуть саму доработку, придётся перезапустить limit-service с миграцией БД. Выкатывать нужно в окно без трафика, а после выката проверить через `GET /transfers`, нет ли переводов, «застрявших» в `NEW`.
- В приёмочных тестах нельзя перезапускать limit-service между созданием перевода и получением финального статуса, иначе тест упадёт по причине, не связанной с доработкой.
- Ошибка чтения настроек (недоступна БД, нет записи — правило 7) приводит к тому же сценарию: повторы, `transfers.DLT`, перевод остаётся в `NEW`. Требование «не одобрять» при этом выполняется, но такие случаи нужно отслеживать по логам.

### 6.2. Валюта при учёте лимитов игнорируется

**Суть.** transfer-service принимает перевод в любой валюте формата `[A-Z]{3}` (по умолчанию RUB — `TransferRequest.java`), и валюта передаётся в `Transfer.currency`. Но limit-service сравнивает и накапливает только `amount` (`LimitLedger.java` → `decide`, `SenderUsage.java` → `reserve`), а в `sender_usage` и `reservations` валюты нет. Переводы на 1000.00 USD и на 1000.00 RUB расходуют лимит одинаково.

**Связь с задачей.** Новый порог унаследует ту же проблему: у максимальной суммы одного перевода нет валюты, и перевод на 10000.00 USD пройдёт при пороге 10000.00. Нужно решение бизнеса (вопрос 8.3). Если бизнес не решит иначе, в рамках задачи это поведение не меняется.

### 6.3. Длина поля причины в limit-service ограничена 50 символами

**Суть.** `reservations.reason` имеет тип VARCHAR(50) (`limit-service/src/main/resources/db/changelog/001-create-tables.sql`).

**Связь с задачей.** Код новой причины должен уложиться в 50 символов (`SINGLE_TRANSFER_LIMIT_EXCEEDED` — 30). Если бизнес захочет «понятную причину» в виде текста с суммами (вопрос 8.7), такой текст без изменения колонки не поместится. В transfer-service ограничения нет: `message_info` имеет тип TEXT.

### 6.4. Для `INVALID_AMOUNT` в резерв записывается сумма 0

**Суть.** При некорректной сумме запись в `reservations` сохраняется с `amount = 0`, а не с фактической суммой (`LimitLedger.java` → `decide`).

**Связь с задачей.** Для нового отклонения так делать нельзя — нужна фактическая сумма (правило 3 в 5.1). Иначе по `reservations` не получится понять, какие суммы отсекает новый лимит, и обосновать выбор порога.

### 6.5. Аутентификации и авторизации нет

**Суть.** Ни в одном модуле нет аутентификации и разграничения доступа (в `pom.xml` сервисов нет соответствующих зависимостей); API `/transfers` открыт.

**Связь с задачей.** Новый API меняет финансовые лимиты сразу для всех отправителей. Без защиты изменить их сможет любой, у кого есть сетевой доступ к порту limit-service. Нужно решение бизнеса (вопрос 8.9), а до него доступ к порту необходимо ограничивать сетевыми средствами.

### 6.6. Граница суток и месяца зависит от часового пояса окружения

**Суть.** Текущая дата берётся через `LocalDate.now()` без явного часового пояса (`LimitLedger.java` → `decide`, `settle`). Пояс не задан ни в `Dockerfile`, ни в `docker-compose.yml`, ни в `application.yml`, поэтому где проходит граница дня и месяца, определяет окружение (требует уточнения).

**Связь с задачей.** Логика периодов не меняется, но бизнес, управляя дневным лимитом через API, может ожидать другую границу суток. Приёмочные тесты дневного и месячного лимитов нельзя проводить около полуночи по времени сервера limit-service.

## 7. КРИТЕРИИ ПРИЁМКИ

**Общие предусловия** (если в кейсе не сказано иное): через `PUT /limits` установлены `dailyMax = 50000.00`, `monthlyMax = 200000.00`, `singleTransferMax = 10000.00`. Отправитель не заблокирован (не входит в тестовый список screening-service: 5, 13, 21, 34, 42) и не делал переводов в текущих сутках и месяце. «Перевод N» — это `POST /transfers` с новым `id` и суммой N. Результат проверяется через `GET /transfers/{id}` после завершения обработки.

### 7.1. Максимальная сумма одного перевода

1. Перевод 9999.99 → `COMPLETED`; в истории на этапе `LIMIT` — `APPROVED`; `daily_used` и `monthly_used` отправителя выросли на 9999.99.
2. Перевод 10000.00 (равен порогу) → `COMPLETED`.
3. Перевод 10000.01 → `CANCELLED`, `decidedBy = limit`, `messageInfo = SINGLE_TRANSFER_LIMIT_EXCEEDED`. В истории на этапе `LIMIT` — `DECLINED` с тем же `messageInfo`. В `reservations`: `decision = DECLINED`, `reason = SINGLE_TRANSFER_LIMIT_EXCEEDED`, `state = NONE`, `amount = 10000.01`. `daily_used` и `monthly_used` отправителя не изменились.
4. Заблокированный отправитель (`senderId = 5`), перевод 10000.01 → `DENIED`, `decidedBy = null`, `messageInfo = "SINGLE_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED"`.
5. Тот же отправитель после отклонения из кейса 3, перевод 10000.00 → `COMPLETED` (отклонённый перевод не израсходовал лимит).
6. Отправитель за текущие сутки уже перевёл 45000.00 (например, 4 × 10000.00 + 5000.00), перевод 10000.01 → `CANCELLED` с `SINGLE_TRANSFER_LIMIT_EXCEEDED`, а не с `DAILY_LIMIT_EXCEEDED`.
7. В том же состоянии (45000.00 за сутки) перевод 5000.01 → `CANCELLED` с `DAILY_LIMIT_EXCEEDED`; следующий перевод 5000.00 → `COMPLETED` (итог за сутки — ровно 50000.00).
8. У отправителя `monthly_used = 195000.00`, `daily_used = 0` (данные подготовлены в `sender_usage`, даты сброса — текущие). Перевод 5000.01 → `CANCELLED` с `MONTHLY_LIMIT_EXCEEDED`; следующий перевод 5000.00 → `COMPLETED`.
9. Перевод отклонён с `SINGLE_TRANSFER_LIMIT_EXCEEDED`, после этого `singleTransferMax` увеличен до 20000.00, а в топик `transfers` повторно доставлено то же событие `NEW` (тот же `id`) → в `limit-results` публикуется прежнее решение (`DECLINED`, `SINGLE_TRANSFER_LIMIT_EXCEEDED`); запись в `reservations` не изменилась.
10. Событие `NEW` с суммой 0 или отрицательной суммой, отправленное прямо в топик `transfers` (через REST такие суммы не проходят) → `DECLINED` с `INVALID_AMOUNT`, а не с `SINGLE_TRANSFER_LIMIT_EXCEEDED`.

### 7.2. Применение изменений

11. Перевод 15000.00 → `CANCELLED` с `SINGLE_TRANSFER_LIMIT_EXCEEDED`; затем `PUT /limits` с `singleTransferMax = 20000.00` → 200; новый перевод 15000.00 → `COMPLETED`. limit-service при этом не перезапускался.
12. Отправитель за сутки перевёл 30000.00 (3 × 10000.00); `PUT /limits` с `dailyMax = 20000.00` → 200; новый перевод 0.01 → `CANCELLED` с `DAILY_LIMIT_EXCEEDED`. Ранее совершённые переводы остаются `COMPLETED`, их резервы — `COMMITTED`, `daily_used = 30000.00`.
13. После успешного `PUT /limits` limit-service перезапущен → `GET /limits` возвращает значения из последнего `PUT`, и решения принимаются по ним.
14. Сразу после развёртывания, без общих предусловий и без вызова `PUT` → `GET /limits` возвращает `dailyMax = 50000.00`, `monthlyMax = 200000.00`, согласованное начальное значение `singleTransferMax` (50000.00, если не решено иначе) и `version = 0`. Перевод 50000.00 от отправителя без использования → `COMPLETED`; следующий его перевод 0.01 в те же сутки → `CANCELLED` с `DAILY_LIMIT_EXCEEDED`, то есть поведение до доработки сохранилось.

### 7.3. API лимитов

15. `GET /limits` → 200; поля `dailyMax`, `monthlyMax`, `singleTransferMax`, `version`, `updatedAt` есть и не равны null; суммы — с двумя знаками после запятой.
16. `PUT /limits` с `dailyMax = 60000.00`, `monthlyMax = 250000.00`, `singleTransferMax = 15000.00` и текущей `version` → 200. В ответе новые значения, `version` выросла на 1, `updatedAt` обновлён; `GET /limits` возвращает то же самое; в логе limit-service есть запись с прежними и новыми значениями.
17. `PUT /limits` без одного из полей (проверяется для каждого поля, включая `version`) → 400, в `detail` названо поле; значения не изменились.
18. `PUT /limits` с `singleTransferMax = null` → 400.
19. Значение лимита 0 → 400; -100.00 → 400; 0.01 (при соблюдении соотношения лимитов) → 200.
20. Значение с тремя знаками после запятой (например, `dailyMax = 50000.001`) → 400; значение не округляется и не сохраняется.
21. Все три значения равны 9999999999999.99 → 200; любое значение, равное 10000000000000.00 → 400.
22. `singleTransferMax = 50000.01` при `dailyMax = 50000.00` → 400; `singleTransferMax = dailyMax = 50000.00` → 200 (если правило из вопроса 8.4 подтверждено).
23. `dailyMax = 200000.01` при `monthlyMax = 200000.00` → 400; `dailyMax = monthlyMax = 200000.00` → 200 (если правило из вопроса 8.4 подтверждено).
24. `PUT /limits` с устаревшей `version` → 409; значения не изменились.
25. Два одновременных `PUT /limits` с одинаковой `version` → один получает 200, другой 409; сохранены значения успешного запроса.
26. Тело запроса — не JSON или значение не число (например, `"dailyMax": "abc"`) → 400 в формате ProblemDetail.

### 7.4. Регрессия

27. Перевод в пределах всех лимитов от незаблокированного отправителя → `COMPLETED`, резерв `COMMITTED`.
28. Заблокированный отправитель (`senderId = 5`), перевод 10000.00 → `CANCELLED`, `decidedBy = screening`, `messageInfo = SENDER_BLOCKED`; резерв `RELEASED`, `daily_used` и `monthly_used` вернулись к прежним значениям.
29. `GET /transfers/{id}` для перевода, отклонённого по новому лимиту → в истории этапы `NEW`, `LIMIT` (`DECLINED`), `SCREENING` (`APPROVED`), `FINAL` (`CANCELLED`); схема ответов `/transfers` не изменилась.

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ

У каждого вопроса есть предложение по умолчанию: если бизнес его подтверждает или не возражает, разработка идёт по нему.

1. **Начальное значение максимальной суммы одного перевода.** В задаче оно не задано, а без него нельзя подготовить миграцию. *Предложение:* 50000.00 — столько же, сколько дневной лимит, поэтому поведение не изменится, пока порог не установят через API. Если бизнес назовёт конкретное значение, оно сразу пойдёт в миграцию.
2. **Только общие лимиты или ещё и индивидуальные?** Формулировка «для всех отправителей» и текущая модель (общие `limits.*`) говорят о единых лимитах. Нужны ли индивидуальные лимиты или категории отправителей? *Предложение:* лимиты единые для всех; индивидуальные — отдельная задача.
3. **Валюта лимитов.** В какой валюте заданы лимиты и что делать с переводами в других валютах (сейчас валюта игнорируется, см. 6.2)? Варианты: оставить как есть, отклонять переводы не в RUB или пересчитывать по курсу (курсов валют в системе нет — в коде не найдено). *Предложение:* в рамках задачи оставить как есть и зафиксировать это как известное ограничение.
4. **Соотношение лимитов.** Запрещать ли значения, при которых `singleTransferMax > dailyMax` или `dailyMax > monthlyMax`? В таких случаях меньший по смыслу лимит ничего не ограничивает. *Предложение:* запрещать (ответ 400), равенство допускать.
5. **Ноль и «без ограничения».** Нужно ли уметь задать 0 (запрет переводов) или отключить лимит (пустое значение)? *Предложение:* нет — все три лимита обязательны и строго больше 0.
6. **Приоритет причин.** Если нарушено несколько лимитов, возвращается одна причина. В каком порядке их проверять? *Предложение:* сначала максимальная сумма одного перевода, затем дневной лимит, затем месячный.
7. **Формат «понятной причины».** Хватит ли машинного кода `SINGLE_TRANSFER_LIMIT_EXCEEDED` (как у существующих причин) или нужен текст для клиента, например с величиной порога? Текст с суммами не помещается в `reservations.reason` (см. 6.3). *Предложение:* код.
8. **Когда изменения вступают в силу.** Сразу или со следующего периода (например, новый дневной лимит — с завтрашнего дня)? Нужны ли отложенные изменения «с такой-то даты»? *Предложение:* сразу, для всех решений после успешного ответа API; отложенные изменения — за рамками задачи.
9. **Доступ к API.** Кто может просматривать лимиты, а кто — изменять? Нужны ли аутентификация и разграничение прав (в системе их нет, см. 6.5)? Должен ли API быть доступен за пределами внутренней сети? *Предложение:* в рамках задачи обойтись без аутентификации, как в существующем API, и ограничить доступ сетевыми средствами; аутентификацию сделать отдельной задачей. Бизнесу нужно явно согласиться с этим риском.
