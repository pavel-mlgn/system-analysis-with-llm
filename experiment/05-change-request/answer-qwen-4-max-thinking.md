# ПОСТАНОВКА НА ДОРАБОТКУ: лимит суммы одного перевода + API управления лимитами

---

## 1. ЦЕЛЬ ДОРАБОТКИ

Ввести第三个 (третий) порог — «максимальная сумма одного перевода», общий для всех отправителей: перевод дороже порога отклоняется с отдельной причиной, даже если дневной и месячный лимиты не исчерпаны. Все три лимита (дневной, месячный, максимальная сумма одного перевода) становятся управляемой настройкой: их значения можно посмотреть и изменить через REST API, без правки конфигурации и перезапуска сервиса. Отказ по новому правилу проходит через существующий асинхронный контур принятия решения и виден в истории перевода.

## 2. ПРЕДПОСЫЛКИ

- Проверяются только **накопленные** суммы: `dailyUsed + amount` vs `dailyMax` и `monthlyUsed + amount` vs `monthlyMax` (`limit-service`, `LimitLedger.decide`). Единичный перевод на 50 000.00 при нулевом использовании проходит и «съедает» весь дневной лимит.
- Значения лимитов — статические свойства приложения (`limit-service/src/main/resources/application.yml`, `limits.daily-max: 50000.00`, `limits.monthly-max: 200000.00`; в `application-docker.yml` не переопределяются). Персистентного хранилища настроек и API управления нет: изменение лимита = правка файла + пересборка/перезапуск.
- Причина отказа крупного единичного перевода сегодня — `DAILY_LIMIT_EXCEEDED`, она не отражает бизнес-смысл «перевод слишком крупный сам по себе».
- У `limit-service` вообще нет HTTP-слоя (`limit-service/pom.xml` — `spring-boot-starter`, без web/validation; в `docker-compose.yml` у сервиса нет `ports`), поэтому задача требует появления у сервиса публичного API, а не только нового правила.

| `limit-service`, логика проверки NEW | модифицируемый | Новое правило и новый источник значений лимитов (хранилище вместо конфигурации), порядок проверок |
| `limit-service`, REST API `GET /limits`, `PUT /limits` | новый | Просмотр и изменение значений лимитов |

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### 4.1. В каком сервисе разместить API управления лимитами

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. `limit-service`** (рекомендуется) | Владелец домена лимитов и данных (`limitdb`: `sender_usage`, `reservations`); настройка и её применение в одном сервисе и одной БД → изменение атомарно и видно проверке сразу; нет межсервисных синхронизаций | Нужно добавить HTTP-стек, валидацию, формат ошибок, порт в compose; сервис из «чистого консьюмера» становится ещё и API |
| B. `transfer-service` | Готовый web-стек, валидация, problem-details, OpenAPI, порт 8080 уже проброшен; единая точка входа для клиентов | Лимиты — не его домен: понадобится либо доступ в чужую БД `limitdb`, либо синхронный вызов/команда в `limit-service` → связность, задержки, рассогласование «что показано в API» и «что применяется при проверке» |
| C. Отдельный сервис настроек | Изоляция админ-функции | Новый модуль, образ, compose-сервис, БД/доступ к настройкам; неоправданно для двух эндпоинтов, проблема принадлежности данных остаётся |

**Рекомендуется A.** Обоснование: значения лимитов сегодня принадлежат `limit-service` (`application.yml`, `LimitLedger`), учёт использования — тоже (`limitdb`).

### 4.2. Где хранить значения лимитов

| Вариант | Плюсы | Минусы |
|---|---|---|
| **A. Таблица в `limitdb`** (рекомендуется) | Персистентность, транзакционное чтение согласованного набора, изменение без перезапуска; Liquibase уже используется | Появляется чтение настроек в контуре обработки события |
| B. Оставить в `application.yml` + внешний конфиг/refresh | Минимум изменений схемы | В коде нет ни actuator, ни config-сервера (в коде не найдено); API не может менять файл в образе; значение сбрасывается при рестарте → требование не выполняется |
| C. Колонки в `sender_usage` | Нет новой таблицы | Смешение настроек и учёта; для нового отправителя строки нет → негде хранить глобальное значение; невозможно выразить «настройка для всех» |
| D. Топик настроек в Kafka | Асинхронная доставка | Eventual consistency, нужен state store/compact-топик и логика ожидания первой загрузки; сложнее гарантировать «прочитал актуальное» |

**Рекомендуется A.**

### 4.3. Гранулярность настройки: глобальная или на отправителя

- **Глобальная (одна строка на всех)** — рекомендуется: соответствует текущей семантике дневного/месячного лимита (одни значения для всех, учёт per-sender) и формулировке API без `senderId`. Плюсы: простой контракт, нет правила приоритета. Минусы: нельзя задать исключение для конкретного отправителя.
- **Per-sender с глобальным дефолтом**: гибче, но требует отдельного контракта (`/limits/senders/{senderId}`), правила наследования и решения о том, что показывать в `GET /limits`. В задаче не запрошено.

**Рекомендуется глобальная**; пер-сендерные переопределения — вне scope до ответа бизнеса (§8, п. 2).

### 4.4. Где проверять порог одного перевода

- **Только в `limit-service`, асинхронно** (рекомендуется): единственная точка правды, актуальные значения на момент решения, нет дублирования правила; `POST /transfers` по-прежнему отвечает `201 NEW`, отказ приходит финальным статусом. Минус — клиент не узнаёт об отказе синхронно.
- **Дополнительно валидировать на входе `transfer-service` (400/422)**: быстрый отказ, но дублирование бизнес-правила в двух сервисах, необходимость читать чужие настройки, гонка «проверил со старым значением — применил новое», расхождение синхронного и асинхронного вердиктов.

**Рекомендуется только асинхронная проверка в `limit-service`.**

### 4.5. Семантика обновления

- **`PUT /limits` — полная замена всех трёх значений одним запросом** (рекомендуется): атомарность, идемпотентность, простой контракт валидации, в т.ч. межполевой. Минус — клиент обязан присылать все поля.
- `PATCH` (частичное обновление): удобнее для точечной правки, но усложняет валидацию согласованности и конкурентные обновления.

**Рекомендуется `PUT`.**

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. limit-service

#### Изменения в БД (`limitdb`)

Новая таблица **`limit_settings`** — глобальные настройки лимитов, ровно одна строка:

| Колонка | Тип | Ограничения | Описание |
|---|---|---|---|
| `id` | SMALLINT | PK, CHECK (`id = 1`) | Признак единственной (глобальной) записи |
| `daily_max` | DECIMAL(15,2) | NOT NULL, CHECK (`> 0`) | Дневной лимит суммы переводов отправителя |
| `monthly_max` | DECIMAL(15,2) | NOT NULL, CHECK (`> 0`) | Месячный лимит суммы переводов отправителя |
| `single_transfer_max` | DECIMAL(15,2) | NOT NULL, CHECK (`> 0`) | Максимальная сумма одного перевода |
| `updated_at` | TIMESTAMP | NOT NULL, DEFAULT NOW() | Момент последнего изменения настроек |

- Тип/точность — как у денежных колонок `sender_usage` и `reservations` (`DECIMAL(15,2)`).
- Верхняя граница значений — 9 999 999 999 999.99 (согласовано с валидацией суммы в `transfer-service`, `TransferRequest`: `@Digits(integer = 13, fraction = 2)`).
- **Миграция начальных данных (обязательна):** одна строка `id = 1` с `daily_max = 50000.00`, `monthly_max = 200000.00` (текущие значения из `application.yml`) и `single_transfer_max = <значение бизнеса>`. Значение нового порога в коде не найдено — **требует уточнения** (§8, п. 1); для dev/test-контура предлагается 15 000.00.
- Таблицы `sender_usage` и `reservations` не изменяются. Новый код причины должен укладываться в `reservations.reason VARCHAR(50)` (предлагаемый код — 29 символов); при выборе более длинного кода потребуется отдельная миграция расширения колонки.
- Тестовых данных в `limit-service` нет (в коде не найдено, в отличие от `screening-service/.../002-insert-test-data.sql`) — миграция тестовых данных не требуется, кроме начальной строки настроек.

#### Изменения в API

Эндпоинт: **GET /limits**
Описание: вернуть текущие действующие значения всех лимитов (общие для всех отправителей).

Параметры запроса:

| Параметр | Источник | Тип | Обязательный | Описание |
|---|---|---|---|---|
| — | — | — | — | Параметры отсутствуют |

Параметры ответа:

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | number (decimal, 2 знака) | нет | Дневной лимит суммы переводов отправителя |
| `monthlyMax` | number (decimal, 2 знака) | нет | Месячный лимит суммы переводов отправителя |
| `singleTransferMax` | number (decimal, 2 знака) | нет | Максимальная сумма одного перевода |
| `updatedAt` | string (ISO-8601 date-time) | нет | Момент последнего изменения настроек (для начальной миграции — момент её применения) |

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Настройки прочитаны |
| 503 | Хранилище настроек недоступно |
| 500 | Прочая непредвиденная ошибка |

Эндпоинт: **PUT /limits**
Описание: атомарно заменить значения всех трёх лимитов.

Параметры запроса:

| Параметр | Источник | Тип | Обязательный | Описание |
|---|---|---|---|---|
| `dailyMax` | body | number (decimal) | да | `> 0`, ≤ 9999999999999.99, не более 2 знаков после запятой |
| `monthlyMax` | body | number (decimal) | да | Те же ограничения |
| `singleTransferMax` | body | number (decimal) | да | Те же ограничения |

Параметры ответа:

| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| `dailyMax` | number (decimal) | нет | Новое действующее значение |
| `monthlyMax` | number (decimal) | нет | Новое действующее значение |
| `singleTransferMax` | number (decimal) | нет | Новое действующее значение |
| `updatedAt` | string (ISO-8601 date-time) | нет | Момент применения изменения |

Коды ответа:

| Код | Условие |
|---|---|
| 200 | Все три значения обновлены (в т.ч. повторный идентичный запрос) |
| 400 | Ошибка валидации: поле отсутствует/`null`, значение ≤ 0, превышен максимум, более 2 знаков после запятой, неверный тип/формат тела, нарушение согласованности лимитов (если правило подтверждено, §8, п. 3). Ни одно значение не изменено |
| 503 | Хранилище настроек недоступно, изменения не применены |
| 500 | Прочая непредвиденная ошибка |

Дополнительно к API:
- Формат тела ошибки предлагается `application/problem+json` (как в `transfer-service`); обработчика ошибок HTTP и текстов сообщений в `limit-service` нет (в коде не найдено) — состав полей и язык сообщений определить в рамках доработки, тексты должны быть корректно закодированы (UTF-8).
- Просмотр израсходованных сумм (`sender_usage`) и история изменений лимитов в scope не входят (задача их не содержит).
- Аутентификация/авторизация в коде отсутствует — см. §8, п. 7.
- Спецификация API оформляется отдельным файлом (предлагается `limit-service/src/main/resources/openapi/limit-api.yaml`); `transfer-api.yaml` не меняется.

#### Изменения в бизнес-логике

- При получении NEW, у которого `amount > singleTransferMax`, система должна отклонить перевод: `status = DECLINED`, `decidedBy = limit`, причина `SINGLE_TRANSFER_LIMIT_EXCEEDED`, зафиксировать решение в `reservations` с `state = NONE`, **не изменять** `sender_usage` и опубликовать результат в `limit-results`.
- При `amount = singleTransferMax` система должна считать порог не превышенным (граница разрешена) и перейти к действующим проверкам — семантика «строго больше», как в существующих сравнениях дневного/месячного лимита (`LimitLedger.decide`).
- При `amount = null` или `amount ≤ 0` система должна отклонять с `INVALID_AMOUNT` (существующее правило), новое правило не применять.
- При нескольких одновременно нарушенных лимитах система должна применять порядок проверок и возвращать **одну** причину по первому сработавшему правилу: `INVALID_AMOUNT` → `SINGLE_TRANSFER_LIMIT_EXCEEDED` → `DAILY_LIMIT_EXCEEDED` → `MONTHLY_LIMIT_EXCEEDED` (порядок — предложение, требует подтверждения, §8, п. 5).
- При проверке каждого NEW система должна использовать актуальные сохранённые значения лимитов, прочитанные как согласованный набор (недопустима смесь старых и новых значений внутри одного решения).
- При успешном ответе на `PUT /limits` система должна применять новые значения к переводам, поступающим после этого ответа, без перезапуска сервиса; значения должны сохраняться после перезапуска. Допустимая задержка вступления в силу (если допускается кэш) — требует уточнения (§8, п. 8).
- При обновлении настроек система должна изменять все три значения атомарно; частичное применение при ошибке недопустимо.
- При повторном NEW по уже обработанному `transfer_id` система должна возвращать ранее сохранённое решение независимо от текущих настроек (существующая идемпотентность, `LimitLedger.decide`, сохраняется).
- При финальном статусе по переводу, отклонённому новым правилом, система должна не изменять учёт использования: резервирования нет (`state = NONE`), существующая логика `LimitLedger.settle` доработок не требует.
- При уменьшении любого лимита система должна не пересчитывать и не отзывать ранее созданные резервирования; допускается состояние `dailyUsed > dailyMax` / `monthlyUsed > monthlyMax`, последующие NEW отклоняются по действующим правилам.
- При невозможности прочитать настройки лимитов система должна **не** принимать решение «по умолчанию» (ни одобрение, ни отказ): обработка события завершается ошибкой и попадает в существующий механизм повторных попыток и DLT (`KafkaErrorHandlingConfig`).
- Существующие правила дневного/месячного лимита, ленивого сброса периодов, резервирования/освобождения и валидации суммы не меняются — меняется только источник значений и добавляется одна проверка.

#### Изменения в контрактах сообщений

- Структура сообщения не меняется: новых полей в `Transfer` (`transfer-common`) не требуется, новых топиков и партиций не требуется.
- Новое допустимое значение `messageInfo` в `limit-results` (и, как следствие, в `transfers` и `transfer_history.message_info`): **`SINGLE_TRANSFER_LIMIT_EXCEEDED`**.
- `status = DECLINED`, `decidedBy = limit` — существующие значения, новых статусов нет.
- Ожидаемые итоговые сообщения (формируются существующей матрицей `TransferDecisionService.decide`, без изменений в ней):
  - limit DECLINED + screening APPROVED → `CANCELLED`, `decidedBy = limit`, `messageInfo = SINGLE_TRANSFER_LIMIT_EXCEEDED`;
  - limit DECLINED + screening DECLINED → `DENIED`, `messageInfo = "SINGLE_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED"`.

#### Изменения в конфигурации и развёртывании

- Добавить HTTP-стек и валидацию запросов, определить серверный порт; пробросить порт в `docker-compose.yml` (предлагается `8081:8080`). `Dockerfile` не меняется.
- Свойства `limits.daily-max` / `limits.monthly-max` перестают быть источником истины для решения; допустимо использовать их только как значения для начальной миграции. После внедрения хранилища конфигурация не должна влиять на результат проверки (иначе появится второй источник истины и «сброс» значений при рестарте).

### 5.2. transfer-service

**Изменений нет.** Матрица решений оперирует только `APPROVED`/`DECLINED` (`TransferDecisionService.decide`), новая причина — это значение `messageInfo`, которое проходит через `transfer_history`/`transfers` (`message_info TEXT`) без ограничений длины; синхронная валидация порога на `POST /transfers` сознательно не добавляется (см. 4.4), поэтому `TransferRequest`, контроллер и `transfer-api.yaml` не меняются.

### 5.3. screening-service

**Изменений нет.** Сервис проверяет только наличие отправителя в `blocked_senders` (`ScreeningJournal.check`) и не работает с суммами и лимитами.

### 5.4. transfer-common

**Изменений нет.** Причина отказа передаётся в существующем поле `messageInfo` записи `Transfer`; новые поля/статусы не требуются.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

1. **Лимиты живут в конфигурации, а не в данных** (`limit-service/src/main/resources/application.yml`, `limits.*`; инъекция в `LimitLedger`). Если оставить конфигурацию работающей «параллельно» с новой таблицей, изменение через API будет теряться при перезапуске, а в docker-профиле значения вообще не переопределяются. Требуется явно определить единственный источник истины.
2. **Решения кэшируются в `reservations`** (`LimitLedger.decide` возвращает сохранённое решение при повторном NEW; `TransferController.duplicate` повторно публикует NEW, если статус ещё NEW). После изменения лимитов повторные проверки на **том же** `transfer_id` дадут старый вердикт — это корректное поведение, но приёмочные тесты обязаны использовать новые id, иначе доработка будет выглядеть неработающей.
3. **Compact-топики + окно join 10 секунд** (`TopicsConfig` во всех трёх сервисах: `.compact()`; `DecisionTopologyConfig`: `JoinWindows.ofTimeDifferenceWithNoGrace(Duration.ofSeconds(10))`). Если ответы limit и screening разойдутся более чем на 10 с (например, из-за задержки чтения настроек или рестарта сервиса во время теста), итоговый статус не сформируется и перевод зависнет в NEW — это будет ложно интерпретировано как дефект нового правила. Дополнительно: из compacted `transfers` промежуточный NEW может быть вытеснен итоговым статусом, и при переигрывании событий `LimitLedger.settle` получит финальный статус без резервирования (warn/skip).
4. **`reason VARCHAR(50)`** в `reservations` (и в `screening_checks`). Слишком длинный код причины приведёт к ошибке вставки → ретраи → `transfers.DLT`, перевод зависнет в NEW. Предлагаемый код укладывается, но ограничение нужно зафиксировать в контракте.
5. **Валюта игнорируется при проверке лимитов** (`LimitLedger.decide` сравнивает `amount` без учёта `currency`; `TransferRequest` допускает любую `[A-Z]{3}`; конвертации в коде не найдено). Новое правило унаследует дефект: порог, задуманный в рублях, будет применяться к переводу в любой валюте. Требуется решение бизнеса (§8, п. 4).
6. **Нет обработки оптимистичных блокировок** (`SenderUsage` помечен `@Version`, но конкурентные конфликты в `LimitLedger.decide`/`settle` не обрабатываются; `DefaultErrorHandler` с `FixedBackOff(1000, 3)` отправляет событие в DLT). При параллельных переводах одного отправителя (типичный сценарий проверки граничных значений) возможны зависшие NEW, не связанные с новым правилом.
7. **В `limit-service` нет HTTP-слоя и обработки ошибок** (`pom.xml` без web/validation; `@RestControllerAdvice` в коде не найден). Копировать подход `transfer-service` нежелательно: `ApiExceptionHandler` перехватывает `Exception` и всегда отдаёт 500, а тексты `INTERNAL_ERROR` и `KAFKA_UNAVAILABLE` (`TransferController`) сохранены с нарушенной кодировкой (mojibake). Новые сообщения об ошибках должны быть читаемыми.
8. **Аутентификация/авторизация отсутствуют во всех сервисах** (в коде не найдено). Новый `PUT /limits` фактически открывает управление бизнес-правилами отклонения переводов всем, кто имеет сетевой доступ к порту.
9. **Аудита изменений настроек нет** (в коде не найдено; `transfer_history` фиксирует только этапы перевода). Если бизнесу нужна история «кто/когда/старое→новое», это отдельная сущность и отдельный scope.
10. **Освобождение использования обрезается нулём и привязано к дате резервирования** (`SenderUsage.release` с `max(ZERO)`, `lazyReset`). При уменьшении лимитов и последующих отменах фактические `dailyUsed`/`monthlyUsed` могут выглядеть «неконсистентно» относительно новых порогов — ожидаемые результаты приёмки нужно формулировать с учётом этого существующего поведения.

## 7. КРИТЕРИИ ПРИЁМКИ

Базовые значения для тестов: `dailyMax = 50000.00`, `monthlyMax = 200000.00`, `singleTransferMax = 15000.00` (порог — предложение, фиксируется после §8, п. 1). Отправитель не заблокирован (не 5/13/21/34/42), использование обнулено, если не указано иное. Каждый тест — с новым `transfer_id` (см. §6, п. 2).

**API управления лимитами**

1. `GET /limits` сразу после миграции → 200; `dailyMax = 50000.00`, `monthlyMax = 200000.00`, `singleTransferMax = 15000.00`, `updatedAt` не null.
2. `PUT /limits` с валидным набором (60000.00 / 250000.00 / 20000.00) → 200, в ответе новые значения; последующий `GET /limits` возвращает их; **перезапуск сервиса не выполнялся**.
3. `PUT /limits` с `singleTransferMax = 0` → 400; `GET /limits` возвращает прежний набор целиком (частичного применения нет).
4. `PUT /limits` с отрицательным значением любого лимита → 400, значения не изменены.
5. `PUT /limits` без одного из обязательных полей / с `null` → 400, значения не изменены.
6. `PUT /limits` с `singleTransferMax = 100.001` (3 знака после запятой) → 400.
7. `PUT /limits` со значением `10000000000000.00` (> 13 целых знаков) → 400.
8. `PUT /limits` со значением-строкой вместо числа / невалидным JSON → 400.
9. `PUT /limits` с `singleTransferMax > dailyMax` → 400 (если правило согласованности подтверждено; иначе тест переформулируется по решению §8, п. 3).
10. Повторный идентичный `PUT /limits` → 200, значения те же (идемпотентность).
11. Два конкурентных `PUT /limits` с разными наборами → в хранилище и в `GET` один из наборов **целиком**, смешанных значений нет.
12. Перезапуск `limit-service` после успешного `PUT` → `GET /limits` возвращает изменённые значения (не значения из конфигурации).
13. Хранилище настроек недоступно → `GET /limits` и `PUT /limits` отвечают 503, изменения не применены.

**Правило «максимальная сумма одного перевода»**

14. `amount = 15000.00` (ровно порог), использование 0 → `limit-results`: `APPROVED`, `decidedBy = limit`; итог `COMPLETED`; резервирование `RESERVED` → `COMMITTED`; `dailyUsed = 15000.00`.
15. `amount = 15000.01` (порог + 0.01) → `limit-results`: `DECLINED`, `decidedBy = limit`, `messageInfo = SINGLE_TRANSFER_LIMIT_EXCEEDED`; в `reservations`: `decision = DECLINED`, `reason = SINGLE_TRANSFER_LIMIT_EXCEEDED`, `state = NONE`; `sender_usage` не изменён; итог `CANCELLED`, `decidedBy = limit`; в `GET /transfers/{id}` история `NEW → LIMIT(DECLINED, причина) → SCREENING(APPROVED) → FINAL(CANCELLED)`.
16. `amount = 60000.00` (превышены и порог одного перевода, и дневной лимит) → причина **`SINGLE_TRANSFER_LIMIT_EXCEEDED`**, не `DAILY_LIMIT_EXCEEDED`.
17. `amount = 15000.00` при `dailyUsed = 45000.00` (порог одного перевода не превышен, дневной лимит превышен) → `DAILY_LIMIT_EXCEEDED` (существующее поведение сохранено).
18. `amount = 15000.00` при `monthlyUsed = 190000.00`, `dailyUsed = 0` → `MONTHLY_LIMIT_EXCEEDED`.
19. Событие NEW с `amount = 0` / отрицательной суммой (в обход REST-валидации) → `INVALID_AMOUNT`, новое правило не применяется.
20. Заблокированный отправитель (id = 5), `amount = 20000.00` → limit `DECLINED/SINGLE_TRANSFER_LIMIT_EXCEEDED`, screening `DECLINED/SENDER_BLOCKED`, итог `DENIED`, `messageInfo = "SINGLE_TRANSFER_LIMIT_EXCEEDED; SENDER_BLOCKED"`.
21. `POST /transfers` с `amount = 20000.00` → синхронно `201`, статус `NEW` (синхронного отказа нет); асинхронно итог `CANCELLED` с новой причиной.
22. Перевод в валюте `USD` на сумму выше порога → отклоняется по новому правилу (фиксирует текущее поведение «валюта не учитывается»; может измениться по решению §8, п. 4).

**Взаимодействие с изменением лимитов**

23. `PUT /limits` с `singleTransferMax = 5000.00`, затем перевод 6000.00 → `DECLINED/SINGLE_TRANSFER_LIMIT_EXCEEDED`; перевод 5000.00 → `APPROVED`.
24. Перевод 15000.00 одобрен и зарезервирован, затем `singleTransferMax` уменьшен до 5000.00, затем по этому же id приходит финальный `COMPLETED` → резервирование `COMMITTED`, использование не пересчитывается, задним числом перевод не отклоняется.
25. Повторное событие NEW по id из теста 24 после изменения лимитов → возвращается ранее сохранённое решение (`APPROVED`), новое правило не применяется.
26. `PUT /limits` с `dailyMax = 10000.00` при уже существующем `dailyUsed = 15000.00` → `GET /limits` показывает 10000.00; следующий NEW на любую сумму > 0 отклоняется по `DAILY_LIMIT_EXCEEDED`; ранее зарезервированные суммы не отзываются.
27. Хранилище настроек недоступно в момент обработки NEW → в `limit-results` нет ни `APPROVED`, ни `DECLINED`; событие обрабатывается существующим механизмом ретраев и попадает в `transfers.DLT`; после восстановления доступности перевод получает корректное решение.
28. Регресс: перевод 100.00 от незаблокированного отправителя → `COMPLETED`; перевод от заблокированного отправителя в пределах всех лимитов → `CANCELLED`, `decidedBy = screening`, `messageInfo = SENDER_BLOCKED`.

2. **Гранулярность настройки:** «для всех отправителей» — это одно глобальное значение (как текущие дневной/месячной лимиты) или нужна возможность переопределения для конкретного отправителя? От ответа зависят схема хранилища и контракт API (см. 4.3).
3. **Согласованность лимитов:** обязательно ли `singleTransferMax ≤ dailyMax ≤ monthlyMax`? Если да — отказывать ли в изменении при нарушении (400) или принимать с предупреждением? Что делать, если бизнес хочет порог одного перевода больше дневного лимита?
4. **Валюта:** пороги заданы в рублях? Нужно ли применять их к переводам в другой валюте (сейчас валюта при проверке лимитов игнорируется, конвертации в коде нет)? Если нужно — по какому курсу и из какого источника (в коде не найдено)?

9. **Судьба уже принятых решений при уменьшении лимитов:** подтверждается, что ранее одобренные/зарезервированные переводы не пересматриваются и не отзываются?
10. **Нужен ли синхронный отказ на `POST /transfers`** при превышении порога одного перевода, или достаточно асинхронного финального статуса (предлагается асинхронный, см. 4.4)?
