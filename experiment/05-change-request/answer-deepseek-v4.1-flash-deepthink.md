## 1. ЦЕЛЬ ДОРАБОТКИ

Добавить глобальное ограничение на сумму одного перевода: если сумма превышает настроенный порог, перевод должен отклоняться с понятной причиной. Также предоставить REST API для просмотра и изменения всех лимитов: дневного, месячного и максимальной суммы одного перевода.

## 2. ПРЕДПОСЫЛКИ

Сейчас в `limit-service` проверяются только накопительные дневной и месячный лимиты. Один перевод может израсходовать весь дневной лимит, потому что ограничения на сумму одного перевода нет. Кроме того, значения лимитов заданы в `application.yml` через `limits.daily-max` и `limits.monthly-max` и не могут быть изменены во время работы без перезапуска/пересборки.

## 3. SCOPE ИЗМЕНЕНИЙ

- `limit-service` — модифицируемый: добавить хранение и проверку максимальной суммы одного перевода, перейти на чтение лимитов из БД, добавить REST API управления лимитами.
- `limit-service` БД — новый объект: таблица глобальных настроек лимитов.
- `limit-service` API — новый: `GET /limits`, `PUT /limits`.
- `limit-service` конфигурация — модифицируемая: текущие `limits.daily-max` и `limits.monthly-max` перестают быть источником истины; при необходимости остаются только для первичного заполнения/миграции.
- `docker-compose.yml` — модифицируемый: опубликовать порт `limit-service` для доступа к REST API.
- `transfer-service` — изменений нет: новые причины отклонения уже передаются через `messageInfo` и историю, схема сообщений не меняется.
- `screening-service` — изменений нет: логика проверки блокировок не затрагивается.
- `transfer-common` — изменений нет: структура `Transfer` достаточна для передачи новой причины отклонения.
- Контракты Kafka-сообщений — модифицируемые в части значений: добавляется новое значение причины отклонения `SINGLE_LIMIT_EXCEEDED`; новые поля/топики не требуются.

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

Рассматриваются варианты размещения REST API управления лимитами.

**Вариант A. API и хранение лимитов в `limit-service` (рекомендуемый).**
- Плюсы: лимиты уже используются в `limit-service`; единый источник истины; проверка и изменение лимитов находятся рядом; не нужно межсервисное взаимодействие для чтения лимитов.
- Минусы: `limit-service` сейчас не является web-приложением; нужно добавить web-зависимость, контроллер, обработку ошибок и опубликовать порт.

**Вариант B. API в `transfer-service`, хранение лимитов в `transfer-service` или общей БД.**
- Плюсы: у `transfer-service` уже есть REST API и открытый порт.
- Минусы: `limit-service` должен получать лимиты из чужого сервиса/БД; появляется связность и дублирование ответственности; усложняется гарантия актуальности лимитов при принятии решения.

**Вариант C. Отдельный admin-сервис.**
- Плюсы: формальное разделение административного и runtime-контуров.
- Минусы: избыточно для текущего проекта; новый сервис, новая БД/миграции, дополнительные эксплуатационные затраты.

Рекомендуется вариант A: разместить REST API управления лимитами в `limit-service`.

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. `limit-service`

**Изменения в БД:**

- Новая таблица `limit_settings` (глобальные настройки лимитов).
  - `id` — `SMALLINT` / `INTEGER`, первичный ключ, ограничение `CHECK (id = 1)`, чтобы строка была singleton.
  - `daily_max` — `DECIMAL(15,2)`, `NOT NULL`, значение `>= 0`.
  - `monthly_max` — `DECIMAL(15,2)`, `NOT NULL`, значение `>= 0`.
  - `single_max` — `DECIMAL(15,2)`, `NOT NULL`, значение `>= 0`.
  - `updated_at` — `TIMESTAMP`, `NOT NULL`, значение по умолчанию `NOW()`.
- Миграция тестовых/начальных данных:
  - Вставить одну строку `id = 1`.
  - `daily_max = 50000.00`, `monthly_max = 200000.00` — текущие значения из `application.yml`.
  - `single_max` — в коде не найдено. Требуется значение от бизнеса. До согласования можно временно заполнить значением, не блокирующим текущее поведение, но это не решает бизнес-задачу; окончательное значение — открытый вопрос.

**Изменения в API:**

Эндпоинт: `GET /limits`
Описание: получить текущие значения всех глобальных лимитов.

Параметры запроса:
| Параметр | Источник | Тип | Обязательный | Описание |
|---|---|---|---|---|
| — | — | — | — | Нет параметров |

Параметры ответа:
| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| dailyMax | number / decimal | нет | Дневной лимит |
| monthlyMax | number / decimal | нет | Месячный лимит |
| singleMax | number / decimal | нет | Максимальная сумма одного перевода |
| updatedAt | string / date-time | нет | Время последнего изменения |

Коды ответа:
| Код | Условие |
|---|---|
| 200 | Лимиты успешно получены |
| 500 | Внутренняя ошибка |

Эндпоинт: `PUT /limits`
Описание: изменить все глобальные лимиты.

Параметры запроса:
| Параметр | Источник | Тип | Обязательный | Описание |
|---|---|---|---|---|
| dailyMax | body | number / decimal | да | Новый дневной лимит, `>= 0`, scale 2 |
| monthlyMax | body | number / decimal | да | Новый месячный лимит, `>= 0`, scale 2 |
| singleMax | body | number / decimal | да | Новая максимальная сумма одного перевода, `>= 0`, scale 2 |

Параметры ответа:
| Поле | Тип | Nullable | Описание |
|---|---|---|---|
| dailyMax | number / decimal | нет | Актуальный дневной лимит |
| monthlyMax | number / decimal | нет | Актуальный месячный лимит |
| singleMax | number / decimal | нет | Актуальная максимальная сумма одного перевода |
| updatedAt | string / date-time | нет | Время изменения |

Коды ответа:
| Код | Условие |
|---|---|
| 200 | Лимиты обновлены |
| 400 | Некорректное тело запроса / значения не проходят валидацию |
| 500 | Внутренняя ошибка |

**Изменения в бизнес-логике:**

- При `amount == null` или `amount <= 0` система должна отклонять перевод с причиной `INVALID_AMOUNT` (существующее правило).
- При `amount > singleMax` система должна отклонять перевод с причиной `SINGLE_LIMIT_EXCEEDED`.
- Проверка `singleMax` должна выполняться до проверок дневного и месячного лимитов, чтобы причина отклонения была максимально конкретной.
- При отклонении по `SINGLE_LIMIT_EXCEEDED` дневной и месячный расход отправителя не должны увеличиваться.
- При `amount <= singleMax` и `dailyUsed + amount > dailyMax` система должна отклонять перевод с причиной `DAILY_LIMIT_EXCEEDED` (существующее правило).
- При `amount <= singleMax` и `monthlyUsed + amount > monthlyMax` система должна отклонять перевод с причиной `MONTHLY_LIMIT_EXCEEDED` (существующее правило).
- При успешной проверке всех лимитов перевод должен быть одобрен, а расход отправителя увеличен на сумму перевода (существующее правило).
- Изменения лимитов через API должны применяться к последующим решениям; уже принятые решения по переводам не пересчитываются.
- Источником истины для всех трёх лимитов должна стать запись в `limit_settings`; значения из `application.yml` больше не должны использоваться как runtime-источник.

**Изменения в контрактах сообщений:**

- Добавляется новое значение причины отклонения: `SINGLE_LIMIT_EXCEEDED`.
- Новые поля в Kafka-сообщениях не появляются.
- Новые статусы переводов не появляются.

### 5.2. `transfer-service`

Изменений нет. Сервис уже передаёт `messageInfo` из результатов `limit-service` в историю и итоговый статус перевода. Новая причина `SINGLE_LIMIT_EXCEEDED` будет отображаться в `messageInfo` без изменения контрактов.

### 5.3. `screening-service`

Изменений нет. Логика проверки отправителя по блокировкам не связана с лимитами.

### 5.4. `transfer-common`

Изменений нет. Текущей структуры `Transfer` достаточно для передачи новой причины отклонения.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ

- В `limit-service` лимиты сейчас берутся из `@Value` (`limits.daily-max`, `limits.monthly-max`). Это прямо блокирует задачу: без перехода на БД или иной изменяемый источник нельзя реализовать API изменения лимитов.
- В `limit-service` проверка лимитов не учитывает валюту перевода: сравнивается `amount` без привязки к `currency`. Если переводы могут быть в разных валютах, новый лимит на один перевод также будет применяться без учёта валюты. Это может дать некорректные отклонения/одобрения. Требует уточнения у бизнеса.
- `limit-service` не содержит web-зависимости и не публикует порт в `docker-compose.yml`. Для REST API управления лимитами потребуется добавить web-слой и открыть порт.
- В `TransferDecisionService` при одновременном отклонении лимитом и скринингом причина формируется конкатенацией через `"; "`. Новая причина `SINGLE_LIMIT_EXCEEDED` будет корректно попадать в `messageInfo`, но итоговая строка может содержать несколько причин.
- Поле `reason` в `reservations` имеет ограничение `VARCHAR(50)`. Значение `SINGLE_LIMIT_EXCEEDED` в него помещается, миграция под увеличение длины не требуется.
- В проекте не найдено аутентификации/авторизации для REST API. API управления лимитами в текущем виде будет открытым; это риск, требующий решения бизнеса/безопасности.

## 7. КРИТЕРИИ ПРИЁМКИ

- `singleMax = 10000`, перевод на `10000` → лимит одного перевода не превышен; решение зависит от дневного/месячного лимитов.
- `singleMax = 10000`, перевод на `10000.01` → отклонён с причиной `SINGLE_LIMIT_EXCEEDED`.
- `singleMax = 10000`, перевод на `9999.99` → лимит одного перевода не превышен.
- `singleMax = 10000`, дневной лимит `5000`, перевод на `10000` → отклонён по `SINGLE_LIMIT_EXCEEDED` (проверка одного перевода срабатывает раньше дневного).
- `singleMax = 10000`, дневной лимит `5000`, перевод на `6000` → отклонён по `DAILY_LIMIT_EXCEEDED`.
- `singleMax = 10000`, месячный лимит `20000`, дневной лимит `50000`, перевод на `9000`, уже израсходовано за месяц `15000` → отклонён по `MONTHLY_LIMIT_EXCEEDED`.
- `singleMax = 10000`, перевод на `10000`, дневной лимит `10000`, месячный лимит `20000`, расход `0` → одобрен.
- `singleMax = 10000`, перевод на `10000`, дневной лимит `10000`, месячный лимит `20000`, дневной расход `0.01` → отклонён по `DAILY_LIMIT_EXCEEDED`.
- `GET /limits` → возвращает текущие `dailyMax`, `monthlyMax`, `singleMax`, `updatedAt`.
- `PUT /limits` с корректными значениями → возвращает обновлённые значения; последующее решение по переводу использует новые лимиты.
- `PUT /limits` с отрицательным значением → `400`.
- `PUT /limits` без обязательного поля → `400`.
- Повторный `NEW` по тому же `transferId` после изменения лимитов → возвращается ранее сохранённое решение, лимиты заново не применяются.
- Отклонение по `SINGLE_LIMIT_EXCEEDED` не увеличивает `dailyUsed` и `monthlyUsed` отправителя.

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ

1. Какое значение `singleMax` должно быть по умолчанию? В коде оно не найдено.
2. Лимит на один перевод должен быть глобальным для всех отправителей или индивидуальным для каждого отправителя? В текущей постановке и существующем коде дневной/месячный лимиты глобальные.
3. Должны ли лимиты учитывать валюту перевода? Сейчас валюта в проверке лимитов не участвует.
4. Нужны ли ограничения между лимитами: например, `singleMax <= dailyMax`, `dailyMax <= monthlyMax`?
5. Можно ли устанавливать лимиты в `0`? Это означает полный запрет соответствующих переводов или `0` должен трактоваться как «без лимита»?
6. Требуется ли авторизация/аутентификация для API управления лимитами? В коде её нет.
7. Нужна ли история изменений лимитов и указание, кто и когда изменил значения?
8. Нужно ли добавить OpenAPI-спецификацию для API управления лимитами? Сейчас OpenAPI есть только у `transfer-service`.
9. Нужно ли публиковать API управления лимитами через отдельный порт/шлюз или достаточно открыть порт `limit-service` в `docker-compose`?
10. Что делать, если текущие накопленные расходы отправителя уже превышают новые уменьшенные лимиты? Новые лимиты должны влиять только на будущие переводы?
