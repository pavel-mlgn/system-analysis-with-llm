Изучил предоставленный исходный код. Проект состоит из единственного файла `TransferService.java`, содержащего заглушку метода `processTransfer`. Детали реализации лимитов, структура БД, API, модели данных и другие сервисы в коде **отсутствуют**.

Ниже — постановка на доработку, составленная строго на основе предоставленного кода и требований бизнеса.

## 1. ЦЕЛЬ ДОРАБОТКИ
Добавить для всех отправителей ограничение на максимальную сумму **одного** перевода и REST API для управления всеми лимитами (дневной, месячный, максимальный перевод). Исключить возможность обхода лимитов через дробление суммы на несколько операций в рамках одного дня.

## 2. ПРЕДПОСЫЛКИ
Текущая система проверяет только дневной и месячный агрегированные лимиты (реализация в `TransferService.processTransfer` — заглушка). Отправитель может совершить единственный перевод на всю сумму дневного лимита, что нарушает бизнес-правила ряда сценариев (антифрод, комплаенс, контроль рисков). Доработка устраняет этот пробел и даёт операционному отделу инструмент управления лимитами без перевыпуска кода.

## 3. SCOPE ИЗМЕНЕНИЙ

## 4. АРХИТЕКТУРНЫЕ РЕШЕНИЯ

### Вариант А: Лимиты — часть таблицы `senders`
- Добавить колонки `daily_limit`, `monthly_limit`, `max_single_transfer` прямо в `senders`.
- **Плюс**: простой доступ, одна строка на отправителя.
- **Минус**: историчность не сохраняется, аудит изменений — только триггерами.

### Вариант Б: Отдельная таблица `sender_limits`
- `sender_id`, `limit_type` (дневной/месячный/макс_перевод), `value`, `updated_at`.
- **Плюс**: историчность, гибкое добавление новых типов лимитов.
- **Минус**: JOIN при каждой проверке.

**Рекомендуемый**: **Вариант Б** с материализованным представлением / кешем в памяти, т.к. требования к аудиту и расширению типов лимитов очевидны из задачи. Валидацию выполнять **до** списания дневного/месячного лимита, чтобы не расходовать агрегированные лимиты на отклонённый перевод.

## 5. ОПИСАНИЕ ИЗМЕНЕНИЙ

### 5.1. Сервис переводов (`TransferService`)

#### Изменения в БД
- **Новая таблица** `sender_limits`:
  - `id` BIGINT PK
  - `sender_id` BIGINT NOT NULL FK → `senders(id)`
  - `limit_type` VARCHAR(32) NOT NULL CHECK (limit_type IN ('DAILY', 'MONTHLY', 'MAX_SINGLE_TRANSFER'))
  - `value` DECIMAL(18,2) NOT NULL CHECK (value >= 0)
  - `updated_at` TIMESTAMP DEFAULT NOW()
  - UNIQUE (sender_id, limit_type)
- **Новый индекс**: `idx_sender_limits_type` на (`sender_id`, `limit_type`).

#### Изменения в API
Эндпоинты нового контроллера (`/api/v1/senders/{senderId}/limits`):

**GET** — просмотр всех лимитов отправителя

| Параметр | Источник | Тип | Обяз. | Описание |
|---|---|---|---|---|
| `senderId` | path | bigint | да | ID отправителя |

Ответ (200):
```json
{
  "daily": 100000.00,
  "monthly": 500000.00,
  "maxSingleTransfer": 50000.00
}
```

Коды: 200, 404 (не найден), 403 (нет прав).

**PATCH** — изменение значения лимита

| Параметр | Источник | Тип | Обяз. | Описание |
|---|---|---|---|---|
| `limitType` | body | enum | да | DAILY / MONTHLY / MAX_SINGLE_TRANSFER |
| `value` | body | decimal | да | Новое значение ≥ 0 |

Ответ (200) — обновлённый объект лимитов.

Коды: 200, 400 (невалидный тип/значение), 404, 403.

#### Изменения в бизнес-логике
- **При** `amount > maxSingleTransfer` **система должна** вернуть ошибку с причиной `SINGLE_TRANSFER_EXCEEDED` **до** проверки дневного/месячного лимитов.
- **При** успешной проверке `maxSingleTransfer` **система должна** продолжить проверку дневного и месячного лимитов (без изменений их логики).
- Метод `processTransfer` должен принимать `maxSingleTransfer` из кеша/таблицы, а не использовать захардкоженное значение.

#### Контракты сообщений
- Добавить поле `rejectionReason` со значением `SINGLE_TRANSFER_EXCEEDED`.
- Обновить enum `TransferStatus` → `REJECTED`.

### 5.2. Остальные компоненты
- **Таблица `senders`**: изменений нет (кроме FK из `sender_limits`).
- **Сервис нотификаций**: изменений нет — отклонение обрабатывается на уровне API Gateway / контроллера.
- **Брокер сообщений**: изменений нет.

## 6. ВЛИЯНИЕ СУЩЕСТВУЮЩИХ АНОМАЛИЙ
- В предоставленном коде `TransferService.processTransfer` — пустая заглушка. Аномалий не обнаружено.
- **Риск**: если в реальной БД уже есть данные с `amount`, превышающими будущий `maxSingleTransfer`, миграция не заблокирует их — потребуется скрипт валидации существующих переводов (открытый вопрос).

## 7. КРИТЕРИИ ПРИЁМКИ

| Условие | Ожидаемый результат |
|---|---|
| Перевод 30 000 при `maxSingleTransfer = 20 000` | HTTP 422, причина `SINGLE_TRANSFER_EXCEEDED` |
| Перевод 15 000 при дневном лимите 10 000 (остаток 0) | HTTP 422, причина `DAILY_LIMIT_EXCEEDED` |
| PATCH `value = 0` | 200, последующие переводы отклоняются |
| PATCH `value = -100` | 400, ошибка валидации |
| GET для несуществующего sender | 404 |
| Два перевода по 15 000 при `maxSingleTransfer = 20 000` и дневном лимите 30 000 | Первый — 200, второй — 422 (дневной лимит) |

## 8. ОТКРЫТЫЕ ВОПРОСЫ К БИЗНЕСУ
1. **Структура хранения**: существует ли таблица `senders` и как она связана с сервисом (монолит / БД на сервис)? Требуется DDL.
2. **Идемпотентность**: должен ли PATCH быть идемпотентным (перезапись) или версионированным?
3. **Права доступа**: кто может менять лимиты — только админ, или также сам отправитель (B2B)?
4. **Историчность**: хранить ли историю изменений лимитов (таблица `sender_limit_audit`)? Требование не озвучено.
5. **Влияние на существующие переводы**: нужно ли отклонить **уже созданные** переводы, превышающие новый порог, или только новые?
6. **Формат ошибки**: точный текст `rejectionReason` и HTTP-статус (422 vs 400) — требуется согласование с API-ревью.
7. **Кеширование**: TTL кеша лимитов (влияет на скорость проверки). Без кеша — прямой SELECT при каждом переводе.
